# Appointment Gotchas — Odoo 18.0 **Enterprise (EE)**

> **EE-only.** `appointment` es módulo Enterprise (license OEEL-1, `odoo_enterprise/18/appointment/`). No existe en Community. Verificado contra fichero:línea de v18 (diffs v17/v19 anotados).

## Slot generation & timezones

**APG1. Slot start times use `appointment_tz`, not `tz_offset` of the visitor** — `_slots_generate()` localizes hours in `appointment_tz` and converts to visitor `timezone` for display. Impact: a 9 AM Madrid slot shows as 8 AM for a London visitor, but the underlying `calendar.event.start` is stored at the Madrid 9 AM moment in UTC. Don't rely on visitor tz for storage. _ES: La hora de la cita se guarda en la zona horaria de la empresa, no en la del visitante; a cada uno le aparece una hora distinta._

**APG2. `min_schedule_hours` is added to the FIRST slot only when reference_date is "near now"** — `ref_start = ref_date + min_schedule_hours` only if `ref_date <= now + min_schedule_hours` (`appointment/models/appointment_type.py:631-632`, `AppointmentType._slots_generate`; el campo, `appointment/models/appointment_type.py:128`, `AppointmentType.min_schedule_hours`). Impact: passing a future `reference_date` skips the buffer; embedding the booking widget with a shifted ref date can offer slots within the lead time. _ES: El tiempo mínimo de antelación para reservar se salta cuando la cita parte de una fecha futura (p.ej. widget incrustado) y se ofrecen huecos dentro del margen._

**APG3. Custom appointments rely on `slot.end_datetime > reference_date`, not `start_datetime`** — Past slots are filtered by their end. Impact: in-progress slots remain bookable; visitors can book a slot already started. Block this in your override of `_check_appointment_is_valid_slot`. _ES: Se puede reservar un hueco que ya ha empezado; las citas en curso siguen apareciendo como disponibles._

**APG4. `recurring` slots are filtered by `byweekday=int(weekday)-1`** — `appointment.slot.weekday` is a string '1'..'7' (Mon..Sun); the `_slots_generate` does `int(x.weekday) == day.isoweekday()` later. Impact: importing slots with weekday='0' (Sunday in some conventions) silently skips. Use `'7'`. _ES: Al importar horarios semanales, los del domingo no aparecen y ese día queda sin huecos disponibles._

## Status & cancellation

**APG5. Setting `active=False` auto-cancels the appointment, and vice-versa** — `calendar_event.write()` syncs `active` ↔ `appointment_status='cancelled'` in both create and write (lines 225-237). Impact: a manager archiving a calendar event silently flips the appointment status; un-archiving sets back to `booked` regardless of previous state (was it `request`? Lost). _ES: Al archivar una cita del calendario se cancela sola, y al desarchivarla vuelve a 'reservada' perdiendo su estado anterior._

**APG6. `appointment_status` cascades only when the type is set/changed** — `_compute_appointment_status` (store=True, readonly=False): if `appointment_type_id` is removed, status is wiped to `False`. Impact: detaching the type loses the booked/attended/no-show history. _ES: Si quitas el tipo de cita se borra su estado y se pierde el historial de asistido, no presentado o reservado._

**APG7. `_send_invitation_emails()` only fires when status TRANSITIONS to `booked`** — Filter `unconfirmed_bookings = appointment_status != 'booked'` BEFORE write, then re-filter `== 'booked'` AFTER. Impact: re-saving a `booked` event without changes does NOT resend the email; manual edits to booked events don't re-notify the attendee. _ES: Al volver a guardar una cita ya confirmada no se reenvía el correo de invitación al cliente._

**APG8. Cancellation via portal token does NOT delete; it archives via `action_cancel_meeting`→`action_archive`** — Portal `/calendar/cancel/<token>` calls `event.action_cancel_meeting()` (`appointment/controllers/calendar.py:127-138`, `AppointmentCalendarController.appointment_add_attendee`), which always `self.action_archive()` (`appointment/models/calendar_event.py:364-378`, `CalendarEvent.action_cancel_meeting`) → `active=False` → status `cancelled` (via APG5). The "remove only the cancelling attendees when >2" behaviour described in the docstring is NOT implemented in v18 — it archives the whole event regardless of `partner_ids`. Impact: cancelled bookings stay in DB taking up calendar grid space; cleaning requires explicit unlink. _ES: Al cancelar desde el portal la cita no se borra, solo se archiva, y sigue ocupando hueco en la agenda._

## Capacity & resources

**APG9. `capacity_used` ≠ `capacity_reserved` when resource is not shareable** — `_compute_capacity_used` returns `resource.capacity` (full size) when `not shareable or not manage_capacity`. Impact: reserving 2 seats on a non-shareable 6-seat table consumes all 6 from availability. Subtle bug: customer thinks 4 are still free, system blocks them. _ES: Reservar unas pocas plazas en un recurso no compartible bloquea toda su capacidad y aparece como lleno indebidamente._

**APG10. `linked_resource_ids` is symmetric across two M2M tables** — Source + destination relationships both go through `appointment_resource_linked_appointment_resource`, written on either side. `_inverse_linked_resource_ids` keeps them in sync. Impact: writing through `source_resource_ids` only doesn't break, but any custom code reading just `source_resource_ids` misses combinations created from the other side. _ES: Los recursos combinados no se ven completos si tu código solo lee un lado de la relación entre recursos enlazados._

**APG11. Resource `shareable=True` means same slot can be reserved by multiple attendees with separate booking lines** — Capacity is summed across booking lines. Impact: setting shareable on a non-divisible resource (a doctor) lets two people book the same slot — no concurrency lock at DB level, only domain check at slot fill. _ES: Marcar un recurso como compartible permite que dos personas reserven el mismo hueco a la vez sin bloqueo._

**APG12. `staff_user_ids` domain `[('share','=',False)]` excludes portal users** — Set on the M2M field. Impact: portal/external users CAN'T be assigned as staff; HR/recruitment integrations must use internal users. _ES: No puedes asignar usuarios de portal o externos como personal que atiende citas, solo usuarios internos._

## Assignment methods

**APG13. v18 has 3 assign methods (`resource_time`/`time_resource`/`time_auto_assign`); v19 collapses to 2 (`auto`/`manual`)** — Refactor in v19. v18 stores selection on `assign_method`; v19 stores on `assignment_method` + `is_auto_assign` + `is_date_first` + `select_first`. Impact: cross-version code reading `assign_method` breaks in v19; see v19_changes.md. _ES: El código que lee el método de asignación de personal deja de funcionar al pasar de la v18 a la v19._

**APG14. v18 `appointment_manual_confirmation=True` AND v19 `auto_confirm=False` are inverse defaults** — v18 default is auto-confirm (manual flag opt-in). v19 default is `auto_confirm=True` + `manual_confirmation_percentage=1.0`, meaning everything auto-confirms unless capacity > 100% (impossible). Toggling `auto_confirm=False` in v19 mirrors `appointment_manual_confirmation=True` in v18. Impact: data migration must invert the boolean semantics. _ES: Tras migrar a v19 las citas se confirman automáticamente cuando antes pedían confirmación manual, semántica invertida._

## Invitations & URLs

**APG15. `appointment.invite.short_code` is validated against `^[\w-]+$`** — `SHORT_CODE_PATTERN = re.compile(r"^[\w-]+$")` (`appointment/models/appointment_invite.py:13`, `SHORT_CODE_PATTERN`), checked in `_compute_short_code_warning` (`:146-151`) and raised by `_check_short_code_format` (`:79-85`); UNIQUE constraint `short_code_uniq` at DB (`:59-61`). CAUTION: in Python 3 `\w` is Unicode by default, so accented/multilingual chars (`José`, `café`) PASS — the only things rejected are spaces, slashes, `?`, `&`, `=` and other punctuation. Impact: pasting `?utm=...` raises ValidationError, but the common assumption that accents are rejected is FALSE. _ES: Pegar parámetros de URL en el código corto de la invitación da error de validación, aunque las tildes sí se aceptan._

**APG16. Filter `staff_user_ids`/`resource_ids` on the invite must be SUBSETS of the type's pool** — No SQL constraint; enforced only when generating slots. Impact: removing a user from a type after creating an invite leaves stale references that silently disappear from the booking page. _ES: Quitar un usuario o recurso del tipo tras crear la invitación deja referencias muertas que desaparecen de la página de reserva._

**APG17. `appointment.invite` has many2many to multiple types but no priority order** — Visitor sees all types in the order returned by `appointment_type_ids` (which uses `sequence,id`). Impact: there's no per-invite override of order; if you want a specific type first you must adjust the global sequence. _ES: No se puede fijar el orden de los tipos de cita por invitación; se ordenan según la secuencia global._

## Calendar integration

**APG18. `calendar.event.access_token` is generated lazily for OLD events** — `_init_column` skips token generation on module install/upgrade. Impact: pre-existing events get tokens only when accessed via portal; bulk migrating links via a script fails for events that haven't been touched. Run `event._generate_access_token()` first. _ES: Los enlaces de portal fallan en citas antiguas porque no tienen token generado hasta que se abren una vez._

**APG19. Two separate computes: `_compute_videocall_redirection` builds the URL, `_compute_videocall_source` chooses the provider** — `_compute_videocall_redirection` (`appointment/models/calendar_event.py:188-196`, `class CalendarEvent`) returns `False` when `videocall_location` is empty, else `{base}/calendar/videocall/{access_token}`. The provider is set by `_compute_videocall_source` (`:198-206`), which copies `appointment_type_id.event_videocall_source` onto the event and falls back to `super()._compute_videocall_source()` ONLY for events with no appointment type (or non-Discuss locations). Impact: if you clear `event_videocall_source` on the type, the appointment event gets NO Discuss room and `videocall_location`/`videocall_redirection` stay empty — the base fallback does NOT run for appointment events. Don't anchor logic on `videocall_redirection`'s depends; it only tracks `videocall_location`/`access_token`. _ES: Si borras el proveedor de videollamada del tipo, la cita se queda sin sala de reunión y sin enlace de vídeo._

**APG20. Reminders only inherit from type at event CREATION** — `_compute_alarm_ids` fills only when `not event.alarm_ids`. Impact: changing `appointment.type.reminder_ids` doesn't propagate to existing events; you must rewrite each event or add an override. _ES: Cambiar los recordatorios del tipo de cita no afecta a las citas ya existentes, solo a las nuevas._

## Multi-company

**APG21. `appointment.type` has no `company_id`** — Single-company by design. Impact: in multi-company setups, all appointment types are visible to all users with the group; staff/resources span companies. Customizations adding `company_id` must add record rules and update `default_get`. _ES: En multicompañía todos los tipos de cita, personal y recursos se ven entre empresas porque no filtran por compañía._

## Performance

**APG22. `_slots_fill_users_availability` reads staff calendar events via `_slot_availability_prepare_users_values_meetings`, filtered `show_as='busy'`** — The search domain is `[('partner_ids','in', staff_users.partner_id.ids), ('show_as','=','busy'), ('stop','>=',day_min), ('start','<=',day_max)]` (`appointment/models/appointment_type.py:1172-1184`, `AppointmentType._slot_availability_prepare_users_values_meetings`; fill at `:1037`). NOTE: it's NOT "all events" — events marked `show_as='free'` are skipped, but PRIVATE events whose `show_as='busy'` ARE counted (privacy doesn't exclude them). Impact: heavy busy calendars on shared staff make slot computation slow; a staff member can hide a slot just by marking a personal event as busy. _ES: El cálculo de huecos va muy lento con agendas cargadas, y un empleado oculta un hueco marcando un evento personal como ocupado._

**APG23. `_get_appointment_slots` builds the entire month grid in Python (no SQL aggregation)** — Calendar dates iterated week-by-week, slots popped one by one. Impact: visible month with high `max_schedule_days` (>90) is CPU-bound. Tune via `min_schedule_hours` and reasonable upper limits. _ES: La página de reservas se vuelve muy lenta cuando se permite mostrar muchos días o meses por delante._

## Migration v18→v19

**APG24. v19 introduces `appointment.question.is_default` + `is_reusable` + `appointment_type_ids` (M2M)** — v18 had `appointment_type_id` (M2O ondelete='cascade'); v19 makes questions reusable across types via M2M (`appointment_type_appointment_question_rel`). Impact: migrating destroys ondelete cascade; orphaned questions remain. Default questions auto-attach to new types via `_default_question_ids` (search `is_default=True`). _ES: Al migrar a v19 quedan preguntas huérfanas porque cambia el vínculo entre preguntas y tipos de cita._

**APG25. v19 splits frontend assets from `js/` into `interactions/`** — `appointment_form.js`, `appointment_validation.js`, `appointment_select_appointment_*.js` moved to `static/src/interactions/`. v18 `wysiwyg.js` removed. Impact: any custom frontend extending those JS modules must update imports. _ES: Tras migrar a v19 el código JavaScript personalizado del formulario de reserva deja de cargar por cambio de rutas._

## Slot config & constraints (verified v18)

**APG83. `end_hour=0` means "next day midnight" (24:00), not "00:00 same day"** — `appointment_slot._convert_end_hour_24_format()` maps `end_hour=0 → 24` (`appointment/models/appointment_slot.py:97-106`, `AppointmentSlot._convert_end_hour_24_format`). The SQL constraint `check_start_and_end_hour` explicitly allows `end_hour=0 AND start_hour BETWEEN 0 AND 23.99` (`appointment/models/appointment_slot.py:51-58`, `class AppointmentSlot`). Impact: a slot `08:00–00:00` is a 16h window ending at midnight, NOT a zero-length/inverted slot. Importing `end_hour=0` thinking it's "midnight start" silently creates an all-day-until-midnight slot. _ES: Al importar un horario que acaba a las 00:00 se crea un hueco que dura todo el día hasta medianoche, no uno de inicio a medianoche._

**APG84. `_compute_end_hour` auto-shifts `end_hour` when it's below `start_hour`** — If the entered `end_hour` (24-format) ≤ `start_hour` and `start_hour + duration ≤ 24`, the compute silently sets `end_hour = (start_hour + duration) % 24` (`appointment/models/appointment_slot.py:75-82`, `class AppointmentSlot`). Impact: typing an end before the start doesn't raise — it's quietly rewritten to `start + appointment_duration`. The user sees a different end than they typed. _ES: Si pones una hora de fin anterior a la de inicio, el sistema la reescribe sola y muestra una hora de fin distinta a la tecleada._

**APG85. `_check_delta_hours` requires the slot window to fit at least ONE full `appointment_duration`** — Constraint at `appointment/models/appointment_slot.py:84-90`, `class AppointmentSlot` rejects recurring slots where `start_hour + appointment_duration > end_hour(24fmt)`. Impact: shortening a slot below the type's duration, or raising the type's `appointment_duration` above an existing slot's span, raises a ValidationError that points at the slot, not the type — confusing when the real cause is a duration change on the parent type. _ES: Al subir la duración de la cita o acortar un horario salta un error que señala al hueco, cuando la causa real es la duración del tipo._

**APG86. `_compute_restrict_to_user_ids` silently drops users no longer in `staff_user_ids`** — `slot.restrict_to_user_ids &= slot.appointment_type_id.staff_user_ids` (`appointment/models/appointment_slot.py:122-125`, `class AppointmentSlot`, intersection with `&=`). The twin `_compute_restrict_to_resource_ids` (`:117-120`) does the same with `resource_ids`. Impact: removing a user from the type's pool silently empties that user out of every slot's restriction — a slot restricted to only that user becomes restricted to nobody (= available to all). No warning. _ES: Quitar un usuario del tipo de cita vacía la restricción de sus huecos, que pasan a estar disponibles para todos sin avisar._

**APG87. `slot_type` is computed from category, not directly settable** — `_compute_slot_type` forces `unique` iff `category=='custom'`, else `recurring` (`appointment/models/appointment_slot.py:71-73`, `AppointmentSlot._compute_slot_type`, store=True). Impact: you cannot mix unique + recurring slots on one type; flipping the type's category rewrites every slot's `slot_type`. `_check_unique_slot_has_datetime` (`appointment/models/appointment_slot.py:92-95`, `class AppointmentSlot`) then requires `start_datetime`/`end_datetime` on unique slots — a category flip on slots without datetimes raises. _ES: No puedes mezclar huecos únicos y recurrentes en un tipo; cambiar la categoría reescribe todos los huecos y puede dar error._

## Capacity & resources (verified v18)

**APG88. `capacity_used >= capacity_reserved` is a hard SQL constraint, not just a compute** — `appointment/models/appointment_booking_line.py:27-30`, `class AppointmentBookingLine` (`CHECK(capacity_used >= capacity_reserved)`). Combined with APG9 (`capacity_used = resource.capacity` when non-shareable), reserving more than the resource's physical capacity on a non-shareable resource cannot violate it (capacity_used = full size ≥ reserved), but a custom override that lowers `capacity_used` below `capacity_reserved` hits a raw PG error. _ES: Un código a medida que baje la capacidad usada por debajo de la reservada revienta con un error crudo de base de datos._

**APG89. Resource `sequence` decides combination priority, lowest first** — `appointment.resource._order='sequence,id'` (`appointment/models/appointment_resource.py:12`, `class AppointmentResource`); `_get_filtered_possible_capacity_combinations` returns `sorted(..., key=lambda c: (c[1], len(c[0])))` i.e. by `(remaining_capacity, number_of_resources)` (`:91-113`), and `_get_possible_capacity_combinations` walks `linked_resource_ids.sorted('sequence')` (`:132`). Impact: the smallest-remaining-capacity / fewest-resources combo is picked first, and within linked combinations the lowest-sequence resource is added first. Re-sequencing resources silently changes which table gets booked for a given party size — surprises in restaurant setups expecting a specific table order. _ES: Reordenar los recursos cambia sin avisar qué mesa o recurso se reserva para un grupo, sorpresas al asignar mesas de restaurante._

**APG90. `appointment.resource.company_id` defaults to `False` (no company)** — Explicit `company_id = fields.Many2one(default=False)` (`appointment/models/appointment_resource.py:19`, `class AppointmentResource`). Impact: resources are company-agnostic by default, mirroring `appointment.type` (APG21). In multi-company a resource booked under company A is visible/bookable under company B unless you add a company manually + record rules. _ES: En multicompañía un recurso reservado en una empresa se ve y reserva desde otra porque no tiene compañía asignada._

**APG91. `capacity_reserved=0` zeroes `capacity_used` — a "ghost" booking line** — `_compute_capacity_used`: `if capacity_reserved == 0: capacity_used = 0` (`appointment/models/appointment_booking_line.py:47-48`, `AppointmentBookingLine._compute_capacity_used`). Impact: a booking line with 0 reserved consumes no capacity but still links a resource to the event. Bulk-imported or buggy lines with 0 reserved silently free up the slot while appearing booked in the UI. _ES: Una línea de reserva con cero plazas no consume capacidad pero mantiene el recurso ligado, liberando el hueco aunque parezca reservado._

## Cancellation window (verified v18)

**APG92. Portal cancel is blocked by `min_cancellation_hours`, measured from NOW against event start** — `_get_prevent_cancel_status` returns `'no_time_left'` if `event.start < now() + min_cancellation_hours` (`appointment/controllers/calendar.py:151-158`, `AppointmentCalendarController.appointment_cancel`). For all-day events it uses `start_date`. Impact: default `min_cancellation_hours=1.0` (`appointment/models/appointment_type.py:127`, `AppointmentType.min_cancellation_hours`) silently forbids portal cancellation within 1h of the slot — the attendee sees "no time left" with no path to cancel; only a backend user can archive it. _ES: El cliente no puede cancelar desde el portal en la última hora antes de la cita y solo ve 'sin tiempo suficiente'._

**APG93. `_check_appointment_is_valid_slot` re-runs full slot generation on every booking submit (sudo)** — `appointment/models/appointment_type.py:936-969`, `AppointmentType._check_appointment_is_valid_slot` regenerates slots and re-checks availability at submit time as `sudo()` (public/portal users lack read on the type). Impact: a slot that passed the front-end grid can be rejected at submit if availability changed; for `recurring` slots it also enforces `appointment_duration == duration` exactly (`float_compare ... != 0`), so any duration tampering in the POST silently fails the slot with no specific error. _ES: Un hueco que se veía libre se rechaza al confirmar la reserva porque la disponibilidad cambió, sin mensaje de error claro._

**APG95. `_compute_category` only decides `recurring` vs `punctual`; `custom`/`anytime` come from the inverse** — `_compute_category` (`appointment/models/appointment_type.py:242-246`, `AppointmentType._compute_category`) sets `punctual` iff `start_datetime or end_datetime` else `recurring`, and auto-fills default slots if none. `custom` and `anytime` are NEVER produced by the compute — they are set through `_inverse_category` (`:248-254`) / `category_time_display`. Impact: writing `start_datetime` on a `custom` type silently recomputes it to `punctual` and wipes the hand-picked unique slots via the default-slot generation; you cannot make a type `custom` just by clearing datetimes.** _ES: Poner fechas a un tipo de cita personalizado lo convierte en puntual y borra los huecos elegidos a mano._

**APG96. `appointment.invite` autovacuums itself after 6 months** — `@api.autovacuum _gc_appointment_invite` (`appointment/models/appointment_invite.py:262-269`, `class AppointmentShare`) unlinks every invite older than 6 months whose bookings are all in the past (or that has no bookings). Impact: long-lived shareable `/book/<short_code>` links silently 404 after 6 months even if still pinned somewhere; don't treat invite URLs as permanent. _ES: Los enlaces de reserva compartidos dejan de funcionar y dan error 404 pasados seis meses, aunque los tengas guardados._

**APG97. `short_code` auto-dedupes on default, but a manual duplicate only WARNS until save** — default `_get_unique_short_code` (`appointment/models/appointment_invite.py:255-260`, `AppointmentShare._get_unique_short_code`) appends `_<n>` to avoid collisions, but a user-typed duplicate is caught by `_compute_short_code_warning` → `short_code_unique_warning` (`:146-151`) which only disables the save button (`_compute_disable_save_button` `:69-77`); the hard guard is the DB `UNIQUE` constraint. Impact: programmatic `create()`/`write()` bypassing the onchange hits a raw `short_code_uniq` IntegrityError, not a friendly ValidationError. _ES: Crear invitaciones por código con un código corto duplicado revienta con error de base de datos en vez de un aviso amigable._

**APG98. `appointment.booking.line._check_resources_match_appointment_type` blocks resources not in the type's pool** — `@api.constrains` (`appointment/models/appointment_booking_line.py:32-40`, `class AppointmentBookingLine`) raises if `line.appointment_resource_id` is not in `appointment_type.resource_ids`. Impact: removing a resource from the type while bookings reference it, then touching those lines, raises a ValidationError naming the resource — archive/unbook first. Also `_order='event_start desc, id desc'` (`:12`) means booking-line lists are newest-first, not creation order. _ES: Si quitas un recurso del tipo mientras hay reservas que lo usan, al tocar esas líneas salta un error de validación._

**APG99. `appointment.resource` forces `resource_type='material'` on the underlying `resource.resource`** — `_prepare_resource_values` override (`appointment/models/appointment_resource.py:144-149`, `AppointmentResource._prepare_resource_values`) hard-sets `resource_type='material'`. Impact: an appointment resource never behaves as a `human` resource even if you link it to an employee; HR/working-hours logic that branches on `resource_type=='human'` will skip appointment resources. _ES: Un recurso de cita siempre se comporta como material aunque lo vincules a un empleado, ignorando la lógica de horarios de RRHH._

**APG100. `capacity` SQL constraint requires `>= 1`, but `capacity_reserved` only `>= 0`** — `appointment.resource` has `check(capacity >= 1)` (`appointment/models/appointment_resource.py:54-56`, `class AppointmentResource`) while `appointment.booking.line` allows `capacity_reserved >= 0` (`appointment/models/appointment_booking_line.py:28`, `class AppointmentBookingLine`). Combined with APG91 (reserved=0 → used=0), a 0-reserved line is legal at DB level. Impact: importing resources with capacity 0 fails hard; importing booking lines with 0 reserved succeeds but creates the capacity-free "ghost" line of APG91. _ES: Importar recursos con capacidad cero falla, pero importar líneas de reserva con cero plazas cuela y crea líneas fantasma._

**APG94. `allow_guests` lets attendees add arbitrary guest partners — but guests are dropped on paid-booking conversion** — `allow_guests` (`appointment/models/appointment_type.py:68`, `class AppointmentType`) feeds `guests` into `_prepare_calendar_event_values`. Cross-ref APG33P: the paid (`appointment_account_payment`) path ignores `guest_ids` when converting booking→event. Impact: enabling guests + payment step silently loses everyone except the main customer + staff user. _ES: Al activar invitados y cobro por la cita se pierden todos los acompañantes menos el cliente principal al convertir la reserva._
