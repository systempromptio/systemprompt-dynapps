# Documents Gotchas — Odoo 18.0/19.0 Enterprise (EE, OEEL-1)

Comportamientos ocultos y fallos silenciosos del stack Documents. Numerados (DOG*) para indexar en `_index/symptoms.md`. Fuente verificada con `fichero:línea` en `odoo_enterprise/18/documents/` y bridges. Bridges → [[integrations]].

## Permissions

**DOG1. `owner_id` ALWAYS gets `edit`, even if `access_via_link='none'`** — `_get_permission_without_token_multi()` short-circuits if `document.owner_id == self.env.user`. Impact: setting an "ex-owner" as another user but forgetting to change ownership leaves them with full edit rights silently. _ES: El antiguo propietario de un documento sigue pudiendo editarlo aunque le haya quitado el acceso o puesto el enlace en 'ninguno'._

**DOG2. `access_internal='view'` is COMPANY-WIDE** — Applies to every internal user (`not user.share`) subject to the `company_id` cross-company check (`documents/models/documents_document.py:406-417`, `Document._get_permission_without_token_multi`). Impact: setting it on a sensitive document leaks to all internal users; use `access_ids` for specific people. _ES: Al marcar un documento como visible internamente lo pueden ver todos los usuarios internos de la empresa, no solo a quien yo quería._

**DOG2b. `group_documents_manager` is silently PROMOTED to `edit` on any `access_internal != 'none'` doc** — `_get_permission_without_token_multi` (`documents/models/documents_document.py:413-416`, `Document._get_permission_without_token_multi`): if the user is in `documents.group_documents_manager`, an internal-view document grants `edit`, not `view`. Impact: "Documents Administrator"-level users can edit every doc that anyone marked internal-visible, even when the intended role was view-only. Plain `group_documents_user` gets the literal `access_internal` role. _ES: Los usuarios administradores de Documentos pueden editar cualquier documento marcado como visible internamente, aunque solo debía ser de lectura._

**DOG3. `access_via_link` propagates from parent folder unless `is_access_via_link_hidden=True`** — Children inherit parent's link role one level deep. Impact: putting a sensitive doc in a "shared with link" folder makes it accessible via link too, even if you didn't explicitly set sharing on the doc. _ES: Un documento se abre por enlace sin haberlo compartido, solo por estar dentro de una carpeta que sí se comparte por enlace._

**DOG4. `documents.access` rows allow `role=NULL` if `last_access_date IS NOT NULL`** — CHECK constraint allows null role for "audit-only" entries (someone who once viewed). Impact: `_compute_user_permission` skips null roles, but lookup tools showing access lists must handle the null case. _ES: En la lista de accesos aparecen personas sin permiso asignado, que solo consultaron una vez, y confunden la auditoría._

**DOG5. Cross-company documents hide silently when company is not in `env.companies`** — `is_disabled_company` check returns `permission='none'` even if user has access. Impact: switching company in the UI makes documents disappear; users think permissions were revoked. _ES: Al cambiar de compañía los documentos desaparecen y el usuario cree que le han revocado los permisos._

**DOG6. `documents.group_documents_system` (admin) can edit documents from companies they DON'T belong to, IF that company is currently active** — Check is `company in env.companies OR company NOT in user.company_ids`. Impact: superusers can break audit trails on companies they shouldn't manage. _ES: Un administrador puede editar documentos de compañías a las que no pertenece si están activas, alterando el historial._

## Tokens & sharing

**DOG7. `access_token` is `document_token + 'o' + hex(id)`** — Embedded ID makes tokens predictable per document_token. Impact: leaking a token leaks the ID; rotating tokens requires regenerating `document_token` (UUID). _ES: El token de acceso lleva dentro el ID del documento: filtrar un enlace expone el documento y rotarlo obliga a regenerarlo entero._

**DOG8. Member sign-up token is HMAC over `(access.id, partner.id)`** — Removing the `documents.access` row invalidates ALL pending sign-up links. Impact: bulk deletion of access rows breaks email links sent earlier; users get "Invalid token" with no explanation. _ES: Al borrar en bloque filas de acceso, los enlaces de invitación enviados antes por email dejan de funcionar y dan 'token inválido'._

**DOG9. `_is_signup_available()` checks `_get_signup_invitation_scope() == 'b2c'`** — Only works if Sign-up policy is "Free sign up" globally. Impact: B2B-only instances can't generate share-and-signup links; admins flip the global policy without realizing. _ES: No se pueden generar enlaces para compartir e invitar a registrarse salvo que el registro libre esté activado globalmente._

## Trash & deletion

**DOG10. `active=False` is the trash; physical delete after `documents.deletion_delay` days (default 30)** — `_gc_clear_bin` runs in autovacuum (`documents/models/documents_document.py:2314`, `Document._raise_if_used_folder`; el método se llama así, no "_gc_archived_documents", que no existe en la fuente). The cutoff compares `write_date <= now - deletion_delay`, NOT the archive date — `_get_gc_clear_bin_domain` (`:2319`). Impact: any write that bumps `write_date` on a trashed doc (e.g. a bridge touching it) RESETS the 30-day clock; archive ≠ delete; backup/audit must include archived docs. Setting delay to 0 deletes immediately on next vacuum. _ES: Cualquier cambio sobre un documento en la papelera reinicia el contador de 30 días y nunca se llega a borrar físicamente._

**DOG11. Deleting a record using `documents.unlink.mixin` keeps the document, just retargets to itself** — `res_model='documents.document', res_id=document.id, active=False`. Impact: unlinking the source record (e.g., a project task) doesn't lose the file but the link to context is lost; "Open record" navigates to the document. _ES: Al borrar la tarea o registro de origen el archivo no se pierde, pero queda sin contexto y 'Abrir registro' lleva al propio documento._

**DOG12. Folder deletion cascades to child documents only via `_parent_store`** — `folder_id` has `ondelete="set null"`; children become orphans (root). Impact: deleting a folder with 1000s of files orphans them silently rather than archiving them. Use the wizard, not direct unlink. _ES: Borrar una carpeta con miles de archivos los deja sueltos en la raíz en vez de archivarlos, sin avisar._

## Shortcuts

**DOG13. `shortcut_document_id` ondelete='cascade' deletes the shortcut when the source is unlinked** — But trashing source (active=False) leaves shortcuts pointing at archived docs. Impact: shortcuts to trashed sources show "Inaccessible" thumbnails (`thumbnail_status='restricted'`). _ES: Los accesos directos a documentos enviados a la papelera muestran miniatura de inaccesible._

**DOG14. Shortcut name falls back to source name if not set** — `shortcut.name = shortcut.name OR shortcut_document_id.name`. Impact: renaming the source doesn't rename existing shortcuts (they have stored names). Inconsistency until manual refresh. _ES: Renombrar el documento de origen no cambia el nombre de los accesos directos ya creados; conservan el nombre antiguo._

## Email-to-document (alias)

**DOG15. Only NON-shortcut folders can have `alias_name`** — Constraint `_check_alias` (`documents/models/documents_document.py:287-293`, `class Document`) rejects `alias_name` when `type != 'folder' OR shortcut_document_id` set. Impact: trying to set an alias on a regular file — or on a *shortcut to* a folder — raises ValidationError (caught at form save, but scripted creation fails late). The alias must live on the real folder, not a shortcut to it. _ES: Poner un alias de email en un archivo normal o en un acceso directo a carpeta da error; solo lo admite la carpeta real._

**DOG16. `message_new()` creates ONE document per attachment** — Email with 5 PDFs → 5 documents in one folder, all with `alias_tag_ids` applied. Impact: receipts batched into one email become separate records; if you wanted one consolidated doc you must merge. _ES: Un email con varios adjuntos genera un documento por cada archivo en vez de uno consolidado._

**DOG17. `document_message_new=True` context bypasses `no_document=True` guard** — `_message_post_after_hook` (`documents/models/documents_document.py:1483-1484`, `Document.message_post`): `email_message_new = message.message_type == 'email' and ctx['document_message_new']`; the guard is `if (not ctx['no_document'] or email_message_new) and attachments`. The flag is set ONLY by `message_new` (`:1457`) on inbound email. Impact: `message_post` on a document folder normally forces `no_document=True` (`:1475`) to NOT create docs, but inbound-email posts re-enable creation regardless of `no_document`. There is NO standard `no_document_message_new` flag — to fully suppress you must override `_message_post_after_hook` or `message_new`. _ES: Los correos entrantes a una carpeta siguen creando documentos aunque se haya intentado desactivar la creación automática._

## URL documents

**DOG18. `_compute_name_and_preview` fetches OG metadata synchronously over HTTP** — Per URL document, on the stored compute (`documents/models/documents_document.py:307-321`, `Document._compute_name_and_preview`) via `mail.tools.link_preview.get_link_preview_from_url(url, request_session)`. Each compute batch opens ONE `requests.Session()` (`:308`) reused across all URLs; each fetch has `timeout=3` (`mail/tools/link_preview.py:31`, `get_link_preview_from_url`), `stream=True`, follows redirects. Impact: bulk URL imports of N rows stall up to ~3 s each on slow/unreachable hosts (serialized in the loop); failures are swallowed (`except RequestException` → no preview, name unchanged). It is NOT timeout-free — the cap is 3 s, but it adds up. _ES: Importar muchas URLs a la vez se queda colgado unos segundos por cada una si el servidor remoto va lento o no responde._

**DOG19. URL preview cached as raw image URL, not stored** — `url_preview_image` is a `Char`, not `Image`. Impact: when remote image is removed, broken thumbnail shown; no fallback chain. _ES: Si desaparece la imagen remota de una URL, la miniatura queda rota y sin alternativa._

## Versioning

**DOG20. `previous_attachment_ids` grows unbounded** — No automatic pruning. Impact: 100 versions of a 50 MB PDF = 5 GB storage. No `max_versions` setting; clean via cron if needed. _ES: El historial de versiones de los archivos crece sin límite y ocupa muchísimo espacio; no hay opción para limitar versiones._

**DOG21. Replacing the attachment OVERWRITES `name` with the new file's name** — `name` is a stored compute (`_compute_name_and_preview`, `documents/models/documents_document.py:72`, `Document.name` y `documents/models/documents_document.py:307-313`, `Document._compute_name_and_preview`) that, whenever `attachment_id` changes, sets `record.name = record.attachment_id.name`. Since "Replace file" assigns a new `attachment_id` (`:2024`), swapping `invoice_v1.pdf` for `invoice_v2.pdf` RENAMES the document to `invoice_v2.pdf`, silently discarding any custom name you'd typed. (Name is `readonly=False`, so a manual rename sticks — until the next attachment swap recomputes it.) _ES: Al reemplazar el archivo de un documento se pierde el nombre personalizado y adopta el del archivo nuevo._

## Tags

**DOG22. `documents.tag.name` UNIQUE across ALL companies** — No `company_id` field. Impact: company A creates tag "Confidential", company B tries to create same → SQL error. Multi-company setups must use prefixed naming. _ES: En multicompañía dos empresas no pueden crear la misma etiqueta (por ejemplo 'Confidencial'); salta error de duplicado._

**DOG23. `_unlink_except_used_in_server_action` only checks tags by external_id** — Tags created via UI without xmlid bypass the check. Impact: server actions referencing those tags break silently when the tag is deleted (resource_ref points to nothing). _ES: Borrar una etiqueta creada desde la interfaz rompe en silencio las acciones de servidor que la usaban._

## Activities & requests

**DOG24. `request_activity_id` is M2O on the document, not the activity** — Each document tracks ONE outstanding request activity. Impact: requesting the same document from 2 people is impossible without custom code; second request overwrites first. _ES: No se puede pedir el mismo documento a dos personas a la vez; la segunda solicitud sustituye a la primera._

**DOG25. Requestee can be a non-internal partner** — `requestee_partner_id` is a M2O to `res.partner` (no `share=False` filter). Impact: portal-uploaded files go through public token routes; access tokens must be guarded to prevent enumeration. _ES: Se puede solicitar un documento a un contacto externo o de portal, con lo que el archivo entra por rutas públicas con token._

## Multi-company

**DOG26. Changing a folder's `company_id` CASCADES via raw SQL to every descendant document and its shortcuts** — `write` → `_update_company` (`documents/models/documents_document.py:1057-1093`, `Document._update_company`) runs a recursive `child_of` UPDATE (`SET company_id = ...`) over the subtree AND over shortcuts pointing into it, bypassing the ORM. (It does NOT touch `attachment_id.company_id`.) Moving a doc into a folder also pulls the folder's company (`:2096-2097`). Impact: re-companying a top folder silently relabels thousands of children in one statement (no per-record `write`, no tracking, no recompute hooks fire except an explicit `invalidate_model`); non-admins only cascade where they have `user_permission='edit'` (`:1069`), so a partial-permission move leaves a mixed-company subtree. _ES: Cambiar la compañía de una carpeta reetiqueta en silencio miles de documentos hijos, sin trazabilidad ni recálculo._

**DOG27. Admin (group_documents_system) sees documents from companies in `user.company_ids` even if archived** — `with_context(active_test=False)` on company check. Impact: archived companies' documents are visible to admins; security audits should filter explicitly. _ES: El administrador ve documentos de compañías archivadas; las auditorías de seguridad deben filtrarlos aparte._

## Performance

**DOG28. `_compute_user_permission` is `compute_sudo=True` BUT `depends_context=('uid', 'allowed_company_ids')`** — Each user gets a separate cache entry per context. Impact: kanban with 100 users sharing the database has 100× cache cost; consider materializing for analytical reads. _ES: En bases con muchos usuarios el cálculo de permisos multiplica el coste de caché y ralentiza la vista kanban._

**DOG29. Search panel iterates folder tree to build counts** — No SQL aggregation; one query per folder for descendants count. Impact: deep folder structures slow the side panel; flatter trees recommended. _ES: El panel lateral de Documentos va lento con estructuras de carpetas muy profundas._

**DOG30. v19 introduces `documents.access.tracking` cron-batched audit** — Not in v18. Impact: enabling tracking in v19 (`documents.tracking_batch_size` config) creates a separate model populated by cron; any v18 audit code that queries `documents.access` for last-access fields must adapt. _ES: En v19 el historial de accesos pasa a un modelo aparte poblado por cron y el código de auditoría de v18 deja de encontrar la fecha de último acceso._

## v19 specifics

**DOG31. v19 wizards `documents.operation` and `documents.sharing` replace v18 inline actions** — v18 had per-action ad-hoc methods on `documents.document`; v19 channels move/copy/shortcut/share through transient models. Impact: customizations adding inline action buttons must convert to wizards or the UX diverges. _ES: En v19 mover, copiar o compartir pasa por asistentes; los botones de acción personalizados de v18 dejan de encajar._

**DOG32. v19 `ir.embedded.actions` pinned to a folder require write access on that folder** — `_check_documents_can_pin()` enforces. Impact: pinning an action you can edit but on a folder you can only view raises AccessError; permissions split by location. _ES: En v19 anclar una acción a una carpeta da error de acceso si solo tienes permiso de lectura sobre esa carpeta._

## Bridges (integrations)

**DOG33. OCR no vive en Documents — sin créditos IAP la factura se crea VACÍA y sin error** — `documents` no incluye digitalización; depende de `account_extract`→`iap_extract` (`extract_mixin.py` `extract_state`). `account_create_account_move` (`documents_account/models/documents_document.py:85`, `DocumentsDocument.account_create_account_move`) SIEMPRE crea el `account.move` vía `journal._create_document_from_attachment` (`:124`) sin comprobar créditos ahí mismo; el OCR corre asíncrono después y, si `extract_state='not_enough_credit'`, la factura se queda sin líneas. Impact: el usuario suelta el PDF, ve "factura creada", pero está en blanco; el motivo (sin créditos) solo aparece en el `account.move`, no en Documents. (El método cierra la actividad de la solicitud con `action_feedback('completed')` aunque no haya datos, `:88`.)

**DOG34. Carpeta→diario es UNIQUE por diario** — `documents.account.folder.setting` tiene `unique(journal_id)` (`documents_account/models/documents_account_folder_setting.py:24`, `DocumentsFolderSetting._sql_constraints`). Impact: no puedes mapear dos carpetas distintas al mismo diario; la segunda asignación lanza error SQL. Un diario = una carpeta de digitalización.

**DOG35. Documentos firmados se libran del autovacuum de papelera** — `documents_sign` excluye `res_model='sign.request'` del dominio de limpieza (`documents_sign/models/documents_document.py:47`, `_get_gc_clear_bin_domain` añade `("res_model","!=","sign.request")`). Impact: a diferencia del resto, los documentos generados por firmas NUNCA se purgan automáticamente tras `deletion_delay`; se acumulan indefinidamente. Retención manual obligatoria.

**DOG36. Firma directa exige UN solo documento** — `document_sign_create_sign_template_x` con `create_model='sign.template.direct'` requiere `len(self)==1` (`documents_sign/models/documents_document.py:12`, `DocumentsDocument.document_sign_create_sign_template_x`); con varios seleccionados solo permite el modo plantilla (`sign.template.new`). Impact: acción masiva "firmar directamente" sobre selección múltiple falla; hay que firmar de uno en uno.

**DOG37. Borrar todos los proyectos de una carpeta la ARCHIVA, no la borra** — `_archive_folder_on_projects_unlinked` (`documents_project/models/project_project.py:29`, `ProjectProject._archive_folder_on_projects_unlinked`) pone `active=False` en la carpeta compartida cuando el último proyecto que la usa se elimina. Impact: la carpeta y sus documentos sobreviven archivados; aparecen como "huérfanos" si luego buscas con `active_test=False`, sorprendentemente recuperables.

**DOG38. Carpeta-destino de un bridge debe ser de la misma compañía (o ninguna)** — `documents_project._check_company_is_folders_company` (`documents_project/models/project_project.py:37`, `ProjectProject._check_company_is_folders_company`) y `documents_hr.documents_hr_folder` con `check_company=True` (`documents/models/res_company.py:12`, `Company._reset_default_documents_folder_id`). Impact: en multi-compañía, asignar una carpeta de la compañía A a un proyecto/RRHH de la compañía B lanza ValidationError; cada compañía necesita su propio árbol de carpetas.

**DOG39. Si archivas/borras la carpeta-destino de un bridge, los adjuntos dejan de convertirse en documentos SIN error** — Los bridges (`documents_project`, `documents_hr`, `documents_account`) crean el `documents.document` solo si existe `*_folder_id` válida. Impact: tras perder la carpeta, los adjuntos siguen creándose como meros `ir.attachment` invisibles en Documents; nadie avisa de que la integración se "apagó".

**DOG40. El ACL de una hoja de cálculo es el de Documents, no el del editor** — `documents_spreadsheet` reutiliza `documents.access` para permisos (`documents_spreadsheet/models/documents_access.py` + `ir_http.py`). Impact: un usuario con role=`view` en el `documents.document` de la hoja no puede editarla aunque la lógica de `spreadsheet_edition` lo permitiría; compartir la hoja = compartir el documento. Revisiones/snapshots los gobierna spreadsheet_edition, pero el muro es Documents.

**DOG41. `documents_fsm` NO integra Documents en FSM — lo DESACTIVA** — A diferencia de los demás bridges, su única función es un post-init hook que pone `project.use_documents=False` en los proyectos FSM existentes (`documents_fsm/__init__.py:8`, `_documents_fsm_post_init` y `documents_fsm/__init__.py:29`, `_documents_fsm_post_init`) más el default del campo (`documents_fsm/models/project_project.py:13`, `ProjectProject.default_get`). Impact: instalar `documents`+`industry_fsm` no da gestión documental en tareas de campo; al contrario, la apaga. Ver [[fsm/integrations]].

## NEW (v18 source-anchored, 2026-06)

**DOG42. `owner_id` por defecto es el USUARIO ACTUAL, no OdooBot** — `owner_id = fields.Many2one('res.users', default=lambda self: self.env.user.id, required=True)` (`documents/models/documents_document.py:97`, `class Document`). OdooBot solo es owner por las rutas del mixin (`documents_mixin._get_document_owner` → `base.user_root`, `documents/models/documents_mixin.py:67`, `DocumentMixin._get_document_owner`) y email-a-documento (`:1491`). Impact: cualquier `documents.document.create()` directo (script, import, acción) deja al creador como dueño con `edit` permanente vía DOG1; para "documentos de sistema" sin dueño humano hay que forzar `owner_id=base.user_root` explícitamente.

**DOG43. Cambiar el `owner_id` MANTIENE al dueño anterior como editor explícito** — `write` registra los dueños salientes (`documents/models/documents_document.py:1956-1962`, `Document.write`) y tras el cambio les crea/garantiza un `documents.access` con `role='edit'` (`_ensure_user_role_without_propagation('edit', ...)`, `:2084`). Excepción: si el dueño anterior era OdooBot (`base.user_root`) NO se conserva (`:1957`). Impact: reasignar la propiedad NO revoca el acceso del antiguo dueño; sigue pudiendo editar vía membresía aunque ya no aparezca como owner. Auditorías de "quién puede editar" deben mirar `access_ids`, no solo `owner_id`.

**DOG44. Solo el dueño (o `manager`) puede cambiar el owner; no-managers no pueden re-asignar docs ajenos** — `write` lanza `AccessError` si un no-manager intenta cambiar `owner_id` de un doc cuyo `owner_id != self.env.user` (`documents/models/documents_document.py:1954-1955`, `Document.write`). Impact: un usuario con `edit` por membresía/enlace NO puede transferir la propiedad; necesita ser dueño actual o `group_documents_manager`.

**DOG45. Un usuario portal NO puede ser dueño de un documento raíz** — Constraint `_check_portal_cant_own_root_document` (`documents/models/documents_document.py:280-285`, `Document._check_portal_cant_own_root_document`): falla si `owner_id.share AND not folder_id`. Impact: compartir/asignar a un partner portal un doc sin carpeta (raíz) lanza ValidationError; los docs subidos por portal deben caer siempre dentro de una carpeta. Mover un doc de un portal-owner a la raíz también revienta.

**DOG46. Borrar un documento de tipo carpeta usado por una app falla con ValidationError** — `_unlink_except_company_folders` → `_raise_if_used_folder` (`documents/models/documents_document.py:2291-2299`, `Document._check_access`) consulta `res.company._get_used_folder_ids_domain` (cada bridge lo extiende; base devuelve `FALSE_DOMAIN`, `documents/models/res_company.py:23`, `Company._get_used_folder_ids_domain`). Impact: no puedes borrar la carpeta-workspace de un bridge (HR/Account/Project) mientras una compañía la referencie; primero hay que desasignarla en Ajustes. El error genérico ("Impossible to delete folders used by other applications") no dice qué app.

**DOG47. Archivar/borrar un doc que NO posees exige `edit` en la CARPETA, no en el doc** — `_raise_if_unauthorized_archive` (`documents/models/documents_document.py:2302-2306`, `Document._check_access`): si el doc está activo y `owner_id != user`, comprueba `folder.user_permission == 'edit'`. Impact: tener `edit` por enlace/membresía sobre el documento NO basta para mandarlo a la papelera si no eres dueño; necesitas editar la carpeta contenedora. Asimetría sorprendente entre "editar contenido" y "archivar".

**DOG48. `documents.access` es INMUTABLE en `partner_id`/`document_id` — y se auto-purga al expirar** — `write` lanza `AccessError` si tocas `partner_id` o `document_id` (`documents/models/documents_access.py:33-35`, `DocumentAccess.write`); para "mover" un acceso hay que borrar y recrear. Además `@api.autovacuum _gc_expired` (`:40-42`) borra hasta 1000 accesos con `expiration_date <= now` por pasada. Impact: (1) cambiar el partner de un acceso no es posible por código; (2) los accesos caducados desaparecen físicamente en el siguiente autovacuum, así que no quedan como registro histórico de "tuvo acceso hasta X" — si necesitas auditoría usa la fila con `role=NULL` + `last_access_date` (DOG4), que el `_gc_expired` no toca (no tiene expiration).

**DOG49. La invitación con alta de usuario solo funciona con política global "Free sign up" (b2c)** — `_is_signup_available` (`documents/models/documents_access.py:48-54`, `DocumentAccess._is_signup_available`) exige `_get_signup_invitation_scope() == 'b2c'`, que haya `role`, que no esté caducado y que el partner NO tenga ya usuario. Impact: en instancias B2B-only o "On invitation", compartir-e-invitar a un externo no genera link de signup (silenciosamente vacío vía `_get_signup_url` → `''`, `:92-99`); el admin cambia la política global sin darse cuenta del efecto colateral en toda la instancia.

**DOG50. Los shortcuts a un destino inaccesible se AUTO-BORRAN (no solo se marcan)** — `_unlink_shortcut_if_target_inaccessible` (`documents/models/documents_document.py:2307-2312`, `Document._unlink_except_unauthorized`) evalúa el shortcut con el usuario del dueño y, si `shortcut_document_id.user_permission == 'none'`, lo `unlink()` en sudo. Se dispara al cambiar owner (`:2080-2081`) y al re-companyear. Impact: revocar el acceso del dueño de un shortcut a la fuente NO deja un shortcut "roto" visible — desaparece.
