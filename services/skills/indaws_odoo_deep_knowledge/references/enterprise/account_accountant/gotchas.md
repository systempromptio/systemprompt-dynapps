# Account Accountant Gotchas — Odoo 18.0 Enterprise

Gotchas specific to the Enterprise accounting module (`account_accountant`). For base account gotchas, see `functional/account/gotchas.md`.

Source root: `odoo_enterprise/18/account_accountant/`. Anchors point to `file.py → method/field` (line numbers are v18.0 hints and drift across patches). Some gotchas below reference sibling EE modules (`account_followup`, `account_batch_payment`) — flagged inline.

## Bank Reconciliation Widget

**AAG1. bank.rec.widget and bank.rec.widget.line are NEVER persisted to DB** — Both models have `_auto = False` and `_table_query = "0"` (`account_accountant/models/bank_rec_widget.py:20-21`, `class BankRecWidget`, `bank_rec_widget_line.py`). They exist only as transient in-memory records (created via `new({})`). Impact: you cannot query them with SQL, cannot create CRON jobs that read their state, and any custom code using `search()` or `browse()` on these models will fail silently with empty results. All interaction must go through the widget's JS<->Python bridge via `todo_command` → `bank_rec_widget.py → _onchange_todo_command` (`:309`), which dispatches to `_js_action_<name>` methods. _ES: no encuentro las líneas del widget de conciliación bancaria por SQL ni desde un cron, las búsquedas salen vacías._

**AAG2. Widget state 'invalid' means suspense account is still present** — `bank_rec_widget.py → _compute_state` (`:198`) sets `'invalid'` when there is no `st_line_id`, OR when `journal.suspense_account_id` appears in `line_ids.account_id` (`:205-206`); `'reconciled'` if the line is already reconciled; else `'valid'`. Impact: any custom write-off line that accidentally uses the suspense account will block validation with no clear error message — the button simply stays disabled. _ES: el botón de validar la conciliación bancaria está gris y no puedo confirmar, sin mensaje de error._

**AAG3. Auto-balance line uses partner ranks to choose receivable vs payable** — `bank_rec_widget.py → _lines_prepare_auto_balance_line` (`:424`) sets `partner_is_customer = customer_rank and not supplier_rank` and `partner_is_supplier = supplier_rank and not customer_rank` (`:453-454`). If BOTH ranks are nonzero (common for a partner who is both customer and supplier), neither branch matches and it falls through to the statement-line amount sign: `st_line.amount > 0` → receivable, else payable (`:459-462`). Impact: a customer who also has supplier_rank > 0 may get the payable account on a negative bank transaction, sending the balance to AP instead of AR. _ES: un cliente que también es proveedor aparece en la cuenta de proveedores al conciliar un cobro negativo._

**AAG4. Editing the liquidity line directly modifies the bank statement line** — Each editable field on the liquidity line writes straight through to `st_line_id` (and its `move_id`) via the `_line_value_changed_<field>` handlers in `bank_rec_widget.py`: `name` → `st_line_id.payment_ref` (`:992-995`), `date` → `st_line_id.date` (`:971-974`), `ref` → `st_line_id.move_id.ref` (`:978-981`), `narration` → `st_line_id.move_id.narration` (`:985-988`), `amount_currency` → `st_line_id.amount` (`:1017-1020`), `amount_transaction_currency` → `st_line_id.amount_currency` + `foreign_currency_id` (`:1002-1010`). Impact: these are side-effects that survive even if the user never validates — the statement line data is already modified. There is no undo. _ES: al editar la línea del banco en el widget se cambia el apunte bancario aunque no valide, y no hay deshacer._

**AAG5. Auto-reconcile CRON only processes lines from the last 3 months** — `account_bank_statement.py → _cron_try_auto_reconcile_statement_lines` (`:90`) filters with `('create_date', '>', start_time.date() - relativedelta(months=3))` (`:105`). Impact: imported bank transactions older than 3 months are NEVER auto-reconciled by the CRON. They must be reconciled manually or via a custom script. _ES: las transacciones bancarias de hace más de tres meses no se concilian solas nunca._

**AAG6. Auto-reconcile CRON silently swallows UserError exceptions** — In `account_bank_statement.py → _cron_try_auto_reconcile_statement_lines`, when `wizard._action_validate()` raises a `UserError` it is caught and logged at INFO level then `continue` (`:154-159`), and `cron_last_check` is still written on all processed lines (`:161`). Impact: lines that fail validation (e.g., missing FX accounts, lock date violations) are silently skipped. Grep the logs for "Failed to auto reconcile statement line". _ES: algunas líneas del extracto se saltan en la conciliación automática sin avisar y quedan sin conciliar._

**AAG7. Auto-reconcile CRON has a 180-second hard time limit** — `account_reconcile_model.py → run_auto_reconciliation` (`account_accountant/models/account_reconcile_model.py:554-562`, `AccountReconcileModel.run_auto_reconciliation`) computes `limit_time = cron_limit_time if 0 < cron_limit_time < 180 else 180` (`account_accountant/models/account_reconcile_model.py:561`, `AccountReconcileModel.run_auto_reconciliation`), where `cron_limit_time = config['limit_time_real_cron'] or -1`, then calls the CRON with that `limit_time`. The CRON loop itself breaks once elapsed time exceeds `limit_time` (`account_accountant/models/account_bank_statement.py:138-139`, `AccountBankStatementLine._cron_try_auto_reconcile_statement_lines`). The scheduled action passes `batch_size=100` (`account_accountant/data/ir_cron.xml:7`, `auto_reconcile_bank_statement_line`). Impact: importing 10,000 bank lines and expecting immediate auto-matching will not work; plan for gradual processing across CRON cycles. _ES: importé miles de líneas de banco y la conciliación automática no las procesa todas de golpe._

**AAG8. Reconciliation model first-match-wins, NOT best-match** — `account_reconcile_model.py → _apply_rules` (`:45`) iterates `self.filtered(...).sorted()` (by `sequence`) and `return`s on the FIRST model that produces a result (`:60-94`). Impact: if model A (sequence=10) matches partially and model B (sequence=20) would match perfectly, model A wins. Order your reconciliation models carefully — most specific first. _ES: se aplica una regla de conciliación peor cuando había otra que casaba mejor, por el orden de las reglas._

**AAG9. Token matching requires minimum 4 characters** — `account_reconcile_model.py → _get_invoice_matching_st_line_tokens` (`:166`) hard-codes `significant_token_size = 4` (`:176`) and drops tokens shorter than that (`:186`, `:197`, `:205`). Impact: short invoice number prefixes like "FV"/"NC" are excluded from numerical and text matching, so an invoice number where the meaningful part is under 4 chars may fail to match. _ES: las facturas con número corto o prefijos de pocas letras no casan en la conciliación automática._

**AAG10. EPD (early payment discount) in bank reconciliation requires SAME currency AND amounts that apply** — `bank_rec_widget.py → _lines_check_apply_early_payment_discount` (`:571`) only applies if `is_same_currency` (all `new_aml` currencies == `transaction_currency_id`, `:586`) AND at least one AML is eligible AND `_do_amounts_apply_for_early_payment(open_amount_currency, total_early_payment_discount)` returns True (`:612-614`). Impact: multi-currency invoices with early payment discounts never get automatic EPD treatment in bank reconciliation. _ES: el descuento por pronto pago no se aplica solo al conciliar facturas en otra divisa._

## Bank Statements

**AAG11. Partner detection cascades through 4 strategies before giving up** — `account_bank_statement.py → _retrieve_partner` (`:169`) tries in order: (1) existing `partner_id` (`:173`), (2) bank account lookup via `sanitized_acc_number ilike` (`:177-190`), (3) partner name match on `complete_name` (`=ilike` then `ilike`, with `company_id parent_of` / shared, `parent_id = False`) (`:193-210`), (4) reconcile-model partner mappings via `_get_partner_from_mapping` gated by `_is_applicable_for` (`:212-219`); else empty recordset (`:221`). Impact: if two partners share the same bank account, or `partner_name` matches multiple partners, no partner is set. The bank account lookup considers archived partners and only filters them out (`partner_id.active`) when several matches remain (`:186-190`). _ES: al importar el extracto no me asigna el cliente aunque coincide, o me pone uno equivocado._

**AAG12. Partner bank account lookup uses ilike on sanitized number** — In `account_bank_statement.py → _retrieve_partner` the search uses `('sanitized_acc_number', 'ilike', account_number_nums)` (`:180`) — a substring match, not exact. Impact: bank account "1234567890" also matches "1234567890123" (a longer IBAN containing the shorter number), which can cause incorrect partner assignment on imported bank statements. _ES: me asigna un cliente equivocado en el extracto porque el número de cuenta coincide parcialmente._

## Deferred Entries (Accruals)

**AAG13. Deferred entries use 30-day months, not actual calendar days** — `account_move.py → _get_deferred_diff_dates` (`:160`) normalizes every month to 30 days (`start_day = 30` / `end_day = 30` for end-of-month, returns `(nb_months * 30 + nb_days) / 30`, `:172-176`). February (28-29 days) and March (31 days) yield the same deferred amount under the 'month' method. Impact: for day-precise accruals use the 'day' method; 'month' is a deliberate simplification that distorts short periods. _ES: los importes diferidos por meses no cuadran con los días reales de febrero o marzo._

**AAG14. Single-month deferrals are silently skipped** — `account_move.py → _generate_deferred_entries` (`:258`) skips a line when `start_date.replace(day=1) == end_date.replace(day=1) == accounting_date.replace(day=1)` (`:297`). Impact: an invoice dated Jan 15 with deferred dates Jan 1–Jan 31 generates zero deferred entries (reversal and deferral would cancel out) — intentional, but confuses users expecting entries. _ES: una factura con diferimiento dentro de un solo mes no genera ningún asiento de diferimiento._

**AAG15. Resetting deferred invoice to draft reverses (not deletes) deferred entries** — `account_move.py → button_draft` (`:124`) calls `self.deferred_move_ids._unlink_or_reverse()` (`:127`); when audit-trail protected, that REVERSES rather than unlinks, and the reversal moves are re-dated and merged back into `deferred_move_ids` (`:128-133`). Impact: reset-to-draft of a deferred invoice can leave extra reversal journal entries in the system, muddying deferred expense/revenue reports. _ES: al pasar a borrador una factura diferida aparecen asientos de reversión extra que ensucian el informe._

**AAG16. Grouped deferral entries block reset to draft** — `account_move.py → button_draft` raises UserError when any deferral move has `len(deferred_original_move_ids) > 1` (`:125-126`). Impact: with the 'Manually & Grouped' generation method, you cannot reset an individual invoice to draft once the grouped deferral exists — only a credit note. _ES: no puedo pasar a borrador una factura con diferimiento agrupado, me obliga a hacer un abono._

**AAG17. Changing account on a line with existing deferrals is blocked** — `account_move.py → AccountMoveLine.write` (`:492`) raises UserError when `account_id` changes on a line that has `has_deferred_moves` AND both `deferred_start_date` AND `deferred_end_date` set AND the new account differs (`:495-506`). Impact: to change the expense/revenue account after deferrals are generated you must first reset to draft (reversing deferrals), change the account, then re-post. _ES: no me deja cambiar la cuenta de gasto o ingreso en una línea que ya tiene diferimientos generados._

**AAG18. Deferred end date is INCLUSIVE — off-by-one trap** — Both `deferred_start_date` and `deferred_end_date` are inclusive. Jan 1–Dec 31 is exactly 12 months, but Jan 1–Jan 1 next year is 12 + 1/30 months (≈12.033), producing odd amounts. `account_move.py → _compute_has_abnormal_deferred_dates` (`:515`) flags this (the diff being off by `1/30`, `:519-528`) into the `has_abnormal_deferred_dates` field but does not prevent it. Impact: use the last day of the service period, never the first day of the next. _ES: salen importes raros en el diferimiento porque puse como fecha fin el primer día del periodo siguiente._

## Fiscal Operations & Lock Dates

**AAG19. Lock date exceptions have time-limited duration** — `account_change_lock_date.py → exception_duration` (`:143`) offers `5min`/`15min`/`1h`/`24h`/`forever` (`:146-150`), mapped to `timedelta`s (`forever` → False) (`:286-291`). When `exception_applies_to == 'everyone'` AND `exception_duration == 'forever'`, the wizard treats it as a normal lock-date change rather than an exception (`:264-265`). Impact: a developer lowering a lock date "for 5 minutes" may find the exception expired before finishing. _ES: la excepción de fecha de bloqueo que puse caduca sola antes de que termine mi trabajo._

**AAG20. Setting lock dates does NOT auto-post draft entries** — `account_change_lock_date.py → _compute_show_draft_entries_warning` (`:204`) sets the `show_draft_entries_warning` boolean (`:159`) when draft moves exist in the locked period, but this is only a warning — it does NOT block the lock. Future lock dates are rejected (`:246`) and `hard_lock_date` cannot be decreased (`:235`). Impact: draft entries in the locked period get stuck — cannot be posted (date locked) and cannot be deleted under audit trail. Post or delete them BEFORE locking. _ES: tengo asientos en borrador en un periodo bloqueado que no puedo ni contabilizar ni borrar._

**AAG21. Fiscal year records on child companies are forbidden** — `account_fiscal_year.py → _check_dates` (`:23`) raises ValidationError if `fy.company_id.parent_id` is set (`:43-44`), and also forbids end-before-start (`:42`) and overlaps (`:56`). Impact: in multi-company setups fiscal years must be defined on the ROOT company only; children inherit the parent's configuration. _ES: no me deja crear el ejercicio fiscal en una compañía hija, da error de validación._

## Invoicing Switch Threshold

**AAG22. Invoicing switch threshold uses raw SQL to mass-cancel moves** — `res_company.py → write` (`:75`) detects a changed `invoicing_switch_threshold` (`:83`) and runs direct SQL UPDATEs on `account_move`/`account_move_line` (`:91-117`), bypassing ORM constraints, computed fields, and audit trail: posted moves dated before the threshold get `state='cancel'` + `payment_state='invoicing_legacy'`, with the prior state stashed in `payment_state_before_switch`; lowering the threshold reverses the legacy moves back to `posted`. Impact: essentially irreversible bulk data modification with all ORM-level validation bypassed — use with extreme caution. _ES: al cambiar el umbral de facturación se cancelaron en masa asientos contabilizados de forma casi irreversible._

## Reconciliation Wizard (Manual)

**AAG23. Manual reconciliation wizard allows max 2 different accounts** — `account_reconcile_wizard.py → default_get` (`:17`) raises UserError when selected AMLs span more than 2 accounts (`:25-29`); with exactly 2 accounts it sets up an automatic transfer entry (`:31-34`). Impact: you cannot reconcile AMLs from 3+ accounts in one operation — split into multiple steps. _ES: no puedo conciliar manualmente apuntes de tres cuentas distintas a la vez._

**AAG24. Auto-reconcile wizard 'one_to_one' matches by absolute rounded amount** — `account_auto_reconcile_wizard.py → _auto_reconcile_one_to_one` (`:111`) groups AMLs by `['account_id', 'partner_id', 'currency_id', 'amount_residual_currency:abs_rounded']` (`:118`) and pairs first positive with first negative (`:124+`). Impact: with two invoices of 100 EUR and one payment of -100 EUR, only ONE invoice reconciles; the second stays unmatched even though the -100 could also match it. _ES: con dos facturas iguales y un solo cobro solo se concilia una y la otra queda pendiente._

**AAG25. Auto-reconcile 'zero_balance' requires EXACT zero sum per group** — `account_auto_reconcile_wizard.py → _auto_reconcile_zero_balance` (`:134`) uses `having=[('amount_residual_currency:sum_rounded', '=', 0)]` (`:143`). Groups that sum to 0.01 from rounding are NOT reconciled. Impact: multi-line reconciliation with rounding differences needs manual intervention or a rounding adjustment first. _ES: la conciliación automática no salda grupos que quedan descuadrados un céntimo por redondeo._

## Follow-ups

**AAG26. Follow-up status search queries ALL partners** — (module `account_followup`, not `account_accountant`.) `account_followup/models/res_partner.py → _search_status` (`:79`) calls `_query_followup_data(all_partners=True)` (`:89`), loading follow-up data for every partner before filtering in Python (`:91-95`); the sibling `_search_followup_line` does the same (`:106`). Impact: on databases with 100K+ partners, searching by follow-up status is extremely slow — the search field is computed, with no DB index to lean on. _ES: buscar clientes por estado de seguimiento va lentísimo en bases de datos con muchos partners._

**AAG27. Follow-up 'total_due' only considers receivable accounts, not payable** — (module `account_followup`.) `account_followup/models/res_partner.py → _compute_total_due` (`:170`): `total_due`/`total_overdue` (`:41-45`) include only `asset_receivable` accounts (`:130`, `:181`), whereas `total_all_due`/`total_all_overdue` (`:35-39`) include receivable AND payable (see field comment `:32-33`). Impact: the default follow-up view shows `total_due`, which ignores vendor credits that could offset the customer debt. _ES: el total adeudado del seguimiento solo cuenta lo de clientes e ignora los abonos de proveedor que compensarían._

## Batch Payments

**AAG28. Batch payment state is computed from individual payment states** — (module `account_batch_payment`, not `account_accountant`.) `account_batch_payment/models/account_batch_payment.py → _compute_state` (`:118`): `reconciled` only if every non-canceled/rejected payment is `is_matched AND is_sent` (`:121`); `sent` if all are merely `is_sent` (`:123`); else `draft`. Impact: a single unmatched payment keeps the whole batch in 'draft'/'sent'; the batch never reaches 'reconciled' until ALL active payments are matched — sometimes you must remove a problematic payment to advance. _ES: el pago por lotes se queda en borrador o enviado y nunca llega a conciliado por un solo pago sin casar._

**AAG29. Batch payment only accepts payments in specific states** — (module `account_batch_payment`.) `account_batch_payment/models/account_batch_payment.py → _valid_payment_states` (`:84`) returns `['in_process', 'paid']` when `account.move._get_invoice_in_payment_state() == 'paid'`, else `['in_process']` (`:85`). Impact: a payment not yet `in_process` cannot be added to a batch — it must first transition (via reconciliation) into one of these states. _ES: no puedo añadir un pago al lote porque todavía no está en proceso._

## Performance

**AAG30. bank.rec.widget creates a new widget instance per statement line** — In `account_bank_statement.py → _cron_try_auto_reconcile_statement_lines`, each line builds a fresh `self.env['bank.rec.widget'].with_context(default_st_line_id=...).new({})` then calls `_action_trigger_matching_rules()` (`:143-144`), which re-runs the compute chain (`_compute_line_ids`, `_compute_available_reco_model_ids`, etc.) per line. Impact: with 10,000 unreconciled lines and several reconcile models doing SQL token matching, the CRON is extremely slow; the 180s limit (AAG7) bounds each run but does not solve throughput. _ES: la conciliación automática por cron va muy lenta con muchas líneas de extracto sin conciliar._

**AAG31. Invoice matching uses REGEXP_SPLIT_TO_ARRAY + UNNEST in SQL** — `account_reconcile_model.py → _get_invoice_matching_amls_candidates` (`:212`) builds a CTE that `UNNEST(REGEXP_SPLIT_TO_ARRAY(...))` over AML names, move names and refs (`:263-264`), then joins against the statement-line tokens. Impact: on large databases (500K+ AMLs) the query is expensive — it materializes matching AMLs before token filtering, and no partial index helps. _ES: el emparejamiento de facturas al conciliar es muy lento en bases de datos grandes._

**AAG32. Predictive bill fields rank a full-text search over the last 100 posted entries** — `account_move.py → _build_predictive_query` (`:656`) caps the candidate query at `int(ir.config_parameter('account.bill.predict.history.limit', '100'))` entries (`:664-666`); `_predicted_field` (`:709`) then ranks with `ts_rank`/`to_tsquery`, takes `LIMIT 2` (`:735`), and accepts the top prediction only if it scores ≥10% better than the runner-up (`result[0]['ranking'] < 1.1 * result[1]['ranking']` → reject, `:745`); any tsquery parse error returns False silently (`:748-752`). Impact: with diverse bill descriptions predictions often return False; tune the 100-entry limit via the `account.bill.predict.history.limit` system parameter. _ES: la predicción de cuenta y datos en facturas de proveedor no acierta y sale vacía cuando las descripciones son variadas._

## Multi-Company

**AAG33. Deferred journal and account are per-company, not shared** — `res_company.py`: `deferred_expense_journal_id` (`:18`), `deferred_expense_account_id` (`:22`), `deferred_revenue_journal_id` (`:47`), `deferred_revenue_account_id` (`:51`) are plain Many2one fields on `res.company` — one value per company record. Impact: each company in a multi-company setup must configure its own deferred accounts/journals; missing config surfaces as a UserError only at invoice posting, not at setup. _ES: cada compañía tiene que configurar sus propios diarios y cuentas de diferimiento, y falta salta al contabilizar._

**AAG34. Reconcile model company filtering uses exact match, not parent_of** — Both `bank_rec_widget.py → _action_trigger_matching_rules` (`:1191-1193`) and `_compute_available_reco_model_ids` (`:170-175`) filter reconcile models with `('company_id', '=', self.company_id.id)`. Impact: reconcile models defined on a parent company are NOT inherited by child companies — each child needs its own set. This differs from COA/fiscal positions which use `parent_of` logic. (Contrast: `_retrieve_partner` uses `_check_company_domain`, AAG11.) _ES: las reglas de conciliación de la compañía matriz no se heredan en las compañías hijas._

## Reset / Secure Entries

**AAG35. You cannot reset a reconciliation on a hashed (secured) bank transaction** — `bank_rec_widget.py → _js_action_reset` (`:1513`) checks `st_line.inalterable_hash` (`:1518`): if set and the line has no reconciled entries it raises a hard UserError (`:1520`); if it has reconciled entries it raises a `RedirectWarning` steering the user to "unreconcile" instead (`:1522-1526`). Only when not hashed does it call `action_undo_reconciliation()` (`:1528`). Impact: once a bank transaction is secured (inalterable hash via the secure-entries flow), the widget's Reset button is dead — you must go through unreconciliation, never reset. _ES: el botón de reiniciar conciliación no funciona en una transacción bancaria ya asegurada o firmada._

**AAG36. Deferred dates survive reversal ONLY under the `move_reverse_cancel` context** — `account_move.py → copy_data` (`:484`) copies `deferred_start_date`/`deferred_end_date` onto the new lines only when `'move_reverse_cancel' in self._context` (`:487-489`); a plain duplicate of a deferred invoice drops the deferred dates. Impact: custom code that copies a deferred move outside the reversal flow loses the deferral configuration silently — set the `move_reverse_cancel` context key if you need it preserved. _ES: al duplicar una factura diferida se pierden las fechas de diferimiento salvo en la reversión._

**AAG37. bank.rec.widget(.line) are hidden from model selectors** — `ir_model.py → _is_valid_for_model_selector` (`:8`) excludes `bank.rec.widget` and `bank.rec.widget.line` (`:10-14`) because they have no psql table (`_auto=False` + `_table_query="0"`, see AAG1). Impact: these models never appear in server-action / automation / `ir.model` selectors, so you cannot target them with standard Studio automations or generic model-driven tooling — extend them in Python only. _ES: los modelos del widget de conciliación no aparecen para crear automatizaciones ni acciones de servidor de Studio._
