# account_3way_match Gotchas — Odoo 18.0 Enterprise

Source: `odoo_enterprise/18/account_3way_match/`. Every entry verified against source with `path:line`. v19-specific gotchas (A3M14, A3M15) are kept here but their detail lives in [[v19_changes]].

**A3M1. Default value 'exception' on install** — `account.move._auto_init` ALTER TABLE sets DEFAULT 'exception' (`account_3way_match/models/account_invoice.py:14-18`, `AccountMove._auto_init`); `account.move.line._auto_init` does the same for `can_be_paid` (`account_3way_match/models/account_invoice.py:94-98`, `AccountMoveLine._auto_init`). Until proper compute runs, ALL bills/lines appear blocked. Impact: post-install dashboard shows everything in exception until a save/recompute fires. _ES: Nada más instalar, todas las facturas de proveedor aparecen bloqueadas o en excepción hasta que se guarda o recalcula algo._

**A3M2. Lines without purchase_line_id → exception** — `else: invoice_line.can_be_paid = 'exception'` (`account_3way_match/models/account_invoice.py:134-135`, `AccountMoveLine._can_be_paid`). A manual vendor bill (no PO) → every line exception → bill exception. Impact: every PO-less bill BLOCKED from auto-pay; user must set `force_release_to_pay=True`. _ES: Las facturas de proveedor sin pedido de compra salen siempre bloqueadas y no se pueden pagar automáticamente._

**A3M3. Currency conversion uses TODAY's rate** — `_convert(..., fields.Date.today())` (`account_3way_match/models/account_invoice.py:123-124`, `AccountMoveLine._can_be_paid`). PO booked at one FX rate, bill compared at today's rate → price mismatch even when prices match in their own currencies. Impact: FX-volatile vendors generate constant exceptions. Confirmed by tests: any price change → exception (`account_3way_match/tests/test_release_to_pay_invoice.py:88-90`, `TestReleaseToPayInvoice.test_3_way_match`). _ES: Proveedores en otra divisa generan excepciones constantes por diferencia de precio aunque el importe coincida en su moneda._

**A3M4. force_release_to_pay auto-set on onchange only** — `_onchange_release_to_pay_manual` sets `force_release_to_pay=True` only when manual differs from computed (`account_3way_match/models/account_invoice.py:85-88`, `class AccountMove`). Impact: this is an ONCHANGE — setting `release_to_pay_manual` via ORM/`write` does NOT trigger it; you must set `force_release_to_pay=True` explicitly too, otherwise `_compute_release_to_pay_manual` (`:79-83`) overwrites your value back to the computed one. _ES: Fuerzo el pago por código o importación y no se respeta: el sistema me lo vuelve a poner en el valor calculado._

**A3M5. `release_to_pay='no'` for paid bills (overloaded value)** — `if payment_state == 'paid' ... : release_to_pay = 'no'` (`account_3way_match/models/account_invoice.py:52-54`, `AccountMove._compute_release_to_pay`). Impact: after payment the "to pay" counter drops correctly, but 'no' is overloaded — it means "already paid" OR "nothing received". Don't read 'no' as a single business state. _ES: Una factura ya pagada aparece como 'no pagar' igual que una sin recepción; no distingo ambos casos._

**A3M6. Only invoice_line_ids checked, section/note skipped** — `lambda l: l.display_type not in ('line_section', 'line_note')` (`account_3way_match/models/account_invoice.py:61`, `AccountMove._compute_release_to_pay`). A bill of only section/note lines → `result=None` → `release_to_pay='no'` (`:77`). Impact: a structurally non-empty but product-empty bill reads as 'no'. Counterintuitive but harmless. Tested at `account_3way_match/tests/test_release_to_pay_invoice.py:60-63`, `TestReleaseToPayInvoice.check_release_to_pay_scenario`. _ES: Una factura solo con secciones o notas, sin líneas de producto, sale como 'nada por pagar'._

**A3M7. Non-invoice / out-invoice moves silently 'no'** — `not invoice.is_invoice(include_receipts=True)` → `'no'` (`account_3way_match/models/account_invoice.py:52-54`, `AccountMove._compute_release_to_pay`); on install only `move_type in ('in_invoice','in_refund')` is computed properly (`:49`). Impact: customer invoices and journal entries always carry `release_to_pay='no'`; the field is meaningless outside vendor bills/refunds. _ES: El indicador de autorizar pago aparece en facturas de cliente o asientos donde no tiene sentido._

**A3M8. Mixed line statuses → exception (NOT logical OR)** — `elif line_status != result: result = 'exception'` (`account_3way_match/models/account_invoice.py:69-71`, `AccountMove._compute_release_to_pay`). One `yes` + one `no` → `exception`, not "any yes = yes". Impact: with multiple PO lines, ALL must share status (or be `yes`) for the bill to flow auto. Tested at `account_3way_match/tests/test_release_to_pay_invoice.py:79`, `TestReleaseToPayInvoice.test_3_way_match`. _ES: Con varias líneas de pedido, si una está aprobada y otra no, la factura entera pasa a excepción en vez de aprobarse._

**A3M9. Decimal precision dependency** — `precision_get('Product Unit of Measure')` (`account_3way_match/models/account_invoice.py:112`, `AccountMoveLine._can_be_paid`), used in every `float_compare` (`:147,149,164,166`). If a custom module narrows this precision, tight qty diffs (kg/lbs at 0.001) can flap yes↔exception. v19 renames the precision key (see [[v19_changes]]). Impact: rounding-sensitive comparisons. _ES: Comparaciones de cantidad con muchos decimales (kg, gramos) fluctúan entre aprobado y excepción sin motivo aparente._

**A3M10. on-ordered formula subtracts current line qty** — `float_compare(invoiced_qty - self.quantity, ordered_qty, ...)` (`account_3way_match/models/account_invoice.py:147`, `AccountMoveLine._can_be_paid_ordered_qty`). `self.quantity` is the CURRENT (unbilled hypothetical) line qty subtracted from the PO's total `qty_invoiced`. Impact: the formula is unreadable without knowing `self.quantity` is the reduction term; not obvious from the method signature. _ES: La fórmula que compara cantidades pedidas contra facturadas da resultados que no cuadran al añadir la línea actual._

**A3M11. on-received: received=0 path** — `elif received_qty == 0 and float_compare(invoiced_qty, ordered_qty, ...) <= 0: 'no'` (`account_3way_match/models/account_invoice.py:166-167`, `AccountMoveLine._can_be_paid_received_qty`). Nothing received yet but within order → 'no' (legitimately not payable yet). If billed > ordered with nothing received → falls through to `exception` (`:168-169`). Impact: a draft bill with no receipt shows 'no' until goods arrive. _ES: Una factura sin mercancía recibida todavía se queda en 'no pagar' hasta que llega el material._

**A3M12. release_to_pay store=True, recomputes on every payment state change** — `store=True` (`account_3way_match/models/account_invoice.py:24`, `class AccountMove`) + `@api.depends(..., 'payment_state')` (`:44`). Impact: every payment_state transition recomputes the bill; bulk-pay flows trigger many recomputes. The line-level `can_be_paid` also depends on `purchase_line_id.qty_received/qty_invoiced/product_qty` (`:103`), so receipts/other bills on the same PO recompute too. _ES: Cada cambio de estado de pago o recepción sobre el mismo pedido dispara recálculos masivos y lentitud en pagos por lotes._

**A3M13. Dashboard query override is purchase-aware** — `_get_open_sale_purchase_query` adds `release_to_pay IN ('yes','exception') AS to_pay` (`account_3way_match/models/account_journal_dashboard.py:39`, `AccountJournal._get_open_sale_purchase_query`); `_get_draft_sales_purchases_query` gates purchase drafts on `invoice_date_due < today OR release_to_pay='yes'` (`:54-57`). Impact: when extending the dashboard, purchase journals carry an extra `to_pay` column sale journals don't. In v19 this method was split/renamed — see [[v19_changes]]. _ES: En el tablero de diarios, los diarios de compra muestran una columna 'por pagar' extra que los de venta no tienen._

**A3M14. v19 `line_subsection` skipped in compute** — v19 adds `'line_subsection'` to the exclusion filter (`account_3way_match/account_invoice.py:62`, `AccountMove._compute_release_to_pay`). v18 only excludes section/note (`account_3way_match/models/account_invoice.py:61`, `AccountMove._compute_release_to_pay`). Impact: in v19 subsection lines never affect `release_to_pay`; backporting/forward-porting custom filters must match. Detail in [[v19_changes]]. _ES: En v19 las subsecciones de la factura ya no afectan a la autorización de pago; filtros personalizados dejan de cuadrar entre versiones._

**A3M15. v19 `'Product Unit'` decimal-precision rename** — v18 uses `precision_get('Product Unit of Measure')` (`account_3way_match/models/account_invoice.py:112`, `AccountMoveLine._can_be_paid`); v19 uses `precision_get('Product Unit')` (`odoo_enterprise/19/account_3way_match/models/account_invoice.py:113`, `AccountMoveLine._can_be_paid`). Impact: custom code calling the old key in v19 gets the fallback precision (effectively no precision configured), silently changing rounding in the qty comparisons. Detail in [[v19_changes]]. _ES: En v19 el redondeo de las comparaciones de cantidad cambia sin avisar por el renombrado de la precisión decimal de unidades._

**A3M16. Module NOT auto_install** — `__manifest__.py` has no `auto_install` key (`account_3way_match/__manifest__.py:1-34`); only `depends: ['purchase']` (`:28`). Impact: customers must install it explicitly. Databases that never installed it have no `release_to_pay` / `can_be_paid` columns, so code referencing those fields fails — guard with the module presence check. _ES: El campo autorizar pago no existe en la base y el código falla porque el módulo de conciliación a tres vías no está instalado._
