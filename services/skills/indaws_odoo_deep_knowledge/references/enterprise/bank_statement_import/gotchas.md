<!-- verified: v18.0 @ 2026-06 -->
# Bank Statement Import — Gotchas (BSIG)

Hidden/verified behaviors. Prefix **BSIG**. Paths are v18 EE unless noted.

---

### BSIG1 — `unique_import_id` is silently namespaced; re-importing into a different journal duplicates lines _ES: Importé el mismo extracto en dos diarios distintos y ahora las transacciones aparecen duplicadas._
The raw bank id is rewritten to `{sanitized_acct}-{journal_id}-{raw_id}` in `_complete_bank_statement_vals` (`account_bank_statement_import/models/account_journal.py:226`, `AccountJournal._find_additional_data`). The UNIQUE constraint (`account_bank_statement_import/models/account_bank_statement.py:17-19`, `AccountBankStatementLine._sql_constraints`) therefore dedups **per journal+account**, not globally. Importing the SAME file into journal A then journal B creates the transactions twice (different namespaced ids). Symptom: "duplicate transactions after I imported the file in the wrong journal first".

### BSIG2 — "You already have imported that file" can fire even on a partly-new file _ES: Al importar el extracto dice que ya lo había importado aunque contiene movimientos nuevos que esperaba ver._
`_create_bank_statements` raises UserError if `len(statement_line_ids) == 0` (`account_bank_statement_import/models/account_journal.py:286-287`, `AccountJournal._create_bank_statements`). If every line matches an existing `unique_import_id` (e.g. overlapping date ranges across two exports) the whole file is rejected with no statement created — even though you expected the new lines. There ARE no new lines because the overlap covered them; the "new" ones had amount 0 or were dups.

### BSIG3 — Lines with `amount == 0` are dropped, not imported _ES: Faltan filas de mi CSV o CAMT en Odoo; los movimientos con importe cero no se importan._
Same filter (`account_bank_statement_import/models/account_journal.py:261`, `AccountJournal._complete_bank_statement_vals`). Zero-amount informational entries (e.g. balance markers, FX legs that net to zero) never become statement lines. Symptom: "some rows from my CSV/CAMT are missing in Odoo".

### BSIG4 — Skipped (already-imported) lines mutate `balance_start` _ES: El saldo inicial del extracto importado no coincide con el del fichero al reimportar un rango de fechas solapado._
When a line is filtered as duplicate, if `balance_start` is set it is increased by that line's amount (`account_bank_statement_import/models/account_journal.py:268-269`, `AccountJournal._create_bank_statements`). This is intentional (keeps opening balance consistent with the surviving lines) but means the imported statement's `balance_start` will NOT equal the value in the file when re-importing an overlapping range.

### BSIG5 — CAMT multi-IBAN file silently drops the other accounts _ES: Solo se importó una parte de mi fichero CAMT que tenía varias cuentas IBAN._
A CAMT.053 covering several IBANs only imports the `Stmt` blocks matching the current journal's IBAN; the rest are logged as a `_logger.warning` and discarded (`account_bank_statement_import_camt/models/account_journal.py:160-166`, `AccountJournal._parse_bank_statement_file_camt`). If the journal has NO IBAN set → hard UserError. Symptom: "half my CAMT didn't import" — must import once per journal/IBAN.

### BSIG6 — CAMT requires journal currency to match the statement currency or the whole Stmt is skipped _ES: El CAMT en otra divisa no se importa y avisa de que no encuentra extractos en esa moneda._
`if currency and journal_currency and currency != journal_currency.name: continue` (`account_bank_statement_import_camt/account_journal.py:67-68`, `AccountJournal._parse_bank_statement_file_camt`). A multi-currency CAMT silently skips statements whose `Acct/Ccy` differs from the journal, then errors "No statements in currency X were found" if nothing matched (`:172-174`).

### BSIG7 — CSV rows MUST be date-sorted or the import hard-fails _ES: La importación del CSV falla diciendo que las filas deben estar ordenadas por fecha._
`_parse_import_data` raises UserError "Rows must be sorted by date" if rows are neither ascending nor descending (`account_bank_statement_import_csv/wizard/account_bank_statement_import_csv.py:82-83`, `AccountBankStmtImportCSV._parse_import_data`). Descending is auto-reversed; mixed/unsorted is fatal. Odoo deliberately won't sort same-date rows for you (can't know order).

### BSIG8 — CSV needs `amount` XOR (`debit` AND `credit`); wrong combo = ValidationError _ES: Error al importar CSV: pide un Importe o bien Debe y Haber, y mi mapeo de columnas no le vale._
`(has_debit ^ has_credit) or not (has_amount ^ has_debit)` (`account_bank_statement_import_csv/account_bank_statement_import_csv.py:62-63`, `AccountBankStmtImportCSV._parse_import_data`). Mapping only `debit`, or both `amount` and `debit`, raises "Make sure that an Amount or Debit and Credit is in the file." `amount = abs(credit) - abs(debit)`.

### BSIG9 — CSV import has NO dedup and NO multicurrency (by design) _ES: Cada vez que reimporto el mismo CSV se vuelven a crear movimientos duplicados._
No `unique_import_id` is generated for CSV (the base_import path doesn't set it). Re-importing the same CSV creates duplicate lines every time. Manifest explicitly says prefer OFX. Same caveat for QIF.

### BSIG10 — OFX ledger balance ≠ ending balance _ES: Tras importar un fichero OFX el saldo final no cuadra al conciliar el banco._
Code comment + GitHub issue #3003: `balance_end_real = account.statement.balance` but the OFX ledger balance is not guaranteed to be the statement's ending balance; `balance_start` is back-computed as `balance - sum(amounts)` (`account_bank_statement_import_ofx/account_journal.py:170-173`, `AccountJournal._parse_bank_statement_file`). Reconciliation "end balance doesn't match" complaints on OFX trace here.

### BSIG11 — OFX/QIF partner matching is by payee NAME string, exact match _ES: En OFX o QIF no se asigna el cliente o proveedor a los movimientos si el nombre no coincide exactamente._
No account number in OFX/QIF, so partner is found by the payee string against `res.partner.bank.partner_id.name`. OFX pre-builds a dict `{partner_bank.partner_id.name: partner_bank}` from `('partner_id.name', 'in', transaction_payees)` (`account_bank_statement_import_ofx/account_journal.py:151-156`, `AccountJournal._parse_bank_statement_file`) and looks up `transaction.payee` per line (`:163`); QIF does a per-payee `search([('partner_id.name', '=', name)], limit=1)` (`account_bank_statement_import_qif/models/account_journal.py:91-94`, `AccountJournal._parse_bank_statement_file`). Both are **exact-domain** matches (not Python `==`), so renamed partners, accents, or trailing spaces → no match, line stays unassigned. On a name collision the OFX dict **keeps the last** matched bank (dict comprehension overwrites); QIF `limit=1` keeps whichever the ORM returns first.

### BSIG12 — QIF date format defaults to day-first (dd/mm/yy), not the QIF spec month-first _ES: Las fechas de mi fichero QIF salen con el día y el mes intercambiados._
`qif_date_format` default is `'day_first'` (`account_bank_statement_import_qif/account_journal.py:34-40`, `AccountJournal.qif_date_format`). Historic QIF spec is month-first. A US QIF (mm/dd) imported with the default flips day/month for dates ≤12. Per-journal toggle; also `qif_decimal_point` per-journal (default `.`).

### BSIG13 — OFX needs the `ofxparse` python lib or import dies at runtime _ES: Al soltar un fichero OFX da error de que falta la librería ofxparse._
Lib imported lazily; if missing you get only a server-log warning at load and a UserError "The library 'ofxparse' is missing" only when someone actually drops an OFX file (`account_bank_statement_import_ofx/models/account_journal.py:14-18`, `OfxParserClass`; el `UserError` en `account_bank_statement_import_ofx/models/account_journal.py:127-128`, `AccountJournal._parse_bank_statement_file`). Not a manifest `external_dependencies`, so module installs fine without it.

### BSIG14 — There is no import wizard menu; entry is the journal dashboard uploader _ES: No encuentro el menú ni la acción para importar extractos bancarios._
The classic "Import Statement" wizard model was removed. Users must use the `account_file_uploader` widget on the bank journal kanban card (`account_bank_statement_import/views/account_bank_statement_import_view.xml:9-13`, `journal_dashboard_view_inherit`) or drop a file. Looking for a menu/action returns nothing. New bank journals auto-set `bank_statements_source='file_import'` (`setup_wizards.py`).

### BSIG15 — Importing requires `default_account_id` on the journal, else UserError mid-pipeline _ES: La importación falla pidiendo configurar una cuenta por defecto en el diario aunque el fichero se lee bien._
`_import_bank_statement` raises "You have to set a Default Account for the journal" after parsing succeeds (`account_bank_statement_import/models/account_journal.py:51-52`, `AccountJournal._import_bank_statement`). The file parses fine but creation aborts — confusing because the error is about config, not the file.

### BSIG16 — Partial import failures commit the good statements then raise RedirectWarning _ES: Sale un error de importación pero algunos extractos ya se han creado igualmente en la base de datos._
On multi-file/multi-statement import, successful statements are `env.cr.commit()`-ed before raising the error for the failed ones (`account_bank_statement_import/models/account_journal.py:97-99`, `AccountJournal._import_bank_statement`). So a "could not import" error can coexist with statements already in the DB. The RedirectWarning offers a button to view them.

### BSIG17 — OCR only triggers for pure PDF/JPEG/PNG batches; mixing types is "rejected" (but via a bugged `return UserError`, not `raise`) _ES: Al subir a la vez PDFs o imágenes junto con otros ficheros no se importa nada y no aparece ningún error._
`account_bank_statement_extract` overrides `_import_bank_statement`: if SOME (not all) attachments are OCR-able, the intent is to block with "Mixing PDF/Image files with other file types is not allowed" — but the code does `return UserError(...)` instead of `raise UserError(...)` (`account_bank_statement_extract/models/account_journal.py:36`, `AccountJournal._import_bank_statement`). So the error object is silently **returned as the action** and never surfaces: the mixed-batch import just no-ops (no statement created, no visible error), rather than raising. OCR-able = raw starts with `%PDF` or mimetype `image/png`/`image/jpeg` (`_is_attachment_ocrizable`, `:8-10`). Pure-OCR batches go to `_send_batch_for_digitization` (`:49`); pure-non-OCR falls through to `super()._import_bank_statement` (`:38`).

### BSIG18 — OCR auto-send is ON by default and sends scans to Odoo's IAP cloud _ES: Al adjuntar un extracto escaneado se envía solo a la nube y consume créditos sin pulsar digitalizar._
`extract_bank_statement_digitalization_mode` defaults to `'auto_send'` (`account_bank_statement_extract/models/res_company.py:7-13`, `ResCompany.extract_bank_statement_digitalization_mode`). Merely setting the main attachment on a bank statement fires `_autosend_for_digitization` → uploads the document to `extract.api.odoo.com` and consumes IAP credits, without an explicit "Digitize" click. Privacy/credit gotcha for ES clients; switch to `no_send` to disable.

### BSIG19 — Imported statement gets an auto-generated PDF attachment (v18 only) _ES: El extracto importado genera automáticamente un PDF adjunto que deja de crearse tras actualizar a v19._
If `statement.is_complete`, `action_generate_attachment()` renders a PDF on creation (`account_bank_statement_import/models/account_journal.py:283-284`, `AccountJournal._create_bank_statements`), suppressible via `skip_pdf_attachment_generation` context. This step is REMOVED in v19 (see v19_changes.md) — code relying on the auto-PDF breaks after upgrade.

### BSIG20 — `set_bank_account` auto-creates a res.partner.bank from the statement's account number _ES: Al importar se creó sola una cuenta bancaria con un número de cuenta erróneo del fichero._
If the journal has no `bank_account_id`, importing silently creates one from the file's account number (`account_bank_statement_import/models/account_journal.py:196-198`, `AccountJournal._find_additional_data`). A typo'd or bank-internal (non-IBAN) account number in the file becomes a permanent bank account record on the company.

### BSIG21 — Norma 43 is not importable on stock Enterprise _ES: No puedo importar un fichero N43 o Norma 43; me manda a instalar un módulo._
Dropping a `.q43`/N43 file hits the base fallback RedirectWarning to Apps ("install the module to support this type of file") because no EE format module recognizes it. Requires OCA `l10n_es_account_statement_import_n43` (different OCA architecture) or a CAMT.053 export from the bank. See core.md ES section.

### BSIG22 — CAMT credit/debit sign is "CRDT or it's negative" — a missing/garbage indicator silently becomes a debit _ES: En el CAMT de mi banco los cobros entrantes aparecen con importe negativo o como pagos._
`_get_signed_amount`: `sign = 1 if CAMT._get_credit_debit_indicator(*nodes) == "CRDT" else -1` (`account_bank_statement_import_camt/lib/camt.py:704`, `CAMT._get_signed_amount`). The test is **equality to the literal `"CRDT"`**, not a check for `"DBIT"`. So if `CdtDbtInd` is absent, empty, namespaced unexpectedly, or any value other than exactly `CRDT`, the entry is treated as a **debit** (amount goes negative). A malformed CAMT from a non-standard bank can silently flip incoming credits to outgoing debits. Same all-or-nothing logic at balance level (`:627`, `DBIT` → negative).

### BSIG23 — CAMT raises a hard ValidationError if it can't derive an FX rate for a foreign-currency entry _ES: La importación del CAMT en divisa se aborta diciendo que no encuentra tipo de cambio para convertir._
When an entry's currency ≠ journal currency, `_get_signed_amount` tries `CcyXchg` rate getters (`_source_rate_getters`/`_target_rate_getters`, `account_bank_statement_import_camt/lib/camt.py:514-526`, `_target_rate_getters`) and a computed `entry_amount / entry_amount_in_currency` fallback; if NONE yields a rate it `raise ValidationError(_lt("No exchange rate was found to convert an amount into the currency of the journal"))` (`account_bank_statement_import_camt/lib/camt.py:702`, `CAMT._get_signed_amount`). A multi-currency CAMT that ships amounts but omits both the instructed/counter-value amount and any `CcyXchg` rate aborts the whole import. Note the message uses `_lt` (the module-local no-op `lambda x: x`, `:11`), NOT a real lazy translation — the CAMT lib is import-context-only and deliberately untranslated. Workaround: ask the bank for the counter-value amount, or import a same-currency statement.

### BSIG24 — CAMT folds bank charges into the line amount (no separate charge line) _ES: El importe de la línea del banco no cuadra con la factura por unos céntimos en transferencias con comisión._
If an entry carries charges (`Chrgs`), `_get_signed_amount` switches to the `_amount_charges_getters` and reconciles `amount + charges` against the entry total (`account_bank_statement_import_camt/lib/camt.py:660-678`, `_get_signed_amount.get_charges`); the Swiss `/100` rule for SEK/DKK/YEN/NOK applies to the rate (`:649`). The charge is **baked into the single statement line's amount**, not emitted as its own transaction. Reconciliation against an invoice for the gross amount then shows a small unexplained delta equal to the charge. Symptom: "the bank line amount doesn't match the invoice by a few cents/euros" on fee-bearing transfers.

### BSIG25 — CAMT `unique_import_id` from `AcctSvcrRef` is rejected if all-zeros or `NOTPROVIDED`, falling back to a positional id _ES: Se duplican las líneas del CAMT de un banco que no rellena la referencia bancaria al reimportar el fichero._
`_get_unique_import_id` discards the bank reference when it `_is_full_of_zeros` or equals the literal `'NOTPROVIDED'`, falling back to `{name}-{date}-{sequence}` (`account_bank_statement_import_camt/lib/camt.py:760-771`, `CAMT._get_unique_import_id`). Banks that emit `0000000000` or `NOTPROVIDED` for every entry get positional dedup ids — re-importing a re-ordered or re-dated export of the same transactions then produces NEW ids and duplicates the lines (the namespaced UNIQUE constraint doesn't catch them because the raw id changed). Symptom: duplicate CAMT lines from a bank that doesn't populate `AcctSvcrRef`.

### BSIG26 — `_check_camt` only matches the literal substring `'camt.053'`; camt.052/054 fall through to "install a module" _ES: Un fichero SEPA XML que parece CAMT no se importa y pide instalar un módulo._
`_check_camt` parses the XML and returns the root only `if root.tag.find('camt.053') != -1` (`account_bank_statement_import_camt/models/account_journal.py:30`, `AccountJournal._check_camt`). The namespace tag must literally contain `camt.053`. A `camt.052` (interim/intraday) or `camt.054` (debit/credit notification) file — both valid ISO 20022 cash-management messages some banks send — is NOT recognized, so `_parse_bank_statement_file` falls to the base RedirectWarning "Did you install the module to support this type of file?". Odoo EE supports CAMT.053 **only**. Symptom: a SEPA XML "doesn't import" though it looks like CAMT.

### BSIG27 — CAMT statement currency is sniffed from the FIRST of `Acct/Ccy` OR `Bal/Amt/@Ccy`; a missing account currency silently uses a balance's currency _ES: Un CAMT sin divisa de cuenta se importa mal o no se importa por un problema de moneda._
`currency = statement.xpath('ns:Acct/ns:Ccy/text() | ns:Bal/ns:Amt/@Ccy', ...)[0]` (`account_bank_statement_import_camt/models/account_journal.py:65`, `AccountJournal._parse_bank_statement_file_camt`). If the statement omits `Acct/Ccy`, the currency used for the whole-statement journal-match (BSIG6) is taken from whatever the first balance node's `@Ccy` is. On odd files this can differ from the entries' currency and either wrongly skip the statement (currency mismatch → `continue`, `:67-68`) or wrongly accept it. Also `[0]` means a statement with NEITHER `Acct/Ccy` nor any `Bal/.../@Ccy` raises an IndexError mid-parse (uncaught → 500), not a clean UserError.

### BSIG28 — CAMT `payment_ref` defaults to the literal `'/'` when no remittance/info is found _ES: Algunas líneas del CAMT aparecen etiquetadas solo con una barra y no casan con ninguna regla de conciliación._
`_get_transaction_name` walks `RmtInf/Ustrd`, `CdtrRefInf/Ref`, `AddtlNtryInf`, `AddtlRmtInf` and returns `'/'` if all are empty (`account_bank_statement_import_camt/lib/camt.py:736-750`, `CAMT._get_transaction_name`). Entries with no narrative (e.g. pure interest/fee postings) land in the rec widget with `payment_ref == "/"`, which reads as a blank/garbage label and never matches a rule on description. Symptom: CAMT lines labelled just `/`.

### BSIG29 — CAMT counter-party party is taken from the OPPOSITE side of the credit/debit indicator _ES: En el CAMT el nombre del cliente o proveedor del movimiento sale cambiado cuando el signo del cobro es erróneo._
`_get_counter_party` returns `'Dbtr'` when `CdtDbtInd == 'CRDT'`, else `'Cdtr'` (`account_bank_statement_import_camt/lib/camt.py:719-722`, `CAMT._get_counter_party`). For an **incoming credit** it reads the **Debtor** (the payer) as counter-party; for an outgoing debit it reads the Creditor. This is correct ISO semantics, but it means `partner_name`/`account_number`/address are pulled from `RltdPties/Dbtr*` vs `Cdtr*` depending on sign — a malformed `CdtDbtInd` (see BSIG22) flips which party Odoo reads, so a sign error also mis-attributes the counterparty.

### BSIG30 — CAMT re-reads the entry gross sign independently for the rounding fix-up — a `CdtDbtInd` other than `DBIT` is treated as credit _ES: En un CAMT con varios detalles aparece un importe de redondeo extraño cargado en la línea más grande._
After summing entry-detail amounts, the per-`Ntry` rounding correction reads `entry.find('ns:Amt')` and flips sign only `if entry.find('ns:CdtDbtInd').text == 'DBIT'` (`account_bank_statement_import_camt/models/account_journal.py:148-150`, `AccountJournal._parse_bank_statement_file_camt`), then dumps `gross - sum(details)` onto the largest detail line. This is a SECOND, independent sign read (different code path from BSIG22's `_get_signed_amount`) and a SECOND `'DBIT'`-equality test — so the same "anything-not-DBIT-is-credit" fragility applies, and a multi-detail entry with inconsistent indicators can push a spurious rounding amount onto the largest line. Also: `entry.find('ns:Amt')`/`ns:CdtDbtInd` here are required — an entry missing either raises `AttributeError` (NoneType `.text`) mid-parse.

### BSIG31 — OFX v2 sniff is `b"<ofx>" in raw.lower()` ANYWHERE in the file (very loose) _ES: Un fichero que no es OFX intenta importarse como OFX y falla porque contiene el texto ofx._
`_check_ofx` returns True for v1 if raw starts with `b"OFXHEADER"`, else for v2 if `b"<ofx>"` appears anywhere in the lowercased raw (`account_bank_statement_import_ofx/account_journal.py:102-110`, `AccountJournal._check_ofx`). Because it's a substring test on the whole file (not a root-tag check), any non-OFX file that merely contains the string `<ofx>` (e.g. a CSV column, a wrapped/forwarded blob) is claimed by the OFX parser before CAMT/QIF get a chance, then fails inside `ofxparse`. Chain-of-responsibility order is incidental, so a greedy `_check_ofx` can shadow the correct format.

### BSIG32 — QIF resets all accumulated transactions on a bare newline marker _ES: De mi fichero QIF solo se importaron los últimos movimientos; una línea en blanco descartó los anteriores._
In the QIF line loop, a line whose first byte is `b'\n'` triggers `transactions = []` (`account_bank_statement_import_qif/account_journal.py:104-105`, `AccountJournal._parse_bank_statement_file`), discarding everything parsed so far. Intended to handle a section break, but a QIF with a stray blank/newline-only record mid-file silently drops all earlier transactions, importing only those after it. Symptom: "only the last few QIF lines imported".

### BSIG33 — QIF balance_end_real is the SUM of amounts, and there is no balance_start _ES: El saldo final de un extracto QIF no es el saldo real del banco y encima no trae saldo inicial._
QIF returns `(None, None, [vals])` with `balance_end_real = total` (sum of all `T` amounts) and no `balance_start` key (`account_bank_statement_import_qif/account_journal.py:109-113`, `AccountJournal._parse_bank_statement_file`). So the "ending balance" is just the net movement of the file, not a real bank closing balance, and the opening balance is left unset. Bank-rec end-balance checks on QIF imports are meaningless. Combined with no dedup (BSIG9) and payee-name partner matching (BSIG11), QIF is the weakest of the four formats — the manifest itself says prefer OFX.

### BSIG34 — `_complete_bank_statement_vals` sets statement `reference` to the attachment filename, and that becomes the statement `name` if empty _ES: El extracto importado toma el nombre del fichero subido y cambia si renombro el archivo._
For each statement it defaults `st_vals['reference'] = attachment.name` if unset (`account_bank_statement_import/models/account_journal.py:219-220`, `AccountJournal._find_additional_data`), and after creation `if not statement.name: statement.name = st_vals['reference']` (`:277-278`). So a statement with no parsed name is named after the uploaded file. Re-uploading a renamed copy of the same file yields a differently-named statement (cosmetic, but confusing when hunting "which statement came from which file").

### BSIG35 — CSV/XLS/XLSX share the bank-import path; "CSV" import actually accepts Excel too _ES: Subí un Excel a la importación de CSV y va por el mismo asistente con las mismas limitaciones._
`_check_file_format` matches `.csv`, `.xls`, AND `.xlsx` (`account_bank_statement_import_csv/models/account_journal.py:16-17`, `AccountJournal._check_file_format`) and `_get_bank_statements_available_import_formats` advertises `CSV, XLS, XLSX` (`:11-14`). The module name says CSV but Excel files go through the same interactive `base_import` mapping wizard — and inherit the same no-dedup / no-multicurrency / must-be-date-sorted caveats (BSIG7-9). Don't assume an `.xlsx` upload uses a different, smarter path.
