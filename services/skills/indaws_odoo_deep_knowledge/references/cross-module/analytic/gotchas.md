# Analytic Gotchas — Odoo 18.0

## Architecture

**ANG1. analytic_distribution is a JSON field, not a relation** — `analytic_distribution` stores `{"account_id": percentage}` as JSON, NOT Many2many. Impact: use `distribution_analytic_account_ids` (computed M2M) for searches; standard relational domains don't work. Direct JSON LIKE queries are unreliable. _ES: No puedo filtrar facturas por cuenta analítica en el buscador, el dominio no devuelve resultados aunque las líneas la tengan asignada._

**ANG2. Each root plan creates real database columns via ALTER TABLE** — Each root plan creates `x_plan{N}_id` Many2one on ALL models inheriting `analytic.plan.fields.mixin`. Impact: high plan churn leaves orphaned columns; plans should be stable. Deletion cascades to ir.model.fields. _ES: Cada vez que creo o borro un plan analítico se añaden o quedan columnas raras en la base de datos y la cosa se ensucia._

**ANG3. Plan applicability competes by score, not sequence — but distribution MODELS use sequence + dedup** — Two different selection mechanisms, easy to conflate. (a) **Plan applicability** (`account.analytic.applicability`) uses scoring: `_get_score()` gives company +0.5 (`analytic/models/analytic_plan.py:422`, `AccountAnalyticApplicability._get_score`), business_domain match +1 / mismatch -1 (`:426`), account_prefix match +1 / mismatch -1 (`account/models/account_analytic_plan.py:67-70`), product_categ match +1 / mismatch -1 (`:71-75`); a single -1 disqualifies the whole rule (`:61`). The highest-scoring rule wins, `default_applicability` if none (`analytic/models/analytic_plan.py:245-257`, `AccountAnalyticPlan._get_applicability`). (b) **Distribution models** (`account.analytic.distribution.model`) instead order by `sequence, id desc` (`analytic/models/analytic_distribution_model.py:14`, `AccountAnalyticDistributionModel._order`) and `_get_distribution()` iterates them merging with `|`, **skipping any model whose root plan is already covered** (`analytic/models/analytic_distribution_model.py → _get_distribution`, líneas 69-72) — so the first model (by sequence) to fill a root plan wins that plan; later models only add plans not yet seen. Impact: don't expect distribution-model precedence to use scoring, and don't expect a later model to override a plan an earlier one already set. _ES: El reparto analítico automático no aplica la regla que esperaba: una distribución posterior no sobreescribe el plan que ya rellenó otra anterior._

**ANG4. Mandatory plans block invoice posting if not 100% — but ONLY on `display_type='product'` lines** — `account.move.line._validate_analytic_distribution()` iterates only product lines (`account/models/account_move_line.py:3235`, `AccountMoveLine._reconcile_marked`) and calls `_validate_distribution(validate_analytic=...)`; the 100%-per-root-plan check runs inside `analytic.mixin._validate_distribution` guarded by `context.validate_analytic` (`analytic/models/analytic_mixin.py:175-189`, `AnalyticMixin._validate_distribution`). Error text is literally "One or more lines require a 100% analytic distribution." Impact: section/note lines never validate; if the move has >1 line missing distribution you get a `RedirectWarning` listing them, but a single-move case raises a plain `ValidationError` (`account/models/account_move_line.py:3251-3264`, `AccountMoveLine._validate_analytic_distribution`). _ES: No me deja validar la factura porque exige distribución analítica al 100%, pero solo se queja de las líneas de producto, no de las de sección._

**ANG5. Project plan is special — uses account_id, not x_plan{N}_id** — The "Project" plan (set via `ir.config_parameter` `analytic.project_plan`) maps to `account_id` field. All other root plans use `x_plan{id}_id`. Impact: code assuming all plans use dynamic columns will miss the project plan. _ES: El plan de Proyecto se comporta distinto al resto de planes analíticos y mi código no lo detecta igual que los demás._

**ANG6. _merge_distribution uses cartesian product** — When `__update__` key is present, `_merge_distribution()` creates cross-product of non-changing × changing plans with proportional scaling. Impact: updating one plan in a multi-plan distribution can create unexpected key combinations. _ES: Al cambiar solo un plan en una distribución con varios planes me aparecen combinaciones de cuentas inesperadas._

**ANG7. Sanitization rounds percentages on every create/write — and the `__update__` sentinel is exempt** — `_sanitize_values()` is called on both `create()` and `write()` (`analytic/models/analytic_mixin.py:165`, `AnalyticMixin.write` y `analytic/models/analytic_mixin.py:172`, `AnalyticMixin.create`) and `float_round`s every distribution value to "Percentage Analytic" precision, EXCEPT the `__update__` key which is passed through verbatim (`:191-197`). Purpose is to make `analytic_distribution` JSON dicts comparable by equality. Impact: very precise distributions lose precision silently; the rounding is what makes `_validate_distribution`'s `float_compare(..., precision_digits=decimal_precision)` line up to exactly 100. _ES: Los porcentajes de reparto analítico se redondean solos al guardar y pierdo la precisión que había puesto._

**ANG8. _read_group on analytic_distribution only supports __count** — Grouping by `analytic_distribution` explodes JSON into rows. Only `__count` aggregation works; sum/avg on amounts will raise ValueError. Impact: need raw SQL or alternative approach for amount-by-analytic reporting. _ES: Al agrupar un informe por distribución analítica solo me deja contar registros; si intento sumar importes da error._

## Propagation

**ANG9. SOL → AML propagation is direct copy, not recompute** — `_set_analytic_distribution()` copies SOL's distribution verbatim to invoice line. Distribution models on the invoice line are only fallback if SOL has no distribution. Impact: changing distribution rules after SO confirmation won't affect existing invoices. _ES: Cambié las reglas de reparto analítico después de confirmar el pedido y las facturas ya existentes siguen con el reparto antiguo._

**ANG10. Stock move _get_analytic_distribution() returns {} by default** — Base `stock_account` returns empty dict. Only `sale_stock._prepare_procurement_values()` injects SOL distribution. Impact: stock moves without SO origin (manual, MRP components) have no analytic unless overridden. _ES: Los movimientos de stock sin pedido de venta detrás (transferencias manuales, componentes de fabricación) salen sin cuenta analítica._

**ANG11. Analytic lines created on POST, not on invoice creation — and unlinked on un-post/draft** — `to_post.line_ids._create_analytic_lines()` runs from `action_post()` (`account/models/account_move.py:5194`, `AccountMove._post`); draft invoices have no analytic lines. Conversely, going back to draft unlinks them (`account/models/account_move.py:5565`, `AccountMove.action_post`), and draft move lines have their `analytic_line_ids` unlinked with `skip_analytic_sync=True` on the relevant writes (`account/models/account_move_line.py:1645`, `AccountMoveLine.create` y `account/models/account_move_line.py:1758`, `AccountMoveLine.write`, `AccountMoveLine.create`). Impact: reporting/AAL aggregation on draft invoices returns nothing; the project profitability panel works around this by reading `account.move.line` directly (see ANG33). _ES: Las facturas en borrador no aparecen en los informes analíticos; las líneas analíticas solo se generan al validar._

**ANG12. Back-sync recomputes distribution as `-aal.amount / line.balance * 100` when analytic lines are modified** — `account.move.line._update_analytic_distribution()` rebuilds the JSON from `analytic_line_ids` using `{aal._get_distribution_key(): -aal.amount / line.balance * 100 if line.balance else 100}` (`account/models/account_move_line.py:3332-3340`, `AccountMoveLine._prepare_analytic_distribution_line`). It is triggered from `account.analytic.line.create/write/unlink` (`account/models/account_analytic_line.py:93`, `AccountAnalyticLine._compute_analytic_profitability`, y `account/models/account_analytic_line.py:99-108`, `AccountAnalyticLine.on_change_unit_amount`) whenever `amount`, `move_line_id` or any plan column changes, and short-circuits under `skip_analytic_sync`. Impact: editing an AAL's amount directly silently rewrites the invoice line's distribution percentages; if `line.balance == 0` it forces 100% and loses the real split. _ES: Si edito el importe de un apunte analítico a mano, se reescriben solos los porcentajes de reparto de la línea de factura._

**ANG13. Reward/discount lines don't inherit analytic** — `sale_loyalty` creates separate lines without copying `analytic_distribution` from the original SO line. Impact: discounts not tracked in the same analytic project. Need distribution model or custom override. _ES: Los descuentos y líneas de fidelización no arrastran la cuenta analítica del pedido y quedan fuera del proyecto._

**ANG14. Expense split copies analytic to all fragments** — `_split_amounts()` duplicates `analytic_distribution` to each tax-bracket copy. Impact: same distribution applied to all splits — cannot have per-tax analytic assignment. _ES: Al dividir un gasto por tramos de impuesto se copia la misma analítica a todos los trozos y no puedo repartirla distinto._

## MRP

**ANG15. MO has NO analytic_distribution field** — Analytic in manufacturing goes through work center (via work orders) and stock moves (via stock_account). Impact: cannot set project-level analytic on an MO directly. _ES: No encuentro dónde poner la cuenta analítica directamente en la orden de fabricación, no existe ese campo._

**ANG16. CE: analytic distribution uniform on all MO moves** — In Community Edition, MO's stock moves all get the same distribution (from SO line if any). No per-component assignment. Impact: per-component tracking needs separate MOs or `_prepare_analytic_lines()` override. _ES: En la orden de fabricación no puedo asignar analítica distinta por componente, todos los movimientos llevan la misma._

**ANG17. Work center costs are negative** — WO analytic: `amount = -(hours * costs_hour)`. Always negative (cost). Impact: summing WO analytic lines with invoice lines requires sign awareness. _ES: Los costes de centro de trabajo salen en negativo en la analítica y al sumarlos con las ventas descuadran._

**ANG18. extra_cost doesn't generate separate journal entry** — `extra_cost` added to finished product's `price_unit` in `_cal_price()`, included in single SVL entry. Impact: overhead isn't visible as separate analytic line — use workcenter costs or distribution for separate tracking. _ES: El coste extra de fabricación no aparece como línea analítica separada, va metido dentro del coste del producto._

## Project & Timesheet

**ANG19. Analytic account mandatory for timesheets** — `allow_timesheets` requires `account_id` on project. Auto-created on enable, but scripts/imports skipping the toggle will fail. _ES: Al activar partes de horas en un proyecto por script falla porque no tiene cuenta analítica creada._

**ANG20. Timesheet amount only recalculates on specific field changes** — `_timesheet_postprocess_values()` only triggers on `unit_amount`, `employee_id`, or `account_id` change. Impact: changing `hourly_cost` on employee doesn't retroactively update existing timesheets. _ES: Cambié el coste por hora del empleado y los partes de horas antiguos no se actualizan con el nuevo coste._

**ANG21. Profitability can double-count if not careful** — `_get_profitability_items()` aggregates from multiple sources (timesheets, invoices, expenses, stock). Hook `_get_already_included_profitability_invoice_line_ids()` prevents double-counting, but custom sources must register. _ES: La rentabilidad del proyecto me sale duplicada al sumar horas, facturas y gastos de varias fuentes._

## POS

**ANG22. POS closing entry has NO analytic_distribution** — `pos.session._create_account_move()` does not set `analytic_distribution` on any line. Impact: POS revenue invisible in analytic reports. Need custom override or Indaws module. _ES: Las ventas de TPV no aparecen en los informes analíticos, el asiento de cierre no lleva cuenta analítica._

**ANG23. POS order lines don't inherit analytic.mixin** — `pos.order.line` does NOT have `analytic_distribution` field. Impact: no per-product analytic in POS without custom development. _ES: No puedo asignar analítica por producto en el TPV, las líneas de pedido de TPV no tienen ese campo._

## Budget

**ANG24. Budget matching is exact plan match, not parent/child** — Budget lines match analytic accounts per-plan exactly. A budget for "Project Alpha" won't match sub-accounts unless explicitly set. Impact: hierarchical analytic structures need budget lines at every level. _ES: El presupuesto no cuadra con las subcuentas: solo cuenta la cuenta exacta y no suma los proyectos hijos._

**ANG25. Committed amount only from confirmed POs** — `budget.report` only counts POs in `purchase`/`done` state with remaining qty. Draft POs excluded. Impact: budget warnings don't account for draft purchase requests. _ES: El presupuesto no avisa del gasto comprometido de los pedidos de compra en borrador, solo cuenta los confirmados._

**ANG26. Achieved amount comes from analytic lines, not invoices directly** — Budget achievement is via `account.analytic.line` (created on invoice posting). Unpaid invoices contribute to achieved (accrual basis). Impact: can show budget achieved even if not cash-received. _ES: El presupuesto marca como consumido importe de facturas aún sin cobrar, va por criterio de devengo._

## Search & Reporting

**ANG27. GIN index only works on stored analytic_distribution** — `init()` creates the index only if `analytic_distribution` is stored on the model. Computed non-stored fields won't have the index. Impact: search performance on non-stored distributions falls back to sequential scan. _ES: Las búsquedas por distribución analítica van muy lentas cuando el campo no está almacenado._

**ANG28. Analytic shadow table negates amounts** — Enterprise reporting's temp view sets `balance = -aal.amount`. Impact: sign conventions differ between direct AAL queries and report-shadowed queries. _ES: Los importes analíticos salen con el signo cambiado entre la consulta directa y el informe._

**ANG29. Multi-plan groupby creates column explosion** — Grouping by multiple plans simultaneously creates N×M columns in reports. Impact: reports can become very wide and slow with many plans/accounts. _ES: El informe analítico por varios planes a la vez se vuelve enorme y lentísimo con tantas columnas._

## Multi-company & Multi-plan

**ANG30. Distribution model company check uses SQL array intersection** — `_check_company_accounts()` validates account company vs model company via SQL with ARRAY operator. Impact: cross-company distribution models with company-specific accounts raise UserError. _ES: Me da error al usar un modelo de distribución analítica entre empresas con cuentas de otra compañía._

**ANG31. Plan applicability is company_dependent** — `default_applicability` is `company_dependent=True`. A plan mandatory in Company A can be optional in Company B. Impact: inter-company transactions may have different validation rules. _ES: Un plan analítico obligatorio en una empresa resulta opcional en otra y la validación cambia según la compañía._

**ANG32. analytic_distribution search converts display_name to IDs** — Searching `('analytic_distribution', 'ilike', 'Sales')` automatically resolves account display_names to IDs. Impact: convenient but can match unexpected accounts if names are similar. _ES: Al buscar por texto en la distribución analítica me trae cuentas que no quería porque sus nombres se parecen._

**ANG33. AAL exist only for POSTED moves, but the project margin reads DRAFT AML** — analytic lines are generated on move post, so any AAL-based aggregation only sees posted documents. The project profitability bills section bypasses this by querying `account.move.line` directly with `('parent_state', 'in', ['draft','posted'])` and treating `parent_state=='draft'` balances as `to_invoice`/to_bill (`project_account/models/project_project.py:26`, `Project._get_add_purchase_items_domain` y `project_account/models/project_project.py:34`, `Project._get_costs_items_from_purchase` y `project_account/models/project_project.py:50-51`, `Project._get_costs_items_from_purchase`). Impact: a margin/forecast built purely on AAL will be missing the draft documents that the project panel already shows under "to bill"/"to invoice"; the two views diverge by exactly the set of draft moves carrying an analytic distribution. See PRJG33 (project-side view of the same behaviour). _ES: El margen del proyecto muestra importes de documentos en borrador que mi informe basado en analítica no ve._

## Stock propagation edge cases

**ANG34. Stock analytic lines are unlinked, not zeroed, when the move nets to zero** — `stock.move._prepare_analytic_lines()` computes `amount`/`unit_amount` from the SVL; if existing `analytic_account_line_ids` are present and both end up `0`, it `unlink()`s them and returns `False` (`stock_account/models/stock_move.py:589-591`, `StockMove._prepare_analytic_lines`). Impact: a return that fully reverses a delivery does NOT leave a pair of +/- AAL audit-trail lines — it deletes the original analytic line outright, so historical analytic detail vanishes. Returns whose net is non-zero post inverse (negative) entries via the same `_perform_analytic_distribution` path. _ES: Al devolver una entrega completa desaparece la línea analítica original en vez de quedar el rastro con el negativo._

**ANG35. Non-real-time (continental/manual) moves estimate analytic at `standard_price`, not at actual cost** — when `state != 'done'` and the move is `picked`, `_prepare_analytic_lines()` sets `amount = -unit_amount * product.standard_price` with an explicit comment that this is "Falsy in FIFO but since it's an estimation we don't require exact correct cost" (`stock_account/models/stock_move.py:571-577`, `StockMove._prepare_analytic_lines`). Impact: under FIFO/AVCO the analytic amount booked at picking time will not match the final SVL value; only `real_time` (Anglo-Saxon, `valuation='real_time'`) moves pull the exact SVL-derived amount (`:578-584`). Continental valuation reconciles via the periodic SVL branch (`:585-587`). _ES: El importe analítico apuntado al preparar el envío no coincide con el coste real final bajo FIFO o precio medio._

**ANG36. Stock analytic distribution comes ONLY from the move, not from the MO/picking** — `stock.move._get_analytic_distribution()` is a `{}` stub in `stock_account` (`stock_account/models/stock_move.py:772-773`, `StockMove._get_analytic_distribution`) and the only CE injector is `sale_stock`, which copies `sale_line_id.analytic_distribution` into procurement values (`sale_stock/models/stock.py:27-28`, `StockMove._prepare_procurement_values`). Impact: dropship moves still carry `sale_line_id` so they flow normally, but back-orders/split moves each keep the distribution they were created with and are never merged, and any move with no SO origin (manual transfer, MRP component, internal) has empty analytic unless a custom override sets it. (Generalises ANG10 to the dropship/back-order/manual cases.) _ES: Los albaranes parciales y las entregas divididas mantienen cada uno su analítica y nunca se unifican._

**ANG37. Landed costs have no dedicated analytic hook — they ride the SVL** — `stock_landed_costs` defines no analytic handling of its own; the extra cost is added to the valuation layer and only reaches analytic through the standard `real_time` SVL branch of `_prepare_analytic_lines()`. Impact: you cannot give a landed cost its own analytic distribution distinct from the receipt move; it inherits whatever distribution the underlying stock move carries (or none). Mirrors `mrp_account`'s `extra_cost` behaviour (see ANG18). _ES: No puedo dar a un coste en destino una cuenta analítica propia, hereda la del movimiento de stock de la recepción._

## Plan / column internals

**ANG39. `_get_all_plans` is ormcached and HARD-FAILS if no Project plan is configured** — `__get_all_plans()` is `@ormcache()` (`analytic/models/analytic_plan.py:104-110`, `AccountAnalyticPlan.__get_all_plans`); it reads `ir.config_parameter` `analytic.project_plan` and raises `UserError("A 'Project' plan needs to exist and its id needs to be set as analytic.project_plan...")` when unset/zero. Because nearly every analytic operation (`_column_name`, `_get_plan_fnames`, view patching, distribution merge) calls it, a missing/zeroed config param breaks analytic UI globally, not just one feature. Impact: after restoring a DB or deleting the wrong plan, set `analytic.project_plan` before anything analytic works. The cache is cleared via `self.env.registry.clear_cache()` on plan `unlink()` (`:265`). _ES: Tras restaurar la base de datos o borrar un plan, toda la analítica deja de funcionar y salta un error de plan de Proyecto no configurado._

**ANG40. Reparenting/replanning an account REFUSES to silently move history — it raises RedirectWarning** — moving an account to another plan (`account.analytic.account.write({'plan_id':...})`, `analytic/models/analytic_account.py:212-218`, `AccountAnalyticAccount.write`) or reparenting a plan (`analytic/models/analytic_plan.py:364-386`, `AccountAnalyticPlan.write`) calls `_update_accounts_in_analytic_lines()`, which if existing analytic lines would be overwritten raises a `RedirectWarning("Whoa there! Making this change would wipe out your current data...")` with a button to view the offending lines (`analytic/models/analytic_account.py:180-198`, `AccountAnalyticAccount._update_accounts_in_analytic_lines`). Only when no collision exists does it run the raw `UPDATE account_analytic_line SET new_col = old_col, old_col = NULL` (`:199-209`) and `invalidate_model()`. Impact: you cannot move accounts between plans programmatically without first clearing/relocating their existing AAL; expect the warning, not a clean migration. _ES: Al cambiar una cuenta de plan analítico salta un aviso de que se perderían datos en vez de mover el histórico limpiamente._

**ANG41. account.analytic.line has NO `move_id`, NO `auto_account_id` column, and `code` is capped at 8 chars** — `account.analytic.line` links to the journal entry only through `move_line_id` (ondelete='cascade', `account/models/account_analytic_line.py:36-42`, `AccountAnalyticLine.partner_id`); there is no direct `move_id`. `auto_account_id` is a context-dependent *computed* magic field (depends on `analytic_plan_id` context, `analytic/models/analytic_line.py:26-38`, `AnalyticPlanFields.auto_account_id`), NOT a stored column — the One2many `account.analytic.account.line_ids` is declared against it (`analytic/models/analytic_account.py:54-58`, `class AccountAnalyticAccount`) and only resolves correctly when the right plan id is in context. `code` is `fields.Char(size=8)` (`account/models/account_analytic_line.py:43`, `AccountAnalyticLine.move_line_id`). Impact: domains/sorts on `move_id` don't exist; searching AAL "by account" generically must go through `auto_account_id`'s `_search_auto_account` which ORs every plan column (`analytic/models/analytic_line.py:48-53`, `AnalyticPlanFields._search_auto_account`), and stuffing a long code into an AAL truncates. _ES: No puedo ordenar ni filtrar apuntes analíticos por asiento porque no existe ese campo, y el código se corta a 8 caracteres._

**ANG42. AAL general_account_id is constrained to equal the journal item's account** — `account.analytic.line.general_account_id` is computed-stored from `move_line_id.account_id` but `readonly=False` (`account/models/account_analytic_line.py:15-22`, `AccountAnalyticLine.product_id` y `account/models/account_analytic_line.py:47-50`, `AccountAnalyticLine.code`), and a `@api.constrains` raises `"The journal item is not linked to the correct financial account"` if you set it to anything other than `move_line_id.account_id` while a move line is linked (`:52-56`). Impact: you can freely set `general_account_id` on a standalone (no `move_line_id`) analytic line, but never override it on an invoice-derived one. _ES: No me deja cambiar la cuenta contable de un apunte analítico ligado a una factura, da error de cuenta incorrecta._

**ANG43. Account balance converts every line at TODAY's rate, not the line's date** — `account.analytic.account._compute_debit_credit_balance()` converts each currency bucket with `from_currency._convert(..., date=fields.Date.today())` (`analytic/models/analytic_account.py:142-148`, `_compute_debit_credit_balance.convert`). It groups analytic lines per `plan._column_name()` + `currency_id`, splits credit (`amount>=0`) vs debit (`amount<0`), and sets `balance = credit - debit` (`:156-178`). Impact: the displayed `balance/debit/credit` on a multi-currency analytic account drifts day to day with FX and will NOT match a historical-rate report; also `from_date`/`to_date` context keys filter the lines (`:151-154`) but the rate is still today's. `debit`/`credit` are further gated behind `account.group_account_readonly` once `account` is installed (`account/models/account_analytic_account.py:18-19`, `AccountAnalyticAccount.debit`). _ES: El saldo de una cuenta analítica multidivisa cambia cada día con el tipo de cambio y no cuadra con informes a fecha histórica._

**ANG44. Invoice/bill counts on an analytic account only see POSTED moves of the matching type** — `_compute_invoice_count` / `_compute_vendor_bill_count` `_read_group` `account.move.line` filtered to `parent_state='posted'` and `('analytic_distribution','in', self.ids)`, grouped by `analytic_distribution` with `__count` (`account/models/account_analytic_account.py:21-51`, `AccountAnalyticAccount._compute_invoice_count`). They depend only on `line_ids`, and the `'in'` operator on the JSON field is what resolves account IDs (see ANG1/ANG8). Impact: smart-button counts exclude draft and the opposite document type; a sale credit note counts under invoices (sale types include receipts), not bills. _ES: Los botones de contador de facturas de la cuenta analítica no cuentan los borradores y mezclan abonos de venta con las facturas._

## v19 changes

**ANG38. v19 replaces `_condition_to_sql` analytic override with a real `search=` method** — in v18 both `analytic.mixin` and `account.analytic.line` overrode `_condition_to_sql` to translate `analytic_distribution`/`date='fiscal_start_year'` filters into SQL (`v18 analytic/models/analytic_mixin.py:73`, `AnalyticMixin._condition_to_sql`, `analytic/models/analytic_line.py:262`, `AccountAnalyticLine._inverse_analytic_distribution`). v19 removes those overrides: `analytic_distribution` now declares `search="_search_analytic_distribution"` returning `Domain.custom(to_sql=...)` (`v19 analytic/models/analytic_mixin.py:16-21`, `AnalyticMixin.analytic_distribution` y `v19 analytic/models/analytic_mixin.py:80-112`, `AnalyticMixin._search_analytic_distribution`), and the fiscal-year filter becomes a non-stored `fiscal_year_search` boolean with `search='_search_fiscal_date'` (`v19 analytic/models/analytic_line.py:222-226`, `AccountAnalyticLine.fiscal_year_search` y `v19 analytic/models/analytic_line.py:272`, `AccountAnalyticLine._search_fiscal_date`). Impact: custom code that overrode `_condition_to_sql` on analytic models (or relied on `('date','=','fiscal_start_year')`) breaks on v19 — port to the `search=` handlers and use `('fiscal_year_search','=',True)`. Negative operators on `auto_account_id` now return `NotImplemented` (`v19 analytic_line.py` `_search_auto_account`). _ES: En la v19 se rompe el código propio que filtraba distribución analítica o el filtro de año fiscal por SQL._
