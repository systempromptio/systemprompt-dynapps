# Security Gotchas — Odoo 18.0

Format per gotcha: **cause → effect → fix**, with source `path:line`. Paths are under `odoo18/odoo/`. NB: in v18 the **groups model is defined in `res_users.py`** (class `GroupsImplied`/`Groups`), there is no `res_groups.py` (that file appears only in v19).

## Layered model & evaluation order

**SECG1. Record rules: global=AND, group=OR** — *Cause:* `_compute_domain` appends no-group rules to `global_domains` (`odoo/addons/base/models/ir_rule.py:160-161`, `IrRule._compute_domain`) and group rules (when `rule.groups & user_groups`) to `group_domains` (`:162-163`), then returns `AND(global_domains + [OR(group_domains)])` when group rules exist, else just `AND(global_domains)` (`:166-168`). The docstring of `_get_failing` states it verbatim: *"local rules are OR-ed together… while global rules get AND-ed and can each fail"* (`odoo/addons/base/models/ir_rule.py:82-85`, `IrRule._get_failing`). *Effect:* a global rule is *always restrictive* and cannot be re-opened by any group rule; a group rule only widens access within its groups. Mixing them up → silent lockout or over-exposure. *Fix:* use **global** rules for mandatory walls (multi-company), **group** rules for graduated visibility; never try to "allow back" with a group rule what a global rule forbade. _ES: No consigo volver a abrir con una regla de grupo un acceso que una regla global bloquea; los permisos por grupo no amplían lo que la global cierra._

**SECG2. No ACL record = DENIED (not default-allow)** — *Cause:* `check()` returns access only if the model appears in `_get_allowed_models(mode)`, which is built from existing `ir.model.access` rows (`odoo/addons/base/models/ir_model.py:2156`, `IrModelAccess.check` y `odoo/addons/base/models/ir_model.py:2130-2141`, `IrModelAccess._get_allowed_models`). *Effect:* a brand-new model with no CSV line → nobody (except root) can read/write it. *Fix:* always ship an `ir.model.access.csv` line per model+group; for transient wizards too. _ES: Creé un modelo nuevo y nadie puede verlo ni editarlo salvo el administrador._

**SECG3. Field groups: SILENT only when fields aren't named — explicit access RAISES** — *Cause:* `check_field_access_rights` has two branches. When `field_names` is empty/None it **silently filters out** inaccessible fields (`odoo/models.py:3792-3793`, `BaseModel.check_field_access_rights`, using `field.is_accessible(env)`, `odoo/fields.py:960-966`, `Field.is_accessible`) → read omits them, write drops them, no error. But when you **explicitly name** an inaccessible field it builds `invalid_fields` and **`raise AccessError`** (`odoo/models.py:3796-3837`, `BaseModel.check_field_access_rights`, raise at `:3837`). *Effect:* `record.read([])` / a plain form view → field just disappears ("data is missing, no error"); `record.read(['restricted'])` / `search([('restricted','=',x)])` / writing that key → hard AccessError. So the "always silent" mental model is wrong. *Fix:* to confirm a *missing* field, `record.sudo().read(['the_field'])`; check the Python field for `groups=`. Field gating is storage-level, not just the widget. (In debug/`group_no_one` the error even lists the allowed groups, `odoo/models.py:3814-3835`, `BaseModel.check_field_access_rights`.) _ES: Un campo restringido desaparece del formulario sin dar error, pero al buscarlo o filtrarlo por él salta un error de acceso._

**SECG4. `implied_ids` inserts REAL rows in `res_groups_users_rel`** — *Cause:* the membership write runs a recursive CTE that physically inserts (gid,uid) pairs for every implied group (`odoo/addons/base/models/res_users.py:1503-1521`, `GroupsImplied.write`). *Effect:* removing a user from group A does **not** remove implied-group rows if another group also implies them — they were stored independently. *Fix:* recompute by re-writing `groups_id`, or rely on `_get_group_ids` rather than reasoning about raw rel rows. _ES: Quito al usuario de un grupo pero conserva permisos heredados porque otro grupo también los implica._

**SECG5. `base.group_no_one` is debug-session-dependent** — *Cause:* `has_group('base.group_no_one')` is `result and bool(request and request.session.debug)` (`odoo/addons/base/models/res_users.py:1215-1216`, `Users.has_group`). *Effect:* technical fields/menus gated on it vanish outside debug mode — by design, but surprising. *Fix:* expected behavior; for always-on internal-tech fields use `base.group_system` or `groups='.'` instead. _ES: Ciertos campos o menús técnicos solo aparecen cuando activo el modo desarrollador._

## ACL layer

**SECG6. `sudo()` flips `env.su` but does NOT change `env.uid`** — *Cause:* `sudo(flag=True)` returns `self.with_env(self.env(su=flag))` (`odoo/models.py:6318`, `BaseModel.sudo`) — only `env.su` changes; its docstring states "does not change the current user" (`:6296-6297`). `env.user` itself is `self(su=True)['res.users'].browse(self.uid)` (`odoo/api.py:687-692`, `Environment.user`) → always the **real uid**. The su short-circuit lives in the public access methods (`odoo/models.py:4443`, `BaseModel.check_access`; `:4451`, `BaseModel.has_access`; `:4460`, `BaseModel._filtered_access`; `:5590`, `BaseModel._apply_ir_rules`), not in `_check_access` itself (`:4464`, which does the real ACL+rule work). *Effect:* code that reads `self.env.user` inside sudo gets the *original* user, not admin → wrong audit trail / wrong owner. *Fix:* use `with_user(target)` when you actually need to act as another user. _ES: Dentro de un sudo el usuario sigue siendo el original en vez del administrador, y el rastro de auditoría queda con el autor equivocado._

**SECG7. Multi-company rule is NOT automatic from `company_id`** — *Cause:* nothing auto-generates an `ir.rule` when you add a `company_id` field. *Effect:* users see rows from ALL companies. *Fix:* ship a global rule `[('company_id','in',company_ids)]`; `company_ids` resolves to `env.companies.ids` (`odoo/addons/base/models/ir_rule.py:48`, `IrRule._eval_context`). _ES: Añadí el campo de empresa pero los usuarios siguen viendo registros de todas las compañías._

**SECG10. Empty `group_id` in ACL = public access (deprecated)** — *Cause:* the SQL allows `a.group_id IS NULL` (`odoo/addons/base/models/ir_model.py:2142`, `IrModelAccess._get_allowed_models`); a logged warning fires (`odoo/addons/base/models/ir_model.py:2202`, `IrModelAccess.create`). *Effect:* a CSV line with no group grants the perm to *everyone*, incl. portal/public. *Fix:* always specify a group in `ir.model.access.csv`. _ES: Una línea de permisos sin grupo asignado da acceso a todo el mundo, incluido portal y público._

**SECG16. ACL caches per (uid, mode) — programmatic changes need a cache clear** — *Cause:* `_get_allowed_models` is `@ormcache('self.env.uid','mode')` (`odoo/addons/base/models/ir_model.py:2129-2130`, `IrModelAccess._get_allowed_models`); only create/write/unlink on `ir.model.access` call `call_cache_clearing_methods()` (`odoo/addons/base/models/ir_model.py:2186-2188`, `IrModelAccess.call_cache_clearing_methods`; call sites at `:2195`, `:2206`, `:2210`). *Effect:* granting a group via raw SQL or via `res.groups` membership change without touching ACL rows can leave stale "denied" caches in a running worker. *Fix:* `self.env.registry.clear_cache()` after out-of-band changes, or restart workers. _ES: Concedí un permiso por SQL o cambiando la pertenencia de grupo y sigue denegando hasta que reinicio el servidor._

**SECG17. Multiple ACL rows for the same model+group are OR-ed, not intersected** — *Cause:* the query `GROUP BY m.model` collapses any matching row that grants the perm (`odoo/addons/base/models/ir_model.py:2130-2141`, `IrModelAccess._get_allowed_models`). *Effect:* you cannot *remove* a permission by adding a stricter second ACL line — the looser one still grants it. *Fix:* to tighten, edit/deactivate the existing permissive row (`active=False`); adding rows only ever widens. _ES: Añadí una segunda línea de permisos más restrictiva pero no quita el acceso; la permisiva anterior sigue mandando._

## Record-rule layer

**SECG9. Rule domains cache by (uid, su, model, mode, allowed_company_ids)** — *Cause:* `_compute_domain` ormcache key (`odoo/addons/base/models/ir_rule.py:137`, `IrRule._compute_domain`); cache cleared on rule CRUD (`odoo/addons/base/models/ir_rule.py:182`, `IrRule.unlink` (y `:190` `IrRule.create`, `:200` `IrRule.write`), `IrRule.unlink`). *Effect:* editing a rule's `domain_force` via SQL, or changing it while another worker holds the cache, "doesn't take." *Fix:* edit via ORM (auto-clears), or `env.registry.clear_cache()` / restart; in `--dev xml` the cache is disabled so rules reload each call. _ES: Edité el dominio de una regla directamente en base de datos y no surte efecto hasta reiniciar._

**SECG12. `ir.rule` in `noupdate="1"` ignores code changes on upgrade** — *Cause:* `<data noupdate="1">` protects admin edits, so module upgrades skip the record. *Effect:* you fix `domain_force` in code, upgrade, and nothing changes. *Fix:* temporarily `noupdate="0"` (overwrites admin customizations) or write a migration script that updates the rule. _ES: Corregí el dominio de una regla en el código, actualicé el módulo y la regla sigue igual que antes._

**SECG18. Per-operation rules: a read-only rule leaves writes unrestricted** — *Cause:* `ir.rule` has independent `perm_read/write/create/unlink`, all default True (`odoo/addons/base/models/ir_rule.py:24-27`, `class IrRule`); `_compute_domain(mode)` only collects rules with `perm_<mode>` set. *Effect:* a rule with only `perm_read` restricts what users *see* but not what they can *write* to (they could write to rows the read rule hides, if they can reference the id). *Fix:* set all relevant perms on the rule, or add a matching write rule. _ES: Puse una regla solo de lectura pero los usuarios siguen pudiendo escribir en registros que no deberían tocar._

**SECG19. Search silently returns fewer rows; direct browse raises** — *Cause:* record rules are compiled into the WHERE clause for search/read (`_apply_ir_rules`, `odoo/models.py:5584-5597`, `BaseModel._apply_ir_rules`), so denied rows are never fetched; but reading a specific denied id raises `_make_access_error` (`odoo/addons/base/models/ir_rule.py:203`, `IrRule.write`). *Effect:* `search([...])` quietly omits records (looks like "missing data"), while `browse(id).read()` errors — inconsistent symptoms for the same restriction. *Fix:* debug with `has_access`/`_filtered_access` to see what's filtered vs. raising. _ES: La búsqueda devuelve menos registros y parece que faltan datos, pero abrir uno directo por su enlace da error de acceso._

**SECG20. Rule domain uses `company_ids` (switched), not `user.company_ids`** — *Cause:* the eval context binds `company_ids = env.companies.ids` (the multi-company selector), not the user's allowed set (`odoo/addons/base/models/ir_rule.py:48`, `IrRule._eval_context`). *Effect:* a rule written with `user.company_ids` behaves differently from `company_ids`; toggling companies in the UI changes visibility and invalidates the rule cache. *Fix:* use the provided `company_ids`/`company_id` context variables for multi-company rules. _ES: La visibilidad de los registros cambia según qué empresa tengo seleccionada en la barra superior._

**SECG21. A user with no matching rule (global or group) sees ALL rows** — *Cause:* if `_compute_domain` finds no global rules and the user is in no group with a rule, the AND/OR build yields an empty domain → no restriction (`odoo/addons/base/models/ir_rule.py:167-168`, `IrRule._compute_domain`). *Effect:* a model with only group-specific rules leaves users *outside* those groups (but with ACL read) seeing everything. *Fix:* pair group rules with a global multi-company rule, or add a catch-all rule for the base user group. _ES: Usuarios que no están en ningún grupo con regla ven todos los registros del modelo._

## sudo / context bypass

**SECG22. `sudo()` bypasses record rules — including multi-company** — *Cause:* `_apply_ir_rules` returns immediately when `env.su` (`odoo/models.py:5590`, `BaseModel._apply_ir_rules`). *Effect:* `model.sudo().search([])` returns rows from *every* company, ignoring the multi-company wall — a frequent cross-company data leak in custom code. *Fix:* never `sudo()` a user-facing search; if you must sudo for a privileged read, re-scope with `with_company` / an explicit `[('company_id','in',...)]` domain. _ES: Una búsqueda con permisos de superusuario devuelve registros de todas las empresas y se salta la multicompañía._

**SECG23. `compute_sudo` runs computes as superuser by default for stored AND related fields** — *Cause:* for a *computed* field `compute_sudo` defaults to the `store` value (`odoo/fields.py:445`, `Field._get_attrs` → stored=True, non-stored=False; declared default `:309`); for a *related* field it defaults to `related_sudo` which is True (`odoo/fields.py:453`, `Field._get_attrs`). The compute runs `model.sudo(records.env.su or self.compute_sudo)` (`odoo/fields.py:762`, `Field._search_related`), and related-to-SQL traversal also sudoes (`odoo/models.py:2935-2938`, `BaseModel._traverse_related_sql`). *Effect:* a stored computed field — or **any related field** — can read data the *current* user can't, leaking restricted values into a field they can see (e.g. a stored total across all companies, or a related field reaching into a record the user can't access). *Fix:* set `compute_sudo=False` (or `related_sudo=False`) on sensitive computes/related fields, or scope the compute explicitly. _ES: Un campo calculado o relacionado muestra datos que el usuario no debería ver, como totales o registros de otra empresa._

**SECG24. `with_user` re-checks everything; `sudo` doesn't — don't confuse them for impersonation** — *Cause:* `with_user(u)` sets `env.uid=u, su=False` (re-evaluates layers); `sudo()` keeps uid and disables layers. *Effect:* "impersonating" with `sudo()` neither applies the target's restrictions nor records them as actor → security tests pass falsely. *Fix:* test permissions with `with_user(u)`, never `sudo()`. _ES: Simulo a otro usuario con sudo pero no se aplican sus restricciones ni queda registrado como él._

## Field-level

**SECG15. `groups='.'` means NO ONE (only sudo)** — *Cause:* `is_accessible` returns False for `groups=='.'` regardless of user, only `env.su` passes (`odoo/fields.py:962`, `Field.is_accessible`). *Effect:* the field is invisible in *every* UI incl. admin; useful for tokens/hashes but a footgun if set by accident. *Fix:* intentional for sudo-only fields; otherwise use a real group. _ES: Un campo no aparece en ninguna pantalla, ni siquiera para el administrador._

**SECG25. Field `groups=` is OR across the CSV, and ANY group grants it** — *Cause:* `is_accessible` calls `user.has_groups(self.groups)` and `has_groups` OR-s comma terms (`odoo/addons/base/models/res_users.py:1168-1197`, `Users.has_groups`). *Effect:* `groups='a.g_invoice,a.g_readonly'` exposes the field to readonly accountants too — often unintended when you meant "managers only." *Fix:* list only the intended group(s); use `!` negation in `has_groups`-based logic if you need exclusion (not available directly in the field `groups=` syntax). _ES: Restringí un campo a un grupo pero también lo ven usuarios de otro grupo que dejé en la lista de permisos._

## Groups & user types

**SECG11. User-type groups are mutually exclusive** — *Cause:* `_check_one_user_type()` constrains membership to ≤1 group in `module_category_user_type` (`odoo/addons/base/models/res_users.py:616`, `Users._check_action_id`). *Effect:* a user can't be internal AND portal; trying to add both raises a ValidationError. *Fix:* for internal users that need portal-like limits, use group-specific record rules, not the portal group. _ES: No puedo marcar al usuario como interno y de portal a la vez; salta un error de validación._

**SECG26. `share` is computed from group membership, not freely set** — *Cause:* `_compute_share` sets internal users (those with `base.group_user`) to `share=False`, everyone else True (`odoo/addons/base/models/res_users.py:530-535`, `Users._compute_signature`). *Effect:* you can't make a user "share" by writing `share=True`; it's derived. Custom code filtering on `share` must remember it tracks the user-type group. *Fix:* change the user's type group, not `share`. _ES: No consigo marcar manualmente a un usuario como externo o de tipo compartido; el valor no se deja fijar._

**SECG27. `has_group` RAISES if you query a user other than yourself (unless su/internal)** — *Cause:* `has_group` guards with `if not (self.env.su or self == self.env.user or self.env.user._has_group('base.group_user')): raise AccessError("You can ony call user.has_group() with your current user.")` (`odoo/addons/base/models/res_users.py:1201-1204`, `Users.has_group`). The `:1201` line is a **caller guard**, not a result short-circuit. The actual membership test is `_has_group` (`:1211-1222`), which resolves the group id via the new `_get_group_definitions().get_id()` registry (`:1220`) and checks `_get_group_ids()`. *Effect:* a non-internal (portal/public) user calling `other_user.has_group(...)` over RPC gets an AccessError — by design, to stop user enumeration. Internal users and sudo bypass the guard. *Fix:* to test *real* membership of an arbitrary user from privileged code, use `user.sudo().has_group(...)` (that's exactly what `_is_internal/_is_portal/_is_public` do, `odoo/addons/base/models/res_users.py:1289-1299`, `Users.action_show_rules`); use `with_user(u)` when you want the check evaluated *as* that user. _ES: Un usuario de portal recibe error de acceso al consultar los grupos de otro usuario._

## Portal & multi-company

**SECG8. Portal users rely ENTIRELY on record rules** — *Cause:* portal ACL is read-only; there's no implicit ownership filter. *Effect:* `perm_read=1` for `base.group_portal` with no record rule → portal user reads ALL records of that model. *Fix:* always pair portal ACL with a partner/follower-scoped record rule. _ES: El usuario de portal ve todos los registros del modelo en vez de solo los suyos._

**SECG14. Portal `child_of [commercial_partner_id]` exposes all sibling contacts** — *Cause:* `child_of` walks the partner tree under the commercial partner (`message_partner_ids child_of [...]`). *Effect:* one contact sees every document followed by *any* contact of the same company. *Fix:* use `=` on the specific partner for strict per-contact isolation; `child_of` only when company-wide visibility is intended. _ES: Un contacto del portal ve los documentos de todos los demás contactos de su misma empresa._

**SECG13. `check_company=True` validates but doesn't filter the UI** — *Cause:* it raises on company mismatch but performs no domain filtering. *Effect:* dropdowns still show incompatible-company records; user picks one and gets an error on save. *Fix:* add `domain="[('company_id','in',allowed_company_ids)]"` on the field/view, or rely on the comodel's record rule. _ES: El desplegable muestra registros de otra empresa y al elegir uno da error al guardar._

**SECG28. `sudo()` in portal/website controllers must be paired with `access_token`** — *Cause:* public/portal controllers `sudo()` to render data the public user can't read, bypassing all layers — `_apply_ir_rules` returns early on `self.env.su` (`odoo/models.py:5593-5594`, `BaseModel._apply_ir_rules`). *Effect:* if the controller doesn't validate an `access_token` (or `portal.mixin` `_document_check_access`), the sudo read leaks other customers' documents via URL guessing. *Fix:* always `_document_check_access(model, id, access_token)` before sudo-rendering; never trust `request.params` ids. _ES: Cambiando el número en la URL del portal, un cliente accede a documentos de otros clientes._

## New in v18 — group algebra & env internals

**SECG31. `with_user(u)` resets `env.su` to False — except for the superuser** — *Cause:* `Environment.__call__` computes `su = (user is None and self.su) if su is None else su` (`odoo/api.py:649`, `Environment.__call__`), so switching `user` with no explicit `su` drops superuser mode; but `Environment.__new__` *forces* `su=True` whenever `uid == SUPERUSER_ID` (`odoo/api.py:570-573`, `Environment.__new__`). *Effect:* `recs.sudo().with_user(u)` is NOT still sudo — it becomes a normal `u` env (good for impersonation). But `with_user(SUPERUSER_ID)` / `with_user(env.ref('base.user_root'))` silently stays in su mode. *Fix:* don't rely on chaining `sudo().with_user()` to keep root powers; pass `su=` explicitly via `with_env(env(user=u, su=True))` if you truly need it. _ES: Encadené superusuario con cambio de usuario esperando mantener los permisos de root y se pierden, o con el usuario root se quedan sin querer._

**SECG32. `env.company`/`env.companies` validate `allowed_company_ids` — and raise — but NOT under sudo** — *Cause:* both properties check `set(company_ids) - set(user._get_company_ids())` and `raise AccessError("Access to unauthorized or invalid companies.")` **only when `not self.su`** (`odoo/api.py:717-720`, `Environment.company` and `:748-750`); the docstrings note "No sanity checks applied in sudo mode!" (`:705-713`, `:735-743`). *Effect:* a forged `allowed_company_ids` context key is rejected for a normal user, but under `sudo()` any company id is accepted — a frequent inter-company write vector in custom code that sudoes then trusts the context company. *Fix:* never derive the target company from untrusted context inside a sudo block; pin it explicitly with `with_company(real_company)`. _ES: Dentro de un bloque de superusuario se acepta cualquier empresa del contexto y se escriben datos en la compañía equivocada._

**SECG33. No `allowed_company_ids` → `env.companies` defaults to ALL the user's companies** — *Cause:* when the context key is absent, `env.companies` returns `browse(user._get_company_ids())` (every allowed company, `odoo/api.py:745`, `Environment.companies` y `odoo/api.py:752-762`, `Environment.companies`), and `env.company` falls back to `user.company_id` (`:715,722`). *Effect:* "out of context" code paths (cron, report rendering, mail templates, `/web/image`, `/mail/redirect`) run with **all** the user's companies active, so a multi-company `[('company_id','in',company_ids)]` rule lets them see every company — not just the UI-selected one. *Fix:* in batch/cron code that must be company-scoped, wrap in `with_company(c)` / set `allowed_company_ids` explicitly; don't assume the active company narrows automatically. _ES: En crons, informes o plantillas de correo el usuario ve todas sus empresas en vez de solo la que tenía seleccionada._

**SECG34. v18 group membership is a set-algebra registry (`SetDefinitions`), not raw rel scans** — *Cause:* `res.groups._get_group_definitions()` builds a cached `SetDefinitions` object over all groups (`odoo/addons/base/models/res_users.py:1574-1575`, `GroupsImplied._get_group_definitions`, decorated `@ormcache(cache='groups')`); ACL resolves the allowed-user set via `_get_access_groups` → `group_definitions.empty/universe/from_ids` (`odoo/addons/base/models/ir_model.py:2106-2122`, `IrModelAccess._get_access_groups`), and `_has_group` resolves ids via `.get_id(ext_id)` (`odoo/addons/base/models/res_users.py:1228`, `Users._has_group`). *Effect:* the canonical "who is in this group" answer now goes through this registry; clearing membership caches uses the dedicated `'groups'` cache bucket (`odoo/addons/base/models/res_users.py:1492`, `GroupsImplied.create`; `:1539`, `GroupsImplied.write`; `:1544`, `GroupsImplied.unlink`), distinct from the per-uid ACL/rule ormcaches. Raw `res_groups_users_rel` queries can disagree with the registry until that cache is cleared. *Fix:* after out-of-band group/implied changes, `env.registry.clear_cache('groups')` (the ORM does this on `res.groups` create/write/unlink); don't reason about membership purely from the rel table. _ES: Cambié la pertenencia a grupos directamente en base de datos y las comprobaciones de grupo no coinciden hasta limpiar caché._

**SECG35. `has_groups` with only `!`-negated terms (no positives) returns True** — *Cause:* `has_groups` ends with `return not positives` after checking negatives then positives (`odoo/addons/base/models/res_users.py:1175-1189`, `Users.has_groups`): if the spec has no positive term and no negative matched, the result is `True`. *Effect:* `has_groups('!base.group_system')` is True for *every* non-admin (and for portal/public users too) — easy to misread as "must be in some group." *Fix:* if you mean "internal-and-not-admin," write `'base.group_user,!base.group_system'`; remember a pure-negation spec defaults to allow. _ES: Una comprobación de grupos escrita solo con negaciones da verdadero para todos, incluidos usuarios de portal y públicos._

**SECG36. Record rules cover `_inherits` parents — a child rule silently AND-s the parent's rules** — *Cause:* `_compute_domain` walks `self.env[model]._inherits` and, for each delegated parent, AND-s the parent's computed domain as `[(parent_field, 'any', parent_domain)]` into the child's global domains (`odoo/addons/base/models/ir_rule.py:143-146`, `IrRule._compute_domain`). *Effect:* e.g. `res.users` (inherits `res.partner`) is also constrained by `res.partner` rules; tightening a parent model's rules can unexpectedly hide child records, and you won't find the cause in the child model's own rules. *Fix:* when a delegated model "loses" rows, inspect the parent model's `ir.rule` too. _ES: Endurecí las reglas del modelo padre y desaparecieron registros del modelo hijo, sin encontrar la causa en las reglas del hijo._

**SECG37. `_compute_domain` group-match uses `groups_id`, while `_get_rules` pre-selects via `_get_group_ids()`** — *Cause:* `_get_rules` SQL filters candidate rules by `tuple(user._get_group_ids())` (`odoo/addons/base/models/ir_rule.py:131`, `IrRule._get_rules`, the ormcached materialized set), but the in-Python "does this group rule apply" test uses `rule.groups & self.env.user.groups_id` (`odoo/addons/base/models/ir_rule.py:154,162`, `IrRule._compute_domain`). *Effect:* the two read membership through different paths; normally equal, but if `groups_id` is stale in the env cache vs the `_get_group_ids` ormcache (e.g. right after a raw membership change), a rule can be selected yet not matched, or vice-versa. *Fix:* after programmatic group changes, invalidate (`user.invalidate_recordset(['groups_id'])`) and clear caches before relying on rule evaluation in the same transaction. _ES: Justo después de cambiar grupos por código, la evaluación de reglas usa una pertenencia desactualizada y da resultados incoherentes._

## Upgrade / v19 forward-compat

**SECG29. `groups_id`/`users`/`trans_implied_ids` renamed in v19** — *Cause:* v19 renames `res.users.groups_id → group_ids`, `res.groups.users → user_ids`, `trans_implied_ids → all_implied_ids` (`odoo19/odoo/addons/base/models/res_users.py::group_ids`, `odoo/addons/base/models/res_groups.py:17`, `ResGroups.user_ids` y `odoo/addons/base/models/res_groups.py:71`, `ResGroups.all_implied_ids`). *Effect:* v18 code/XML referencing the old names breaks on v19. *Fix:* see `v19_changes.md`; use `all_group_ids` for "user's effective groups." _ES: Código o vistas que usan los nombres de campos de grupos de la v18 dejan de funcionar al migrar a la v19._
