# MRP Gotchas — Odoo 18.0
<!-- verified: v18.0 @ 2026-06 -->

**MG1. Production location is virtual** — `product.property_stock_production` (usage=`production`) is a routing abstraction. Components enter, finished products leave, but nothing sits there. Impact: never query stock at production location expecting real inventory. _ES: el stock de la ubicación de producción sale a cero o negativo y no cuadra con lo que hay físicamente en fábrica._

**MG2. Phantom BOMs explode at move confirmation, not MO creation** — Kit moves are exploded in `stock.move._action_confirm()` via `action_explode()`. The original kit move is deleted and replaced by component moves. Impact: after confirmation, kit product moves don't exist — only component moves. _ES: al confirmar la orden desaparece el producto kit y solo aparecen sus componentes en los movimientos de stock._

**MG3. _run_manufacture() merges into existing draft MOs** — Like `_run_buy()`, it searches for draft MOs with same product/BOM/company and increases qty via `change.production.qty` instead of creating a new MO. Impact: unexpected MO quantity increases when reorder rules trigger alongside existing draft MOs. _ES: la regla de reabastecimiento no crea una orden de fabricación nueva sino que suma cantidad a un borrador ya existente._

**MG4. Backorder MOs share procurement_group_id** — Partial production backorders share the same `procurement_group_id` as the original MO for traceability. Impact: group-based queries return both original and backorder MOs. _ES: al filtrar órdenes de fabricación por grupo salen mezcladas la original y su entrega parcial (backorder)._

**MG5. manual_consumption requires operator to confirm qty** — When the BoM line's `manual_consumption = True` (`mrp/models/mrp_bom.py:655-658`, `MrpBomLine.manual_consumption`), the move's `manual_consumption` is set via `_determine_is_manual_consumption(bom_line)` and the consumed quantity isn't auto-picked. Impact: with `consumption='flexible'` the move is just left un-picked; with `'warning'`/`'strict'` a mismatch is caught at `_get_consumption_issues()`. Note: a move also auto-flips to `manual_consumption=True` once a user manually edits its picked qty (`mrp/models/stock_move.py:398-400`, `StockMove._onchange_quantity`), so reservation-driven recompute stops touching it. _ES: el componente no descuenta la cantidad automáticamente y hay que confirmar a mano lo consumido en cada orden._

**MG6. unit_factor scaling produces rounding issues** — `unit_factor = product_uom_qty / ((MO.product_qty - MO.qty_produced) or 1)` (`mrp/models/stock_move.py:337`, `StockMove._compute_is_done`) scales consumption proportionally; `should_consume_qty = (qty_producing - qty_produced) * unit_factor` rounded to the move UoM (`:360`). With fractional quantities and UOM conversions, rounding accumulates. Impact: last backorder may have slightly wrong component quantities. _ES: en fabricaciones parciales con decimales las cantidades de componentes salen ligeramente descuadradas por redondeo en la última entrega._

**MG7. Subcontract BOMs cannot have operations or byproducts** — `@api.constrains('operation_ids','byproduct_ids','type')` `_check_subcontracting_no_operation()` raises `ValidationError` if a `type='subcontract'` BoM has any `operation_ids` OR `byproduct_ids` (`mrp_subcontracting/models/mrp_bom.py:24-27`, `MrpBom._check_subcontracting_no_operation`). Impact: byproducts from subcontractors need workarounds (separate product or manual stock adjustment). _ES: no deja guardar la lista de materiales de subcontratación si tiene operaciones o subproductos._

**MG8. Subcontracting changes move location silently** — `_action_confirm()` changes receipt move's `location_id` from supplier to subcontracting location when a subcontract BOM is detected. Impact: custom code checking `move.location_id` after confirmation sees the subcontracting location, not the supplier. _ES: tras confirmar una recepción subcontratada la ubicación de origen cambia sola y ya no aparece el proveedor._

**MG9. Kit cost distributed via cost_share, not proportionally** — Kit cost goes to components based on `bom_line.cost_share` percentage, not by value or quantity. Impact: if cost_share is unconfigured, all cost may go to one component — always set it on all BOM lines. _ES: el coste del kit se reparte mal entre componentes y todo el importe cae en uno solo si no se configura el porcentaje._

**MG10. Production cost = components + operations + extra_cost** — `_cal_price()` sums component SVL values + workcenter time x hourly cost + `extra_cost` field. Impact: zero-duration work orders produce zero operation costs, undervaluing the finished product. _ES: el producto fabricado sale infravalorado porque las operaciones con duración cero no suman coste de mano de obra._

**MG11. WIP account entries only with real_time valuation** — WIP journal entries (component → WIP, labor → WIP, finished → stock) only exist when `product.valuation == 'real_time'`. Impact: manual valuation companies get no WIP visibility in accounting. _ES: no aparecen asientos de trabajo en curso (WIP) en contabilidad cuando la valoración no es en tiempo real._

**MG12. Multi-level BOMs need reordering rules, not just MTO** — For sub-assemblies, 0/0/1 reordering rules are preferred over MTO. MTO reserves stock for the specific parent MO. Impact: cancelled parent MO with MTO locks the sub-assembly stock; reordering rules keep it flexible. _ES: al cancelar la orden padre se queda bloqueado el stock del semielaborado por usar fabricación bajo pedido en vez de reglas de reabastecimiento._

**MG13. 2-step manufacturing creates pickings BEFORE the MO** — With `manufacture_steps = 'pbm'`, confirming an MO creates a pick-before-manufacturing transfer. Impact: MO shows "Waiting" until the component picking is validated first. _ES: la orden de fabricación se queda en espera hasta que se valida primero la transferencia de componentes (fabricación en dos pasos)._

**MG14. Subcontractor portal has very limited write access** — `mrp.production.write()` rejects any field not in `_get_writeable_fields_portal_user()` for portal users (not su), raising `AccessError` (`mrp_subcontracting/models/mrp_production.py:51-55`, `MrpProduction._inverse_move_line_raw_ids`). The whitelist is exactly `['move_line_raw_ids', 'lot_producing_id', 'subcontracting_has_been_recorded', 'qty_producing', 'product_qty']` (`:194`). Impact: custom MO fields are NOT writable by subcontractors — use move_line fields instead. _ES: el subcontratista no puede editar campos personalizados de la orden desde el portal y salta error de acceso._

**MG15. MPS skips phantom BOMs to avoid double procurement** — `mrp_mps.action_replenish()` filters out kit products; components are procured, not the kit. Impact: MPS forecasts for kit products won't generate procurement — create MPS entries for individual components. _ES: el MPS no genera abastecimiento para productos kit y hay que planificar cada componente por separado._

**MG16. Cancelling MO cascades to stock moves, not to POs/SOs** — `action_cancel()` cancels `move_raw_ids` and `move_finished_ids` but NOT the triggering SO or component POs. Impact: orphaned POs and unfulfilled SO deliveries remain and must be manually cancelled. _ES: al cancelar una orden de fabricación quedan sueltos pedidos de compra y entregas de venta que hay que anular a mano._

**MG17. Consumption='strict' blocks mismatched quantities** — `consumption` selection is `flexible`='Allowed' / `warning`='Allowed with warning' / `strict`='Blocked' (`mrp/models/mrp_production.py:233-239`, `MrpProduction.consumption`, default `flexible`). `_get_consumption_issues()` early-returns for `flexible` (`:1671`) and otherwise compares picked vs expected per product; the `mrp.consumption.warning` wizard then blocks (strict) or lets you confirm (warning). Impact: scrap during production requires `flexible` first, or the MO scrap wizard which handles it separately. _ES: no deja confirmar la orden si las cantidades consumidas no coinciden con lo previsto (consumo estricto)._

**MG18. Finished product move_dest_ids links to SO delivery** — MTO-created MO's finished move has `move_dest_ids` linking to the SO delivery move; `_trigger_assign()` auto-reserves on completion. Impact: breaking this link (delete/recreate finished move) prevents SO delivery auto-reservation. _ES: si se recrea el movimiento del producto acabado, la entrega de la venta deja de reservarse automáticamente._

**MG19. No native re-work flow** — Odoo has no built-in rework concept. Failed QC requires: scrap + new MO, or a separate "Rework BOM" taking defective product as input. Impact: rework needs manual intervention or custom module; no automatic QC-fail → production loop. _ES: no existe flujo de retrabajo nativo: recuperar producto defectuoso obliga a chatarra más orden nueva o lista de materiales aparte._

**MG20. Analytic distribution propagates from MO uniformly** — In CE, the MO's analytic distribution applies to ALL raw/finished moves — no per-component assignment. In Enterprise, work orders can have own distribution but only for labor costs. Impact: per-component tracking needs separate MOs or a `_prepare_analytic_lines()` override. _ES: la distribución analítica se aplica igual a todos los componentes y no se puede imputar coste por componente._

**MG21. extra_cost does NOT generate a separate journal entry** — `extra_cost` is added to the finished product's `price_unit` in `_cal_price()`, included in the single SVL entry. Impact: overhead isn't visible as a separate journal line — use analytic accounts or workcenter costs for separate tracking. _ES: el coste extra/gastos generales no aparece como línea de asiento separada, va mezclado en la valoración del acabado._

**MG22. Cost Structure Report requires mrp_account_enterprise** — The materials + labor + overhead breakdown report is Enterprise-only. CE has `_cal_price()` for totals but no breakdown report. Impact: CE users must build custom reports from SVLs + workorder durations. _ES: el informe de estructura de costes (materiales, mano de obra, gastos generales) no existe en Community, solo en Enterprise._

**MG23. Kit (phantom BOM) supports cross-UoM components** — Kit in Units can consume components in L, Kg, etc. The BOM line specifies the component's UoM independently; phantom explosion uses the component's UoM. Impact: standard pattern for hospitality/retail. Constraint: component UoM must be in the same category as the component product's stock UoM. _ES: un kit en unidades puede consumir componentes en litros o kilos, pero la unidad de medida debe ser de la misma categoría._

**MG24. BOM component qty can include expected shrinkage** — Set `bom_line.product_qty` higher than theoretical to account for waste (e.g., 0.28L instead of 0.25L for draft beer). Impact: simpler than inventory adjustments but less accurate — periodic inventory counts still recommended. _ES: se puede subir la cantidad de la lista de materiales para cubrir mermas, pero pierde precisión frente a inventarios periódicos._

**MG25. Procurement MOs are created as SUPERUSER** — `_run_manufacture()` creates the `mrp.production` with `.with_user(SUPERUSER_ID).sudo()` because the user triggering the procurement (e.g. a salesperson confirming an SO) may have no MRP rights (`mrp/models/stock_rule.py:79-80`, `StockRule._run_manufacture`). Impact: `create_uid` on procurement-launched MOs is the admin/superuser, not the real actor — record rules or audit logic keyed on `create_uid` see the wrong user. The `change.production.qty` wizard used to merge into a draft MO is also run as `sudo()` (`:72`). _ES: las órdenes de fabricación lanzadas por abastecimiento aparecen creadas por el usuario administrador, no por quien confirmó la venta._

**MG26. mrp_subcontracting_account splits the receipt credit into component + service lines** — On a subcontracted receipt SVL, `_generate_valuation_lines_data()` does NOT post a single credit line: it splits into `subcontract_service_cost` (the PO fee) and `component_cost` (`mrp_subcontracting_account/models/stock_move.py:15-40`, `StockMove._generate_valuation_lines_data`). With `cost_method='standard'`, `component_cost = sum(move_raw SVL values)` and `subcontract_service_cost = credit_value - component_cost`; any gap between the PO fee and standard cost lands in the **price-difference account** (`stock_input`). With fifo/average, `subcontract_service_cost = extra_cost × qty`. Impact: the finished-product valuation entry has two/three credit lines, not one; reconciling subcontracting cost requires reading both. `_should_force_price_unit()` is also forced True for `is_subcontract` moves (`:11-13`). _ES: el asiento de valoración del producto subcontratado tiene varias líneas de crédito (servicio y componentes) en vez de una sola._

**MG27. _bom_find resolves by `sequence`, not by picking_type specificity** — The domain only filters `picking_type_id in (picking_type, False)`; the actual pick is `search(order='sequence, product_id, id', limit=1)` (`mrp/models/mrp_bom.py:351-377`, `MrpBom._bom_find_domain`). Impact: a warehouse-specific BOM (picking_type set) does NOT automatically win over a generic `picking_type_id=False` BOM — if the generic one has a lower `sequence` it is selected instead. To force per-warehouse BOMs, give the specific BOMs a lower `sequence` than the fallback. _ES: se selecciona una lista de materiales genérica en vez de la específica del almacén porque manda la secuencia, no el tipo de operación._

**MG28. 3-step (`pbm_sam`) MOs produce to `sam_loc_id`, not Stock** — With `manufacture_steps='pbm_sam'`, `move_finished_ids.location_dest_id = sam_loc_id` (post-production staging), and a push rule (`sam_type_id`) moves it sam_loc → Stock afterwards. Impact: after `button_mark_done` the finished product is NOT in Stock and not available for delivery/sale until the Store Finished Products transfer is validated. `move_dest_ids._trigger_assign()` (MG18) fires only after that final SAM transfer is done, not at MO completion. _ES: tras terminar la orden en tres pasos el producto acabado no está disponible para venta hasta validar la transferencia final a stock._

**MG29. MPS replenishment ignores lead/produce delays (`skip_lead_time=True`)** — `mrp.production.schedule.action_replenish()` runs procurement with `with_context(skip_lead_time=True)` (`odoo_enterprise/18/mrp_mps/models/mrp_mps.py::action_replenish`), so generated MOs/POs use the period `date_planned` directly without subtracting `produce_delay`/supplier lead time (`mrp_mps/models/stock_rule.py:13`, `StockRule._make_po_get_domain`). Impact: MOs/POs planned from MPS are scheduled at the start of the demand period as-is — actual procurement that needs lead time may already be late. Manual reordering rules (which DO subtract lead time) behave differently from MPS for the same product. _ES: las órdenes planificadas desde el MPS salen tarde porque no restan el plazo de fabricación ni de proveedor._

**MG30. Finished product cannot also be a byproduct of its own BoM** — `_get_moves_finished_values()` raises `UserError("You cannot have %s as the finished product and in the Byproducts")` if `product_id` appears in `bom_id.byproduct_ids` (`mrp/models/mrp_production.py:1225-1226`, `MrpProduction._get_moves_finished_values`). Impact: you cannot model "produce N of X plus a few extra X as byproduct" on one BoM — the extra yield must be handled via a different product/variant or by adjusting `product_qty`. _ES: no deja poner el mismo producto como acabado y como subproducto de su propia lista de materiales._

**MG31. `button_mark_done` sets un-consumed moves to `done` with qty 0, it does NOT cancel them** — at mark-done, raw/finished moves still in a non-`done`/`cancel` state are written to `state='done', product_uom_qty=0.0` rather than cancelled (`mrp/models/mrp_production.py:2135-2138`, `MrpProduction.button_mark_done`). The code comment is explicit: this is so that if the user later edits the (locked-then-unlocked) MO and sets a consumed qty, the move lines are not lost. Impact: a "completed" MO can carry zero-qty done component moves — reports/automations that count `move_raw_ids` filtered only by `state='done'` will include components that were never actually consumed; filter on `quantity`/`picked` too. _ES: una orden terminada arrastra movimientos de componentes en estado hecho con cantidad cero que falsean los informes de consumo._

**MG32. Backorder pop-up is governed by `picking_type_id.create_backorder`, not by the user** — in `pre_button_mark_done()`, quantity-to-backorder issues are routed by the operation type's `create_backorder` field: `'ask'` shows the backorder wizard, `'always'` silently creates the backorder via `button_mark_done(skip_backorder=True, mo_ids_to_backorder=...)`, `'never'` marks done with no backorder (`mrp/models/mrp_production.py:2253-2269`, `MrpProduction.pre_button_mark_done`). Impact: if a manufacturing operation type is set to `always`/`never`, partial productions backorder (or don't) with no operator prompt — surprising when migrating from another WH where it was `ask`. _ES: en fabricaciones parciales no aparece el aviso de entrega pendiente porque lo decide el tipo de operación, no el usuario._

**MG33. Marking an MO done with `qty_producing == 0` triggers mass-produce / auto-fill, not an empty close** — in `pre_button_mark_done()`, an MO whose `qty_producing` is zero is sent to `_auto_production_checks()` → either `_set_quantities()` (auto-fills full qty) or `action_mass_produce()` (`mrp/models/mrp_production.py:2235-2246`, `MrpProduction.button_mark_done`). Impact: you cannot "mark done with nothing produced" by leaving `qty_producing` at 0 expecting a no-op — Odoo assumes you meant to produce the full ordered quantity (or opens mass-produce). To truly produce nothing, cancel instead. _ES: marcar como hecha una orden con cantidad producida cero no la cierra vacía sino que autocompleta la cantidad total o abre producción en masa._

**MG34. Subcontracting valuation forces `price_unit` and bypasses automatic raw-move valuation** — in `mrp_account`, `_should_force_price_unit()` returns True for `is_subcontract` moves (`mrp_subcontracting_account/models/stock_move.py:11-13`, `StockMove._should_force_price_unit`) and `_ignore_automatic_valuation()` returns True for any `raw_material_production_id` move (`mrp_account/models/stock_move.py:24`, `StockMove._ignore_automatic_valuation`), so component (raw) moves do NOT post their own valuation entries — their value is rolled into the finished/received product via `_cal_price` / the split receipt SVL (MG26). Impact: looking for an SVL on a raw component move of a subcontracted/manufactured MO and finding none is expected; the value moved through the production/WIP account, not via the raw move itself. _ES: no hay asiento de valoración en el movimiento de componente de una orden subcontratada o fabricada; el valor va por otra cuenta._
