# Discuss / Bus Gotchas — Odoo 18.0

<!-- verified: v18.0 @ 2026-06 -->

> BUSG1-BUSG40. Citas `path:line` verificadas contra `odoo18/addons/bus/` y `mail/models/discuss/`. Notas v19 inline donde aplica (detalle en `v19_changes.md`).

## Bus Core

**BUSG1. _sendone() defers creation until commit** — Notifications appended to `cr.precommit.data["bus.bus.values"]`, not inserted immediately (`bus/models/bus.py:117-127`, `ImBus._sendone`). El INSERT real ocurre en el hook precommit `create_bus()` (`bus/models/bus.py:134-136`, `_ensure_hooks.create_bus`) y el `pg_notify` en el hook postcommit `notify()` (`bus/models/bus.py:145-163`, `_ensure_hooks.notify`). Leer `bus_bus` tras `_sendone()` sin commit → vacío. Las notifs no llegan al cliente hasta que el COMMIT tiene éxito (`bus/models/bus.py:141-144`, `ImBus._ensure_hooks` lo documenta).

**BUSG2. PostgreSQL NOTIFY payload limit 8000 bytes** — `NOTIFY_PAYLOAD_MAX_LENGTH = 8000` (`bus/models/bus.py:31-42`, `get_notify_payload_max_length`, override env `ODOO_NOTIFY_PAYLOAD_MAX_LENGTH`). `get_notify_payloads()` (`bus/models/bus.py:67-84`, `get_notify_payloads`) parte recursivamente la lista de canales por la mitad si excede; loguea INFO (`bus/models/bus.py:150-154`, `_ensure_hooks.notify`). Un solo canal con nombre >8000 bytes NO se parte (la recursión corta en `len(channels)==1`, `bus/models/bus.py:79`, `get_notify_payloads`) → ese NOTIFY puede fallar. Cuidado con muchos canales o nombres de modelo largos en un broadcast.

**BUSG3. Deduplication window only 10 seconds** — `MAX_NOTIFICATION_HISTORY_SEC = 10` (`bus/websocket.py:259`, `Websocket.MAX_NOTIFICATION_HISTORY_SEC`). Transacciones largas (>10s) entre el `create` de la notif y el COMMIT pueden no despacharse NUNCA si el usuario recibe otra notif entre medias (`bus/websocket.py:252-258`, `Websocket`, lógica de trim en `bus/websocket.py:707-730`, `Websocket._dispatch_bus_notifications`). Crear las notifs lo más cerca posible del commit.

**BUSG4. Channel format mixing causes missed notifications** — Los canales pueden ser string, `(Model, sub)` o instancia de modelo; `channel_with_db()` (`bus/models/bus.py:57-64`, `channel_with_db`) los normaliza. `_bus_send()` exige `models.Model` y hace `assert isinstance(main_channel, models.Model)` + `ensure_one()` (`bus/models/bus_listener_mixin.py:19-21`, `BusListenerMixin._bus_send`). `_sendone()` acepta todos los tipos pero un tuple mal formado se devuelve tal cual (`bus/models/bus.py:64`, `channel_with_db`) → canal incorrecto → miss silencioso.

**BUSG5. LISTEN lost on DB reconnect** — `ImDispatch.loop()` hace `cr.execute("listen imbus")` una vez por cursor (`bus/models/bus.py:236-239`, `ImDispatch.loop`). Si la conexión cae, el `run()` captura la excepción, duerme `TIMEOUT` (50s) y reintenta (`bus/models/bus.py:256-264`, `ImDispatch.run`), pero las notifs emitidas durante la caída se pierden (no quedan en buffer tras el GC). Con multi-worker cada proceso tiene su propio `LISTEN` (`bus/models/bus.py:269`, `dispatch`).

## Websocket

**BUSG6. Subscribe REPLACES channels, doesn't add** — `ImDispatch.subscribe()` REEMPLAZA la lista entera: calcula `outdated_channels = websocket._channels - channels` y los limpia (`bus/models/bus.py:207-221`, `ImDispatch.subscribe`); `Websocket.subscribe()` hace `self._channels = channels` (`bus/websocket.py:356-358`, `Websocket.subscribe`). Segunda llamada con lista distinta elimina los canales de la primera. Hay que enviar el set completo en cada subscribe.

**BUSG7. Expired session kills connection with code 4001** — Si la sesión expira entre mensaje y dispatch → `SessionExpiredException` (`bus/websocket.py:695-701`, `Websocket._dispatch_bus_notifications`) → cierre con `CloseCode.SESSION_EXPIRED = 4001` (`bus/websocket.py:174`, `CloseCode.SESSION_EXPIRED`, manejo en `_handle_transport_error` `bus/websocket.py:636-637`, `Websocket._handle_transport_error`). Breve pérdida de mensajes durante la reconexión.

**BUSG8. Outdated worker version → clean close "OUTDATED_VERSION" (no clear error)** — OJO: el handshake del PROTOCOLO usa `SUPPORTED_VERSIONS={'13'}` → mismatch da HTTP 426 (`bus/websocket.py:897`, `WebsocketConnectionHandler.SUPPORTED_VERSIONS`, y `bus/websocket.py:1014-1015`, `WebsocketConnectionHandler._assert_handshake_validity`). Pero lo que rota en cada deploy es la versión del WORKER `_VERSION="18.0-7"` (`bus/websocket.py:908`, `WebsocketConnectionHandler._VERSION`): si el worker del navegador es viejo, el server cierra con code CLEAN + razón `"OUTDATED_VERSION"` (`bus/websocket.py:1034-1044`, `WebsocketConnectionHandler._serve_forever`), NO con close code custom (para no romper el backoff). El worker viejo se desactiva (`bus/static/src/workers/websocket_worker.js:333-336`, `_onWebsocketClose`).

**BUSG9. Closing handshake can hang up to 15s per connection** — Si no se recibe el close frame, `_terminate()` pone `settimeout(1)` y drena el socket (`bus/websocket.py:582-589`, `Websocket._terminate`); además los frames PING/CLOSE esperan respuesta hasta `TimeoutManager.TIMEOUT = 15s` (`bus/websocket.py:740,776-779`, `class TimeoutManager`). Muchas tabs cerrando → retraso de limpieza acumulado.

## Presence

**BUSG10. Guest presence es 100% capa mail, no bus** — El modelo base `bus.presence` (bus) SÓLO tiene `user_id`; el campo `guest_id` y toda la lógica guest la AÑADE mail vía `_inherit` (`mail/models/bus_presence.py:9`, `BusPresence.guest_id` define `guest_id`, `:12` índice único, `:15` constraint XOR user/guest, `:18-30` overrides `_get_bus_target`/`_get_identity_field_name`/`_get_identity_data`). El update guest sólo ocurre si mail está instalado y se llama `_update_bus_presence()` con `identity_field="guest_id"` (`mail/models/discuss/ir_websocket.py:87-99`, `IrWebsocket._update_bus_presence`, dentro de `if not self.env.user or _is_public()`). Guest cierra navegador sin disparar `on_closed` → sigue "online" hasta el GC de 12h (`PRESENCE_OUTDATED_TIMER`, `bus/models/bus_presence.py:11`, `PRESENCE_OUTDATED_TIMER`, y `bus/models/bus_presence.py:119-123`, `BusPresence._send_presence`). Si depuras presencia guest mirando sólo el módulo bus, no encontrarás nada.

**BUSG11. Multi-tab concurrent presence updates race** — Mismo usuario en varias tabs → writes duplicados a `bus.presence` → errores de concurrencia. `update_presence()` los silencia con `mute_logger('odoo.sql_db')` + captura `PG_CONCURRENCY_EXCEPTIONS_TO_RETRY` → `cr.rollback()` (`bus/models/bus_presence.py:63-78`, `BusPresence.update_presence`). El comentario del modelo lo documenta (`bus/models/bus_presence.py:14-19`, `class BusPresence`). El update de presencia puede perderse silenciosamente. **v19**: `bus.presence` eliminado, lógica reescrita.

**BUSG12. Longpolling no escribe el `last_poll` propio** — `/websocket/peek_notifications` (`bus/controllers/websocket.py:31-43`, `WebsocketController.peek_notifications`) SÍ envía las presencias ajenas perdidas (`missed_presences._send_presence`, `bus/controllers/websocket.py:39-40`, `WebsocketController.peek_notifications`) pero NUNCA llama `update_presence()`, así que NO refresca el `last_poll`/`status` del PROPIO usuario. Para eso hay ruta separada `/websocket/update_bus_presence` (`bus/controllers/websocket.py:45-50`, `WebsocketController.update_bus_presence` → `_update_bus_presence`). Cliente que sólo hace `peek` y olvida `update_bus_presence` → su presencia cae a "offline" tras `DISCONNECTION_TIMER=65s` (`bus/models/bus_presence.py:9`, `DISCONNECTION_TIMER`) aunque siga polleando notifs. Además `peek` exige `is_websocket_session` en sesión (puesto en `is_first_poll`), si no → `SessionExpiredException` (`bus/controllers/websocket.py:33-37`, `WebsocketController.peek_notifications`).

**BUSG13. im_status NO es N+1: una sola query por recordset, pero NO almacenado** — CORRECCIÓN: `res.partner._compute_im_status` (`bus/models/res_partner.py:12-23`, `ResPartner._compute_im_status`) hace UNA búsqueda `bus.presence.search([("user_id","in",self.user_ids.ids)])` para TODO el recordset, no una por partner. Mostrar 100 partners = 1 query, no 100. Idéntico en `res.users` (`bus/models/res_users.py:12-19`, `ResUsers._compute_im_status`) y `mail.guest` (`mail/models/discuss/mail_guest.py:63-68`, `MailGuest._compute_im_status`). El gotcha real: el campo NO es `store=True` (es `compute` sin store, `bus/models/res_partner.py:10`, `class ResPartner`), así que se recomputa en cada lectura no cacheada; `_invalidate_im_status` (`bus/models/bus_presence.py:106-108`, `BusPresence._invalidate_im_status`; mail añade el guest en `mail/models/bus_presence.py:28-30`, `BusPresence._invalidate_im_status`) invalida la caché ORM al cambiar el status. Partners SIN usuario → `im_status = "im_partner"` (no "offline"), partners con usuario y sin presence → "offline" (`bus/models/res_partner.py:22-23`, `ResPartner._compute_im_status`). **v19**: `im_status` ELIMINADO de `res.partner`/`res.users` del módulo bus (BUS-C01/C03) → provisto por mail/discuss.

## Channels & Messaging

**BUSG14. Member-specific broadcasts don't reach new members immediately** — El subchannel `(channel, "members")` (`mail/models/discuss/ir_websocket.py:82`, `IrWebsocket._build_bus_channel_list`) sólo alcanza a suscriptores activos. Añadir miembro y enviar de inmediato → el nuevo puede perderlo si su subscribe aún no se aplicó. **v19** renombra el subchannel a `(channel, "internal_users")` (`v19_changes.md` DISC-C05) — código que envía a `"members"` deja de llegar.

**BUSG15. Typing status has no server-side rate limit** — Server broadcasts every typing notification received. Client debounces (1s), but malicious client sending rapid updates → all relayed. DoS vector. _ES: El chat se satura o va lento cuando alguien tiene el 'está escribiendo...' disparándose sin parar; el servidor reenvía cada aviso sin ningún límite._

**BUSG16. Reaction spam via bus — no rate limit** — Adding/removing message reactions broadcasts immediately. No throttle on reaction creation. Flood = bus overload for all members. _ES: Reaccionar en masa a los mensajes sobrecarga el canal y ralentiza el chat a todos los miembros; no hay freno a las reacciones._

**BUSG17. RTC state broadcasts spike bus load** — Each camera/mic toggle → broadcast to all members. No batching. Calls with >50 people spike bus on every state change. _ES: En videollamadas grandes todo se ralentiza cada vez que alguien enciende o apaga cámara o micrófono, porque se avisa a todos los participantes._

**BUSG18. Sub-channel GC UNPINEA (no borra) miembros idle 2 días** — CORRECCIÓN: `_gc_unpin_outdated_sub_channels()` (`mail/models/discuss/discuss_channel_member.py:53`, `ChannelMember._gc_unpin_outdated_sub_channels` -` , `@api.autovacuum`) NO borra hilos: marca miembros de sub-canales (`parent_channel_id IS NOT NULL`) como des-pinneados cuando `last_interest_dt`/`create_date` del miembro Y del canal son < `now - 2 días` (`:55 outdated_dt`) y no quedan mensajes recientes. Usa `fields.Datetime.now()` (reloj del servidor app) vs timestamps en BD, todo en una query SQL → si app y BD difieren de reloj, el corte de 2 días se desplaza, pero el efecto es que el hilo desaparece del panel del usuario (unpin), NO una pérdida de datos. El hilo sigue existiendo y se re-pinnea al recibir actividad.

## Security

**BUSG19. Guest token constant-time compare but ID lookup is not** — `_get_guest_from_token()` usa `consteq(guest.access_token, guest_access_token)` (`mail/models/discuss/mail_guest.py:78`, `MailGuest._get_guest_from_token`) para evitar timing attacks sobre el TOKEN. El cookie `dgid` es `{id}|{access_token}` (nombre/separador en `mail/models/discuss/mail_guest.py:48-49`, `class MailGuest`; formateo en `mail/models/discuss/mail_guest.py:144-151`, `MailGuest._format_auth_cookie`) y el `browse(int(guest_id))` por id es SQL normal. El token sigue protegido por `consteq`; el id no es secreto. `access_token` tiene `groups='base.group_system'` (`mail/models/discuss/mail_guest.py:56`, `class MailGuest`) → sólo legible con sudo (el método lo hace, `mail/models/discuss/mail_guest.py:77`, `MailGuest._get_guest_from_token`).

**BUSG20. Channel UUID = 10 chars de alfabeto 58, con `secrets.choice` (SÍ cripto-seguro)** — VERIFICADO 2026-07: `_generate_random_token` (`mail/models/discuss/discuss_channel.py:37-41`, `Channel._generate_random_token`) hace `''.join(choice('abc…789') for _ in range(10))` sobre un alfabeto de 58 chars no-ambiguos (sin l/o/0/1). `choice` es **`secrets.choice`** (`from secrets import choice`, `:6`) — CSPRNG, criptográficamente seguro (NO `random`/Mersenne Twister). ~58^10 ≈ 2^58.6 combinaciones. El comentario del código: "enough to avoid brute force, but short enough to be shareable". Campo `uuid` size=50 con constraint UNIQUE (`:78,89`). Link de invitación: `/chat/{id}/{uuid}` (`:245`). Corrección (era falso el claim previo de "no cripto"): el token de canal SÍ usa fuente segura; el límite práctico es la longitud (~58 bits), no el generador.

**BUSG21. No per-notification authorization in bus.bus** — Authorization assumed at _sendone() caller level. If caller sends to wrong channel, no server-side check. Client-side filtering via subscription only. _ES: Una notificación acaba llegando al canal equivocado sin que el servidor lo impida; el filtrado depende solo del cliente._

**BUSG22. Guest has no logout mechanism** — Cookie-only identification. No logout endpoint. Clearing cookie client-side leaves presence online until 12h GC. No "goodbye" broadcast. _ES: Un invitado cierra el chat pero sigue apareciendo conectado durante horas; no existe manera de cerrar sesión de invitado._

## Performance

**BUSG23. is_member NO es N+1: una sola query batched** — CORRECCIÓN: `_compute_is_member` (`mail/models/discuss/discuss_channel.py:201-207`, `Channel._compute_is_member`) hace UNA `discuss.channel.member.search([('channel_id','in',self.ids),('is_self','=',True)])` para todo el recordset y luego itera en memoria. Abrir Discuss con 1000 canales = 1 query, no 1000. (El gotcha de rendimiento real está en `_search_is_member` (`:209-`), que hace una query candidata separada a propósito porque el sub-select del ORM hacía tomar mal plan a psql — pero es eficiente).

**BUSG24. Group auto-subscription SÍ es idempotente** — CORRECCIÓN: `_subscribe_users_automatically_get_members` (`mail/models/discuss/discuss_channel.py:359-365`, `Channel._subscribe_users_automatically_get_members`) RESTA los miembros ya existentes: `(channel.group_ids.users.partner_id.filtered(active) - channel.channel_partner_ids).ids`. No crea duplicados: sólo añade partners que aún no son miembros. La afirmación previa de "no comprueba membresía / duplica records" es falsa en v18.

**BUSG25. First longpoll (last=0) returns 50s buffer only** — `_poll()` con `last==0` filtra `create_date > now - TIMEOUT` donde `TIMEOUT=50` (`bus/models/bus.py:24`, `TIMEOUT`, y `bus/models/bus.py:166-170`, `ImBus._poll`). El cliente recién conectado sólo ve los últimos 50s; lo anterior se pierde. No hay catch-up para mensajes perdidos offline (usar `/bus/has_missed_notifications`, `bus/controllers/main.py:15-19`, `class BusController`, para detectar el gap).

## Nuevas (path:line verificados)

**BUSG26. `_bus_send` exige Model y ensure_one por record** — `bus.listener.mixin._bus_send` itera `for record in self`, llama `record._bus_channel()` y hace `assert isinstance(main_channel, models.Model)` + `main_channel.ensure_one()` (`bus/models/bus_listener_mixin.py:15-22`, `BusListenerMixin._bus_send`). Si el override de `_bus_channel()` devuelve un recordset vacío o multi-record → `ensure_one()` revienta. El default `_bus_channel()` devuelve `self` (`bus/models/bus_listener_mixin.py:24-26`, `BusListenerMixin._bus_channel`). En **v19** el `ensure_one()` se mueve a `_bus_send` y se añade un loop de resolución de canal en cadena (`v19_changes.md` BUS-N01).

**BUSG27. `_sendone` persiste un message con shape fijo `{type, payload}`** — El cliente SIEMPRE recibe `{"type": notification_type, "payload": message}` (`bus/models/bus.py:120-126`, `ImBus._sendone`). Confundir `notification_type` con el contenido, o esperar el `message` en la raíz, rompe el handler JS. El `payload` es lo que pasaste como tercer argumento.

**BUSG28. NOTIFY se emite contra la BD "postgres", no la del tenant** — El hook `notify()` abre cursor con `db_connect("postgres")` (`bus/models/bus.py:155`, `ImBus._ensure_hooks`) y `ImDispatch.loop()` también hace `LISTEN` sobre `postgres` (`bus/models/bus.py:236`, `ImDispatch.loop`). Por eso el canal lleva el `dbname` embebido (`bus/models/bus.py:57-63`, `def channel_with_db`): un único listener multiplexa todas las BBDD del filestore. Override `ODOO_NOTIFY_FUNCTION` (`bus/models/bus.py:28`, `ODOO_NOTIFY_FUNCTION`) si pg_notify no está disponible (ej. pgbouncer en transaction mode).

**BUSG29. `bus_bus` crece sin parar entre GCs; retención configurable** — `_gc_messages` es `@api.autovacuum` y borra `create_date < now - bus.gc_retention_seconds` (default `DEFAULT_GC_RETENTION_SECONDS = 86400` / 24h) vía `DELETE` SQL directo (`bus/models/bus.py:95-103`, `class ImBus`). Si el autovacuum cron no corre (cron deshabilitado, worker dedicado caído), la tabla `bus_bus` crece sin control — alto volumen de reactions/typing/RTC lo acelera. Ajustar con `ir.config_parameter` `bus.gc_retention_seconds`.

**BUSG30. Worker reconnect: backoff exponencial ×1.5 hasta 60s** — `websocket_worker.js`: `INITIAL_RECONNECT_DELAY=1000ms`, `connectRetryDelay *= 1.5`, `MAXIMUM_RECONNECT_DELAY=60000ms`, jitter `RECONNECT_JITTER=1000ms` (`bus/static/src/workers/websocket_worker.js:42`, `MAXIMUM_RECONNECT_DELAY`, y `bus/static/src/workers/websocket_worker.js:52-53`, `WebsocketWorker.INITIAL_RECONNECT_DELAY`, `:440-446`). Un cierre CLEAN (incl. "OUTDATED_VERSION") NO reconecta (`bus/static/src/workers/websocket_worker.js:338-341`, `WebsocketWorker._onWebsocketClose`). Por eso un deploy que sube `_VERSION` no provoca tormenta de reconexiones: los workers viejos se cierran limpios y se desactivan.

**BUSG31. SharedWorker comparte UNA conexión entre todas las tabs** — El bus usa SharedWorker cuando el navegador lo soporta (`bus/static/src/workers/websocket_worker.js:51`, `WebsocketWorker` (el comentario de clase, `:44-50`, explica el fallback)); Safari y minoritarios caen a Worker normal por tab. Con SharedWorker, todas las pestañas del mismo origin comparten 1 websocket y el `multi_tab_service` elige un main tab por leader-election sobre `localStorage` (`multi_tab_service.js`, heartbeats `MAIN_TAB_HEARTBEAT_PERIOD=1.5s`, kill old `15s`). Implicación: el conteo de "conexiones" no es por tab; y bugs de presencia/typing entre tabs suelen ser del leader election, no del bus.

## Nuevas v2 (verificadas contra capa Python, path:line)

**BUSG32. `update_presence()` hace `cr.commit()` por cada poll** — `update_presence` (`bus/models/bus_presence.py:63-78`, `BusPresence.update_presence`) NO sólo escribe: tras `_update_presence` hace `self.env.cr.commit()` explícito (`bus/models/bus_presence.py:75`, `BusPresence.update_presence`). Cada poll de presencia (cada 60s por cliente, `UPDATE_PRESENCE_DELAY`) commitea su propia transacción. Si extiendes `update_presence`/`_update_presence` para escribir otros datos, esos writes se COMMITEAN antes de tiempo. En errores de concurrencia hace `cr.rollback()` (`bus/models/bus_presence.py:78`, `BusPresence.update_presence`) — un rollback que también revierte lo que hubieras escrito antes en esa transacción. No metas lógica de negocio ahí.

**BUSG33. `_on_websocket_closed` sólo marca offline a usuarios autenticados (guest aparte)** — En bus, `_on_websocket_closed` (`bus/models/ir_websocket.py:133-135`, `IrWebsocket._on_websocket_closed`) hace `if self.env.user and not _is_public()` → marca `bus.presence.status = "offline"`. El guest NO entra por ahí: mail override (`mail/models/discuss/ir_websocket.py:100-107`, `IrWebsocket._on_websocket_closed`) lo resuelve por cookie `dgid`. PERO `on_closed` es una ruta HTTP (`/websocket/on_closed`) que el navegador llama en `beforeunload` — si el cliente muere sin enviarla (crash, kill -9, móvil suspendido), NADIE marca offline y la presencia cuelga hasta el DISCONNECTION_TIMER/GC. No es fiable como señal de logout.

**BUSG34. `_authenticate` del websocket degrada a public_user, no rechaza** — `IrWebsocket._authenticate` (`bus/models/ir_websocket.py → _authenticate`): si la sesión tiene `uid` y `check_session` falla → logout + `SessionExpiredException`. Pero si NO hay `uid` (anónimo) NO falla: hace `update_env(user=base.public_user)`. Es decir, el websocket SIEMPRE se establece (público o autenticado); la autorización real es por canal en `_build_bus_channel_list`. Un public user igualmente recibe el canal `'broadcast'` y sus `groups_id` (los del public user).

**BUSG35. El cliente sólo puede suscribir canales STRING; los de modelo los pone el server** — `_prepare_subscribe_data` (`bus/models/ir_websocket.py:92-93`, `IrWebsocket._prepare_subscribe_data`) hace `if not all(isinstance(c, str) ...): raise ValueError`. Si tu código JS intenta suscribir un canal que no sea string puro → excepción y la suscripción entera falla. Los canales `(model, id)` y `(channel, "members")` los inyecta SIEMPRE el server en `_build_bus_channel_list` según membresía/grupos (`bus/models/ir_websocket.py:58-71`, `IrWebsocket._build_bus_channel_list` + mail `:63-84`). No hay forma de que el cliente pida un canal de modelo arbitrario directamente.

**BUSG36. `last` se resetea a 0 si supera el último id del bus** — `_prepare_subscribe_data` (`bus/models/ir_websocket.py:95`, `IrWebsocket._prepare_subscribe_data`): `last = 0 if last > _bus_last_id() else last`. Tras restaurar un dump (o cambiar de BD con menos notifs), el `last` que el cliente guardó en localStorage puede ser MAYOR que cualquier id existente → se fuerza a 0 → el cliente recibe el buffer de los últimos 50s como si fuera nuevo (posible re-procesado de notifs). Relevante al clonar BD a un entorno con clientes ya conectados.

**BUSG37. Canales de presencia perdidos: ventana de 2s al suscribir** — Al suscribir a canales `odoo-presence-*`, `_prepare_subscribe_data` (`bus/models/ir_websocket.py:105-112`, `IrWebsocket._prepare_subscribe_data`) busca presencias con `last_poll > now - 2s` y las reenvía (`missed_presences._send_presence`). Esto cubre el gap entre el subscribe debounced en cliente y el subscribe real en server. Si un contacto cambió de estado hace >2s justo antes de tu subscribe, NO recibes ese estado inicial por aquí (lo verás en el siguiente cambio o vía el Store). Ventana fija de 2s, no configurable.

**BUSG38. El subchannel "members" sólo lo añaden canales DONDE eres miembro** — `member_specific_channels = [(c, "members") for c in all_user_channels if c.id not in discuss_channel_ids]` (`mail/models/discuss/ir_websocket.py:82`, `IrWebsocket._build_bus_channel_list`). `all_user_channels` viene de `search(["|",("is_member","=",True),("id","in",discuss_channel_ids)])` (`:80-81`). Es decir: si NO eres miembro de un canal, no recibes su subchannel "members" aunque conozcas su id. Para los canales pasados por id explícito (`discuss.channel_N`) recibes el canal principal pero NO el subchannel "members". Enviar a `(channel,"members")` nunca alcanza a no-miembros.

**BUSG39. `_compute_im_status` de partner reduce con preferencia a "online"** — `res_partner._compute_im_status` (`bus/models/res_partner.py:14-20`, `ResPartner._compute_im_status`): cuando un partner tiene VARIOS usuarios (multi-company / usuarios técnicos), el status del partner colapsa los de todos sus usuarios prefiriendo "online" (`status_by_partner.get(partner,"offline")=="offline" or presence.status=="online"`). Un partner con 2 usuarios, uno online y otro offline → el partner aparece "online". No refleja un usuario concreto.

**BUSG40. `bus.gc_retention_seconds` es un `ir.config_parameter`, leído en cada autovacuum** — `_gc_messages` (`bus/models/bus.py:96-103`, `ImBus._gc_messages`) lee `ir.config_parameter` `bus.gc_retention_seconds` en cada ejecución (default 86400s/24h). Bajarlo a, p.ej., 3600 reduce el tamaño de `bus_bus` pero también acorta la ventana de catch-up del primer poll para clientes que reconectan (aunque el primer poll real usa `TIMEOUT=50s`, no esta retención). Subirlo mucho con alto volumen de reactions/typing/RTC infla `bus_bus`. El borrado es `DELETE` SQL crudo por `create_date`, sin paginación → un GC sobre una tabla enorme puede ser lento.
