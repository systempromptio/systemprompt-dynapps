# ir.cron Gotchas — Scheduled Actions Troubleshooting (Odoo 18.0)

Operational troubleshooting for "the cron is active and the date passed but it does not run".
Source: `odoo/addons/base/models/ir_cron.py`, runner `odoo/service/server.py`, config `odoo/tools/config.py`.
Prefix **CRONG**. See `core.md` for the model/runner overview.

## No runner / not picked up

**CRONG1. `--max-cron-threads=0` → NO cron runner at all** — config.py:321 default 2. With 0, threaded mode spawns zero threads (`cron_spawn`, server.py:539 `for i in range(config['max_cron_threads'])` = `range(0)`) and multiprocess spawns zero `WorkerCron` (server.py:937 `while len(self.workers_cron) < config['max_cron_threads']` never enters with 0). Crons stay `active=True`, `nextcall` in the past, and NEVER run. Very common on lightweight/dev containers and on web-only frontends behind a separate cron node. Symptom: nextcall frozen in the past, lastcall never advances, no `Job ... starting` lines in the log. _ES: Ninguna acción programada se ejecuta en este servidor aunque estén activas y con la fecha pasada; el cron parece congelado y no hay nada en el log._

**CRONG2. DB not in the cron worker's database list** — Multiprocess `WorkerCron._db_list` (server.py:1248-1253): if `--database`/`db_name` is set, only those comma-listed DBs are polled; otherwise `list_dbs(True)` filtered by `--db-filter`. A DB excluded by `--db-filter` or absent from `--database` is NEVER polled → its crons never run, regardless of `active`/`nextcall`. Symptom: same DB works elsewhere; on this node nothing fires. Check the cron node's `--database` / `--db-filter`. _ES: El mismo cron funciona en otro servidor pero en este nodo no salta ninguna acción programada de esta base de datos._

**CRONG3. Code/DB version mismatch silently skips the whole DB** — `_check_version` (ir_cron.py:170-182) compares DB `base.latest_version` to code `BASE_VERSION` (ir_cron.py:20). Mismatch raises `BadVersion` → `_process_jobs` logs "Skipping database X as its base version is not Y" and returns (ir_cron.py:155-156). Happens during the migration window (new code, DB not yet `-u base`). ALL crons on that DB are frozen until versions align. Symptom: one warning line per poll, zero jobs run. _ES: Tras subir código nuevo sin actualizar la base, todos los crons se paran y aparece un aviso de que se salta la base de datos._

**CRONG4. Pending module install/upgrade blocks crons** — `_check_modules_state` (ir_cron.py:184-210): any module in state `to install/upgrade/remove` raises `BadModuleState` → DB skipped (ir_cron.py:157-158). A stuck/aborted `-u`/`-i` (a module left in `to upgrade`) freezes ALL crons. Self-heals only after the oldest ready job has waited > `MAX_FAIL_TIME` (5h, ir_cron.py:21,203) → forces `reset_modules_state`. Symptom: "Skipping database X because of modules to install/upgrade/remove" for up to 5h. _ES: Un módulo se quedó a medias instalando o actualizando y ahora ninguna acción programada se ejecuta durante horas._

## Date passed but still does not run

**CRONG5. `active=False` overrides everything** — Readiness SQL is `active = true AND (nextcall <= now ...)` (ir_cron.py:218-219). A past `nextcall` on an inactive cron is IGNORED. Reactivating may have been undone by neutralization (see CRONG14) or by auto-deactivation (CRONG6). First check: is `active` really True in the DB, not just in an unsaved form? _ES: La acción programada no salta aunque la fecha ya pasó, porque en realidad está desactivada en la base de datos._

**CRONG6. Auto-deactivated after repeated failures (NOT after N calls)** — `numbercall` no longer exists (core.md). A cron that keeps raising is deactivated only when BOTH `failure_count >= 5` AND `first_failure_date + 7 days < now` (ir_cron.py:24-26,478-484). So a job failing every minute is NOT disabled until 7 days later it also has >=5 failures; conversely 5 failures within a day do NOT disable it yet. On deactivation, `_notify_admin` only logs a warning (ir_cron.py:318-326,485-492) — no email by default, easy to miss. Symptom: cron suddenly `active=False`, log warning "has been deactivated after failing 5 times". _ES: El cron se desactivó solo de repente sin que nadie lo tocara, tras estar fallando varios días._

**CRONG7. Exception → rollback → reschedule, work lost silently** — `_callback` catches, `reset_changes()`, `cr.rollback()`, re-raises (ir_cron.py:578-582). `_run_job` maps a no-progress exception to `FAILED` (ir_cron.py:432-433); `_process_job` then calls `_reschedule_later` for BOTH `FULLY_DONE` AND `FAILED` (ir_cron.py:379-380) so on a failing run `nextcall` ADVANCES to the future AND `lastcall` is set to now (ir_cron.py:525-534) even though nothing was accomplished — the action's DB work is rolled back, only `nextcall`/`lastcall`/`failure_count`/`first_failure_date` get committed (ir_cron.py:388,498-509). IMPORTANT: a failing cron's `lastcall` advances just like a healthy one (it is NOT a success marker; the only success-only field is `failure_count` resetting to 0, ir_cron.py:493-496). So you CANNOT tell a failing cron from `lastcall` alone — check `failure_count > 0` / `first_failure_date` set, or the per-run traceback in the log. Symptom: nextcall and lastcall both advance every minute, `failure_count` climbing, data never changes, traceback per run. _ES: El cron se ejecuta cada minuto y avanza la fecha, pero los datos nunca cambian y da error en cada ejecución._

**CRONG8. No catch-up: missed slots collapse to one run (old `doall` gone)** — `_reschedule_later` does `while nextcall <= now: nextcall += interval` (ir_cron.py:521-522). If the server was down for 10 intervals, the job runs ONCE on resume, not 10 times. Crons that assumed "one execution per period" (e.g. period accruals, sequence rollovers) will MISS periods after downtime. There is no `doall` flag to force catch-up in v18. Symptom: a "daily" job that produced fewer records than days elapsed after an outage. _ES: Tras estar el servidor caído un rato, el cron diario se ejecuta una sola vez y faltan registros de los días perdidos._

## Triggers (one-shot) vs recurring interval

**CRONG9. `ir.cron.trigger` is one-shot, independent of `nextcall`** — `_trigger(at=)` / `_trigger_list` (ir_cron.py:644-703) insert `ir.cron.trigger` rows; readiness fires when `call_at <= now` even if `nextcall` is far in the future (ir_cron.py:220-224). After a successful run the consumed trigger is DELETED (ir_cron.py:536-540) and the recurring `nextcall` is recomputed. Pitfall: code paths that rely on `_trigger()` to "run now" do nothing if the trigger commit never lands (the trigger and the NOTIFY are added in `postcommit` — ir_cron.py:701-702 — so a rolled-back transaction inserts no trigger and sends no NOTIFY). Symptom: "I called `._trigger()` but nothing happened" → the surrounding transaction rolled back, or you only see it on the next regular poll. _ES: Llamé al método para lanzar el cron al instante pero no pasó nada; se ejecuta después en el ciclo normal._

**CRONG10. `_trigger` on an inactive cron drops immediate triggers** — `_trigger_list` (ir_cron.py:686-691): if the cron is `not active`, only FUTURE `at` values are kept (`at > now`); a "run now" trigger on an inactive cron is silently discarded and returns an empty recordset. Symptom: triggering a disabled cron does nothing, no error. _ES: Intento lanzar manualmente un cron desactivado para que corra ya y no hace nada ni da error._

**CRONG11. Triggers don't wake workers when PG is in recovery (replica)** — Wake-up relies on `LISTEN/NOTIFY` on channel `cron_trigger` (`_notifydb`, ir_cron.py:705-712; LISTEN in server.py:499). If the cron connection is on a read replica / cluster in recovery, LISTEN is skipped with a warning (server.py:495-501); triggers then only get picked up on the next polling sleep cycle, not instantly. Symptom: `_trigger()` works but with up to `SLEEP_INTERVAL` latency, or not at all if that node never polls the right DB. _ES: El disparo inmediato del cron tarda hasta un minuto o no llega, en un servidor con réplica de base de datos._

## Multi-worker locking

**CRONG12. SKIP LOCKED — another worker already took it (normal)** — `_acquire_one_job` uses `FOR NO KEY UPDATE SKIP LOCKED` (ir_cron.py:295). If worker B holds the row, worker A gets no row → logs "another worker is processing job X, skip" (ir_cron.py:147,231) and moves on. This is correct behaviour, not a bug — but explains "I see the job acquired by one worker and skipped by the other". Also a concurrent commit of the new nextcall surfaces as `TransactionRollbackError` → rollback + skip (ir_cron.py:142-145,299-304). _ES: Veo que un worker coge el trabajo del cron y otro lo salta; el log dice que otro worker lo está procesando._

**CRONG13. Row left LOCKED after a worker crash blocks edits/reruns** — `write`/`unlink`/`method_direct_trigger` call `_try_lock` with `FOR ... NOWAIT` (ir_cron.py:584-607,609-617,114-124). If a worker died holding the row lock (or a job is genuinely mid-execution), editing or manually triggering the cron raises `UserError` "This cron task is currently being executed and may not be modified" (ir_cron.py:605-607). Until that PG backend/transaction is gone, the lock persists and the job can't be re-acquired either. Symptom: "Record cannot be modified right now" on a cron that is clearly not running. Fix: find/terminate the stale PG backend. _ES: No puedo editar ni lanzar el cron: dice que se está ejecutando ahora mismo, aunque claramente no está corriendo._

## Neutralized / staging

**CRONG14. Neutralized DB cannot re-enable crons via side effects** — `toggle()` (ir_cron.py:634-642): if `database.is_neutralized`, it returns True WITHOUT writing `active`. On staging/neutralized copies, model-driven cron (de)activation toggles are no-ops, so a cron stays whatever the neutralize script left it (usually disabled). Symptom: flipping the source condition doesn't re-arm the cron on a staging DB. _ES: En la base de staging el cron no se reactiva aunque cambie la condición; los toggles de activación no tienen efecto._

## Timeouts / long jobs

**CRONG15. Long job killed by `--limit-time-real-cron`** — A cron thread exceeding `limit_time_real_cron` (default -1 → falls back to `limit_time_real`; config.py:364, applied server.py:460-462,803-805) is terminated. Combined with the timeout protocol: 3 consecutive timeouts (`CONSECUTIVE_TIMEOUT_FOR_FAILURE`, ir_cron.py:23,361-364) with no committed progress mark the job FAILED without executing it. Symptom: heavy cron repeatedly killed mid-run; eventually counted as failures (→ CRONG6). Fix: raise `--limit-time-real-cron`, or make the action use the progress API (`_notify_progress`) so committed batches survive and it resumes (PARTIALLY_DONE → ASAP reschedule, ir_cron.py:381-382,542-548). _ES: El cron pesado se mata a mitad una y otra vez por tiempo excedido y acaba contando como fallos._

**CRONG16. Batch cap of 10 per pass — big backlogs need multiple passes** — `_run_job` calls the action at most `MAX_BATCH_PER_CRON_JOB = 10` times per worker pass (ir_cron.py:22,421). A progress-API action with a huge backlog does 10 batches, returns PARTIALLY_DONE, and is rescheduled ASAP (ir_cron.py:381-382). It only fully drains over several passes / poll cycles. Symptom: progressive draining instead of one big run; looks "slow" but is by design. An action NOT using the progress API runs exactly ONCE per due slot (ir_cron.py:437-440), so it must loop internally or it will only process one chunk and leave the rest until next `nextcall`. _ES: El cron vacía la cola poco a poco en varias pasadas en vez de procesar todo de golpe; parece lento pero es normal._

## Tests / manual run

**CRONG17. Crons NEVER fire inside tests; `_trigger()` is a no-op in tests** — `TransactionCase`/`HttpCase` run in a single rolled-back transaction and the cron runner thread does not drive the test DB. Calling `cron._trigger()` only inserts an `ir.cron.trigger` row (in postcommit, ir_cron.py:701-702) that no runner ever consumes, and the transaction rolls back anyway. To test cron logic, call the method directly (`self.env['my.model']._cron_x()`) or `cron.method_direct_trigger()`. Symptom: "my test sets up data and waits for the cron" → nothing happens, ever. Also note `method_direct_trigger` (ir_cron.py:114-124) runs in the CURRENT cursor with NO batch loop and NO failure_count bookkeeping, so a manual/test run can pass where the scheduled run (separate cursor + commit) fails, and vice-versa. _ES: En los tests el cron nunca se dispara y esperar a que corra no sirve; hay que llamar al método directamente._

## Legacy data XML / migration

**CRONG18. `numbercall`/`doall` in data XML errors on 18+** — Both fields were REMOVED in 18.0 (still present in 17.0/16.0, `odoo/addons/base/models/ir_cron.py:67-68`, `ir_cron`). A migrated module shipping `<field name="numbercall">` or `<field name="doall">` raises `Invalid field 'numbercall' on model 'ir.cron'` at load. "Run once and disable" (`numbercall=1`) and "catch up missed runs" (`doall=True`) have NO 18 equivalent — drop the fields; for run-once use `active=False` + `_trigger()`, accept no catch-up (CRONG8). Symptom: module install/upgrade fails parsing the cron record. _ES: Al instalar o actualizar el módulo migrado falla diciendo que el campo numbercall o doall no existe en ir.cron._

## base_automation (time-based rules)

**CRONG19. Time automations share ONE cron — worst-case latency = shared interval** — All `on_time`-family Automation Rules run via `base_automation.ir_cron_data_base_automation_check` calling `_check(True)` (`base_automation/models/base_automation.py:998`, `BaseAutomation._check`). The interval is auto-tuned by `_get_cron_interval` to `min(delay)//10`, clamped to **[1 min, 4 h]** (`base_automation/models/base_automation.py:629-639`, `BaseAutomation._get_cron_interval`). So a rule can fire up to that interval LATE (the UI even warns: `_compute_least_delay_msg`, line 641). A coarse rule (e.g. "7 days before") leaves the cron at hours; a record can be processed long after its trigger date. Symptom: "my time-based automation is late by up to N minutes/hours" — by design. _ES: Mi regla de automatización basada en tiempo salta tarde, hasta minutos u horas después de la fecha prevista._

**CRONG20. Deleting/disabling the base_automation cron silently kills ALL time automations** — The cron is `active=False` by default and only armed when ≥1 time-based rule exists (`_update_cron`, `base_automation/models/base_automation.py:576-589`, `BaseAutomation._update_cron`, called on every rule create/write/unlink). If an admin deletes the cron, or it's left inactive on a neutralized staging DB (CRONG14), or no time rule exists so it was never armed, ZERO time automations run and there is no error. `_check` also swallows each rule's exception (`base_automation/models/base_automation.py:1014`, `BaseAutomation._check` try/except logs and continues), so one failing rule is invisible but does not block the others. Symptom: time-based rules across many models all silently stop. _ES: Todas las automatizaciones por tiempo dejaron de funcionar a la vez, sin ningún error, en muchos modelos._

## mail crons

**CRONG21. Outgoing email is queued, not sent — needs the mail scheduler cron** — `mail.mail` rows sit in `state='outgoing'` until `mail.ir_cron_mail_scheduler_action` runs `process_email_queue(batch_size=1000)` HOURLY (`mail/data/ir_cron_data.xml:4`, `ir_cron_mail_scheduler_action`). No cron runner / disabled cron = mail never leaves. `force_send=True` on `send_mail`/`message_post` (or calling `.send()`) bypasses the cron and sends synchronously. Fetchmail is the inverse: its cron ships `active=False` and is armed by `fetchmail.server` create/write (`mail/models/fetchmail.py:306-315`, `FetchmailServer._update_cron`); a confirmed incoming server with the cron still off (e.g. neutralized DB) fetches nothing. Symptom: emails stuck "outgoing", or incoming mail never imported, with no error. _ES: Los correos se quedan atascados en la cola de salida y no se envían, o el correo entrante no se importa, sin error._

## OCA queue_job (parallel runner, looks like a cron problem)

**CRONG22. `with_delay()` jobs stuck in PENDING forever — the jobrunner is not the cron runner** — OCA `queue_job` does NOT use `ir.cron` to execute jobs; a separate `jobrunner` daemon thread does (`queue_job/jobrunner/__init__.py:159-163`, monkey-patched into the server). If Odoo is started WITHOUT `--load=web,queue_job` (or `server_wide_modules`), the jobrunner never starts and every `queue.job` stays `PENDING` with no error and no cron warning. Diagnosing it as "the cron isn't running" wastes time — `--max-cron-threads` is irrelevant here. Symptom: `queue.job` records pile up in `pending`, cron runner is healthy, no traceback. (queue_job's ONLY ir.cron is the daily GC, `queue_job/data/queue_data.xml:10-18`, `ir_cron_autovacuum_queue_jobs`.) _ES: Los trabajos lanzados con with_delay se quedan pendientes para siempre aunque el cron funciona bien._

**CRONG23. queue_job channel capacity 0 / unreachable base URL stalls jobs** — Even with the jobrunner loaded, `ODOO_QUEUE_JOB_CHANNELS="root:0"` (capacity 0) disables dispatch ("jobrunner thread NOT started, because root channel's capacity is set to 0"). And the runner dispatches via an HTTP GET to `/queue_job/runjob` using scheme/host/port from `ODOO_QUEUE_JOB_*` / `http_interface`/`http_port` (`jobrunner/runner.py:350-376`, `QueueJobRunner.from_environ_or_config`); if that URL is not reachable from the Odoo host (reverse-proxy-only, wrong port, TLS mismatch) the callback fails and jobs stay PENDING/ENQUEUED. Symptom: jobrunner logs "starting jobrunner thread" but jobs don't progress → check channel capacity and the internal HTTP callback URL. _ES: El jobrunner arranca pero los trabajos en cola no avanzan por capacidad de canal a cero o URL interna inalcanzable._

## Access rights of the scheduler user

**CRONG24. Cron fails with `AccessError` when the scheduler user lacks rights on the action's model** — A cron runs its server action via `ir.actions.server.run()`, which enforces access BEFORE executing the body (ir_actions.py:962-989). Two paths: (a) if the action has `groups_id` set, the running user (the cron's `user_id`) must belong to one of those groups, else `AccessError` "You don't have enough access rights to run this action" (ir_actions.py:963-966); (b) if no `groups_id`, it calls `self.env[model].check_access("write")` for the scheduler user (ir_actions.py:967-975), and additionally `records.check_access('write')` on any real records the action targets (ir_actions.py:980-989). So a cron whose `user_id` is a low-privilege user (not `base.user_root`) raises AccessError on the model of `model_id` — which is then caught by `_callback` as a generic failure (rollback + re-raise, ir_cron.py:578-582) and counted toward auto-deactivation (CRONG6). Symptom: cron traceback `AccessError`/"Forbidden server action ... executed while the user X does not have access to model Y" with no functional cause; fix is the scheduler `user_id`, not the code. Note the action runs `self.sudo()` for dispatch (ir_actions.py:962) but the access *checks* use `self.env.user` = the cron's `user_id`. _ES: El cron falla con error de permisos sobre el modelo aunque el código está bien; el usuario del planificador no tiene acceso._

## More locking / toggling pitfalls

**CRONG25. Model-driven (de)activation via `toggle()` is silently SKIPPED if the cron is mid-run** — `toggle(model, domain)` (ir_cron.py:634-642) computes a boolean from a search and calls `try_write({'active': ...})`. `try_write` (ir_cron.py:619-632) grabs `FOR NO KEY UPDATE NOWAIT` inside a savepoint and, on `OperationalError` (row already locked by a running worker), `pass`es and returns `False` WITHOUT writing. So if the cron happens to be executing when the arming condition flips, the `active` change is dropped with no error and no retry — the cron stays in its previous state until the next `toggle()` call. This is by design (avoids blocking) but means cron arm/disarm via `toggle` is best-effort, not guaranteed. (Contrast `write`/`unlink`/`method_direct_trigger` which use `_try_lock` and raise a `UserError` instead, ir_cron.py:584-617,114-124.) Symptom: a cron that should have been (de)activated by a model side-effect didn't change, intermittently, under concurrency. _ES: Un cron que debía activarse o desactivarse por un cambio en un registro no cambió de estado, de forma intermitente bajo concurrencia._

## Trigger lifecycle subtleties

**CRONG26. FUTURE-dated triggers SURVIVE a regular run and fire again** — On a successful reschedule, `_reschedule_later` deletes ONLY past triggers: `DELETE FROM ir_cron_trigger WHERE cron_id=%s AND call_at < now()` (ir_cron.py:536-540). A trigger created with a future `at` (`cron._trigger(at=now+30min)`) is NOT consumed by an interval/`nextcall` run that happens in the meantime — it remains and will independently make the cron ready again when its `call_at` arrives. So `_trigger(at=future)` is an *additional* one-shot on top of the recurring schedule, not a replacement. Stale future triggers are only cleaned by the autovacuum GC after 1 week (ir_cron.py:762-768). Symptom: "the cron ran an extra time I didn't expect" → a previously scheduled future trigger fired after a normal run. Each distinct `at` you pass to `_trigger_list` is one extra execution. _ES: El cron se ejecutó una vez de más que yo no esperaba, por un disparo programado a futuro que saltó tras la ejecución normal._

## Queue ordering / starvation

**CRONG27. Failing crons sink to the BOTTOM of the ready queue (ordering is `failure_count` FIRST)** — Both `_get_all_ready_jobs` (ir_cron.py:226 `ORDER BY failure_count, priority, id`) and `_acquire_one_job` order by failure_count before priority. So a cron that keeps failing is progressively de-prioritised relative to healthy jobs — the OPPOSITE of what `priority` alone implies. Intent is to not let a flapping job hog workers, but under a saturated runner (few threads, many ready jobs) a high-`priority` job that is also failing can be starved by lower-priority healthy ones, and a chronically failing job may rarely get a worker at all (slowing its march toward the 7-day/5-failure deactivation, CRONG6). Symptom: "my priority-0 cron runs after others" — check its `failure_count`. _ES: Mi cron con prioridad máxima se ejecuta después que otros porque está fallando y baja al final de la cola._

## Polling latency (single thread)

**CRONG28. Worst-case ~60 s latency to pick up a due `nextcall` (no trigger)** — Without a trigger/NOTIFY, a cron whose `nextcall` just passed is only noticed on the next poll. Threaded mode sleeps `SLEEP_INTERVAL + number` seconds per thread (`SLEEP_INTERVAL = 60`, server.py:65,505) plus a `number/100` jitter (server.py:506); multiprocess `WorkerCron` sleeps `SLEEP_INTERVAL + pid%10` only once it has cycled all DBs (server.py:1225-1228). So with `--max-cron-threads=1` and no NOTIFY (e.g. PG replica, CRONG11), a job due at T runs at up to T+60s. `nextcall` is therefore a "not before" time, never an exact-fire time. Symptom: "my cron is consistently ~1 min late" — that's the poll interval, not a bug; use `_trigger()` for immediacy. _ES: El cron llega siempre con cerca de un minuto de retraso; es el intervalo de sondeo, no un fallo._

## v17 / v19 diffs

Full version map (incl. v17's removed `numbercall`/`doall` and the v19 runner refactor) is in
**`v19_changes.md`**. The short of it for troubleshooting:

- **v17→v18**: `numbercall`/`doall` REMOVED (CRONG18); auto-deactivation moved from call-counter to
  failure-based; `failure_count`/`first_failure_date`/`ir.cron.progress`/progress protocol ADDED.
  Runner topology unchanged.
- **v18→v19**: same field set, same deactivation thresholds, same SKIP-LOCKED + neutralize guard +
  LISTEN/NOTIFY → **ALL CRONG gotchas above hold in v19**. Behaviour-relevant changes: batch cap
  `MAX_BATCH_PER_CRON_JOB=10` → time/run budget `MIN_RUNS_PER_JOB=10` + `MIN_TIME_PER_JOB=10s`
  (CRONG16 reasoning changes: judge draining by wall-clock, not iteration count);
  `_notify_progress` deprecated → `_commit_progress`. Refactor-only (matters for overrides):
  methods `@staticmethod`, `_process_jobs`→`_process_jobs_loop`, `_get_ready_sql_condition`,
  `_acquire_one_job(..., include_not_ready=False)`, `_check_modules_state` keyed on
  `max(nextcall, write_date)`, `reset_modules_state` in `odoo.modules.loading`, `WorkerCron` uses a
  notify-aware `deque` instead of round-robin `db_index`.
