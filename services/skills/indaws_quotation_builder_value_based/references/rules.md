# Complete rules — quotation-builder-value-based

**This file is the single source of truth for the rules.** `SKILL.md` carries the non-negotiables
(`## Important`) and a short operational digest (`## Key rules`) that points here; everything else
lives below. Deliberately **no rule count is quoted anywhere** — the list grows, counts rot.

## Model principles

1. **Closed price per app** — a card with included features, NOT hours
2. **Core absorbed** — Core modules included in the base do NOT appear as a cost line
3. **Configuraciones Generales (General Configuration) always included** — 500€ minimum base, NOT deselectable
4. **±15% adjustment** — free for the sales rep. >15% requires management approval
5. **Complements with ⚙️** include a Dynapps Core module (invisible to the client)
6. **Single interactive list, live price** — apps + support + developments + value-added in a single block with a live TOTAL; the sales rep builds it WITH the client and **the price IS shown** (in `live`). No Recommended/Custom concept

## Rules

1. **The client NEVER sees hours** — neither in Excel (Propuesta sheet), nor in the PDF, nor in the cards. **The price IS shown** (single interactive list, `live` mode)
2. **Core absorbed** — Core modules included in the base do NOT appear as a separate cost line
3. **±15% adjustment** — the sales rep can adjust freely. >15% is highlighted in orange and requires a flag
4. **Config General and Salida a producción (go-live / production rollout) always included and NOT deselectable** — Config General (500€ minimum base); Salida a producción (10% of the implementation PRICE — config + apps + selected developments — plus analysis; includes support, migrations and training)
5. **Custom developments are selectable** — they appear in the single list as selectable items with their price; their PRICE DOES count toward the 10% support figure (as in the E36 sheet row), even though it is not part of the "apps base"
6. **Validate before filling in** — ALWAYS present a summary and wait for confirmation before writing to the spreadsheet
7. **Spanish context** — If products are searched in Odoo, ALWAYS use `context: {"lang": "es_ES"}`
8. **Don't make up data** — If the intake data doesn't have enough info, ask the sales rep. Don't assume complements without clear signals
9. **Correct template** — The quote MUST use the "Implantación v2" template so the spreadsheet exists. Its **id is discovered by name at runtime** (`scripts/odoo_discovery.py`) and is **never hardcoded**: on the `master`/`es` DB it happens to be 15, but another operator's Odoo will differ
10. **Substring matching** — `fill_spreadsheet.match_extra()` looks up extras by partial match: exact equality, then containment **in both directions**, and finally a **20-character prefix heuristic when the candidate name is longer than 10 characters**. Consequence: a **new add-on name must not collide** with an existing one (a shared 20-char prefix is enough to match the wrong row). Verify names whenever an extra doesn't activate
11. **Real personalization of the HTML** — each app must mention concrete client data (number of users, warehouses, revenue, pain points) both in `intro` and in each `feature`. Generic plain text = rejected proposal
11.b. **`app_overrides.features` is MANDATORY** — write 1-2 personalized sentences for each spreadsheet feature. If only `intro` is set and `features` is omitted, the features come out as plain text and the proposal ends up generic
12. **Quantities in `por_unidad` extras** — Use the `"Name:N"` format in `extras_activos` (e.g. `"Multi-compañía:5"` for 6 companies = 5 additional). The skill multiplies price × quantity
13. **Salida a Producción support = 10% DYNAMIC of the PRICE** — included and NOT deselectable; **replicates the sheet (Interna Comercial E36 -> F36)**: amount = `ROUND(0.10 × (analysis + selected Config + selected apps + selected developments), 0)`, and the line's own internal hours are derived from that € like any other line (`ROUND(€ × factor / rate, 1)`). **Price base, not hours**, so the line is INVARIANT to the productivity factor: deriving it from factored hours made lowering the factor cut the PRICE, handing the client the gain that must be margin (measured on PR4086: 0.92 -> 0.70 discounted 203 €). **Recalculates live** when toggling apps/devs. Includes "support, migrations and training". The sales rep does NOT duplicate this line manually.
14. **Value-added / AI block** — fixed catalog (MCP/Starter mutually exclusive, Payroll/Delivery-Note OCR, conditional CRM/Field Service, POC, on-site presence), all **unchecked by default**; conditional items (305, 288, 212) are hidden if their app is not selected. **Training: 2h per session** wherever sessions are mentioned
15. **dev_overrides mandatory** — In `extra_data.json`, write a specific description for each development (based on the intake data / RFP). The generic fallback is not acceptable in a professional proposal
16. **Recurring costs** — Read from `Interna Comercial` rows **60, 61, 62** (column A title, column B formatted price). If those cells contain unevaluated `=ODOO.LIST(...)` formulas (typical when the sale.order has no lines with `recurring_invoice=True`), the script discards them and uses `RECURRENT_DEFAULTS` (Dyn Cloud 1,080€/year, Maintenance 360€/month, Odoo License 334.80€/user·year = Custom, yearly, list price; Standard 178.80 is the sanctioned alternative). **Light User** (4.90€/user/month) is never a `costes_recurrentes` card: its own annual line comes from `num_usuarios_light` (Gotcha 12b). To use client-specific values, pass them in `extra_data.json` as `costes_recurrentes: [{"title": "...", "price": "...", "desc": "..."}, ...]` — this overrides the spreadsheet values
17. **Subtotals in the template (internal)** — The "Implantación v2" template keeps subtotals in rows 39-42 (`SUM(...)` that tolerates empty cells). These are internal spreadsheet names (not client-facing, since the client only sees the single list); the skill does NOT rebuild these formulas
18. **Client-first ordering (v5)** — fixed section order in web and PDF: hero → understanding ("What you told us": context + ambition only) → challenges (max 4) → comparable cases (proof) → solution map → timeline → apps → Why Dynapps (3 pillars + figures band) → team → investment (+ added value) → **the calendar, together (AFTER pricing)** → closing. Problems are listed ONCE, in the challenges section — never repeated in the understanding opener. In the PDF, methodology + timeline merge into one "How we deliver it" section. Full table in `references/html_structure.md`
19. **2-step workflow with STOP** — STEP 3 (fill in the spreadsheet + update order lines) **must stop** and wait for the sales rep's confirmation before continuing to STEP 4 (draft content + generate HTML). The sales rep reviews the spreadsheet in Odoo and can adjust it manually
20. **HTML naming** — `propuesta-pr<NUM>.html` in lowercase (e.g. `propuesta-pr3722.html` for sale.order PR3722). The generator only writes it locally; **publishing it and registering it on the `sale.order` is STEP 5's job** (see SKILL.md §STEP 5 and `workflow_detail.md` §STEP 5) — the older "publishing is decided outside the skill" wording is obsolete
21. **Self-contained files** — `generate_proposal.py` embeds Readex Pro and the Dynapps logos as base64 data URIs → the web HTML is a single file with no external resources. The PDF is rendered with headless Chrome from the `-pdf.html`. Suitable for local download, the Odoo portal, external hosting or email attachment
22. **Dynapps brand + dual output** — the proposal follows `common-skills:dynapps-brand` (Readex Pro; pure brand palette with extended digital tokens — Midnight Denim #050543, Unicorn Violet, Ferrarri Carmine, Sunset Tangerine —; brand-guideline 45° gradient violet → carmine at 52% → orange #FF7759; central mindmap node = Odoo purple #714B67). **In prose the brand is always written "Dynapps" (capital D)** — the all-lowercase form only exists inside the logo artwork, never in text. Web adds the dark glass top nav and the dark footer with the gradient line. The skill ALWAYS delivers TWO files from the same `extra_data.json`: a rich interactive web HTML (glassmorphism, mindmap, flow, single list with a live TOTAL) + a **static print-perfect PDF** that replicates the web's visual language (cards, subtotals, dark total panel; body = ONLY what's selected, including the selected AI items; no showcase appendix). Requires Google Chrome / Chromium installed for the PDF
23. **The same `extra_data.json` feeds both** — `mode` (`predemo`|`live`), `apps_recomendadas`, `understanding`, `executive_summary_html`, `pain_points`, `cost_of_delay`, `anchor_dates`, `app_overrides`, `dev_overrides`, `costes_recurrentes`, `equipo`, `casos_exito` and `sector_glossary` are used identically in web and PDF. Validate the JSON with the sales rep ONCE; there's no need to maintain content per format
24. **Official Odoo icons per app** — each active app is rendered with its official Odoo icon (in `assets/odoo-icons/`, embedded as a data URI) in the web cards, the PDF cards and the mindmap nodes. The name→file mapping lives in `APP_ICON_FILES` (`generate_proposal.py`); apps without a mapping fall back automatically (initial/bar). NEVER use emojis or generic icons instead of the official ones. Details in `references/html_structure.md`
25. **Team and success cases are optional and hidden without data** — `equipo` (ask the sales rep for names → `fetch_team.py` pulls photo+role+email from `hr.employee`) and `casos_exito` (Dynapps catalog / cases_library) only render if present. NEVER make up client photos, names or results
26. **Output modes** — `mode` controls the document: `predemo` (no prices, for the demo) or `live` (single interactive list with real prices; built live with the client and is the source for the PDF; default). **The price IS shown to the client in `live`** — *this SUPERSEDES the old "Golden Rule 3"* which prohibited showing the price in writing. The `proposal` (ranges) and `close` modes, and the Recommended/Custom concept, are removed. Future migration = 15% of (selected apps+devs) / 24 €/month (cycle renewal every 2 years)
27. **Zero brochure adjectives + mechanical style rules** — short sentences, concrete numbers. Forbidden: "innovative/leading/cutting-edge/end-to-end/360 solution". Test: if any competitor could sign the sentence, delete it. Talk about the client 2:1. Sentence-case capitalization — **no all-caps anywhere, not even via CSS `text-transform`** (v5, overrides the old "CSS eyebrow caps" doctrine). **No em-dashes (—)**; an en-dash (–) is only valid inside numeric/date ranges ("S12–S14", "jul–ago"). **One language per document** — no language leaks (per-pack denylist). **Register per pack**: es keeps professional "tú" (untouched), nl uses je/jij, fr uses vous. Use `sector_glossary` (the sector's language, not Odoo jargon). Validate with `scripts/brand_lint.py` (v2 checks: DASH, MARCA, IDIOMA, REGISTRO, PRESION, plus warn-only EXCL/PASIVA) — on the JSON and, with `--html`, on the rendered output
28. **Metric-first cases with a link** — the number goes first; cases from the Dynapps catalog (`cases_library.json`, includes ES cases). **Links ALWAYS point to the Dynapps cases website**, never to the Odoo backend. The URL is composed **per locale** by `match_cases.py` as `instance.cases_base_url` + the case's `slug`; the shared `_base_url` in `cases_library.json` (production `https://www.dynapps.es/en/cases` — the temporary November Five URL is retired, `_base_url_TEMP: false`) is only the fallback when the active pack declares no `cases_base_url`
29. **Team from Odoo** — photo/role/`work_email` come from `hr.employee` as-is. Do NOT rewrite the email domain: if it must be `@dynapps.es`, the employee changes it in the Odoo backend
30. **Sticky navigation on the web** — the web HTML automatically renders a sticky side index with scroll-spy + progress bar (only present sections, hidden below 1280px). Web only; the PDF doesn't have it. Requires no action from the sales rep
31. **Default contact and brand** — `extra_data.contacto` defaults to Dynapps (info@dynapps.es · www.dynapps.es · 960 202 942). Recurring hosting cost = "Dyn Cloud". The closing section shows the sales rep's photo (when available) and the next-step line — **never a phone number**
32. **Max 4 challenges** — the challenges section renders at most 4 pains. The cap is enforced at data level (the engine warns on stderr): with more than 4, MERGE related pains into one, don't drop context. Fewer, sharper challenges read as understanding; a laundry list reads as templated
33. **Quotes are never invented** — a case card carries a client quote ONLY if that quote genuinely exists on the Dynapps market site (scraped with provenance by `fetch_references.py`). No quote → the card leads with a factual headline (metric/result). Same for logos: real logo when available, the client name as text otherwise — never a fabricated logo or testimonial
34. **Mutual commitment AFTER pricing** — "The calendar, together" (anchor dates) always renders after the investment block, never before. Commitment is only credible once the client has seen the number. Urgency is framed as **planning transparency** (how our team-assignment calendar works), never as sales pressure (`brand_lint.py` PRESION check)
35. **verify_totals gate is mandatory** — after generating ANY client-facing HTML (web in STEP 4, PDF-source in STEP 5.2), run `scripts/verify_totals.py --html <rendered> --extra-data <extra.json>` (add `--ss/--toma` when available for the exact-match model). It recomputes the recurring totals with the same engine and hard-FAILS on summary-vs-detail drift (the PR4021 bug class). Do not deliver on FAIL
