# Client documentation — the question is wired, the layout is not decided

Documentation written **for a client**: their own how-tos, onboarding, the
documentation of what we implemented for them.

> **There is no house layout yet, and the old one is not it.** What exists today
> under CLIENTES grew by sedimentation — inconsistent names, a per-deliverable
> skeleton that belongs to an implementation project rather than to a client — and
> it is being replaced. Nothing of it should be taken as the standard.

## What to do meanwhile

1. **Do not reuse the internal five blocks.** They answer a question a client
   never asks (which department owns this) and they would have to be undone later.
2. **Say the layout is not defined yet**, agree the shape with the user for this
   specific document, and author that.
3. Everything that is **not** structure still applies: the rules of form and the
   metadata conventions are found the usual way (`../knowledge-as-source.md`),
   because those are about how a document is written, not about where it sits.

## What is still open, and blocks deciding it

- **Whose is the documentation, the project's or the client's?** If it belongs to
  the project it dies when the project closes and the client is left with nothing;
  if it belongs to the client, something has to say what happens when the second
  project contradicts the first.
- **Access.** Client documentation nobody can navigate to is not documentation.

When it is decided, the layout lands in Knowledge tagged like the rest, and the same
query finds it. This file stays a pointer to the question, never a copy of the answer.
