# Weekly report — sales team tracking

Deterministic 2-step pipeline. **The format is frozen**; only the data (and the team) change on
each run.

**Output language**: everything the agent produces for the user (the executive PM analysis, chat
summaries, findings) MUST be written in the user's language unless they ask otherwise. The
script-generated dashboard HTML currently renders its labels in Spanish (the team's working
language) — known limitation tracked in the suite's IDEAS.md.

## Setup (first run per user)

Plugin: the skill folder is a read-only cache; state lives in the WORKDIR
(`$HOME/dynapps-informes/team-weekly-report/`, override with `TEAM_REPORT_DIR`). If the credential is
missing, the refresh stops asking for `<WORKDIR>/config.local.sh` with `ODOO_KEY="..."`
(+ optional `DEFAULT_TEAM="Tokyo"`) — ask the user for their Odoo API key and create it. The API
user needs the **Time Off Officer/Administrator** role to see the whole team's vacations.

## Picking the team (before running anything)

1. If the user named the team ("informe de Mónaco") → pass it as the argument.
2. If they did NOT and `DEFAULT_TEAM` exists in the WORKDIR's config.local.sh → use it, no question.
3. If they did NOT and there is no default → **ask with AskUserQuestion** (typical options:
   Tokyo · Mónaco · Servicios).

The name is resolved against `crm.team` by "ASCII skeleton" (lowercase, accents stripped):
"monaco", "Mónaco" and "MONACO" all match. If nothing matches, the script lists the available teams
and exits (exit 2) — show them to the user.

## How to run it

Scripts live in the skill's `scripts/`; STATE (data/, snapshots/, reports/, fotos/, credential)
lives in the **WORKDIR** `$HOME/dynapps-informes/team-weekly-report/` (override with
`TEAM_REPORT_DIR`). The skill produces **TWO deliverables**:
1. **Data dashboard**: `reports/seguimiento_<team>_<date>.html` (generated by the scripts).
2. **Executive PM report**: `reports/analisis_pm_<date>.html` (written by the agent, see the
   framework below).

Full flow when the skill is invoked:

```bash
# Step 1 — refresh Odoo data + generate the dashboard + open it (team optional if DEFAULT_TEAM set)
bash <skill-dir>/scripts/team_report.sh "Mónaco"
# Step 2 — analytical digest (exact figures to ground the analysis; uses the team from step 1)
bash <skill-dir>/scripts/pm_digest.sh
```

**Step 3 (done by the AGENT, not a script):** with the digest from step 2, write the executive PM
report and save it to `reports/analisis_pm_<date>.html` following the framework in the
**"Executive PM report"** section. Then open it with `Start-Process`. (The analysis requires
judgment → it cannot be automated in bash; Claude produces it when running the skill.)

Regenerate the dashboard only, without touching Odoo (after a format change; uses the last
refreshed team):

```bash
bash <skill-dir>/scripts/gen_team_report.sh
```

## Requirements

- `curl`, `awk`, `base64`, `date` (git-bash) and PowerShell to open the HTML.
- **`<WORKDIR>/config.local.sh`**: `ODOO_KEY="..."` required (without it the refresh stops with an
  actionable `:?` message) and optional `DEFAULT_TEAM="Tokyo"`. Host/DB defaults:
  `ODOO_URL=https://portal.dynapps.es`, `ODOO_DB=master` (JSON2 / Bearer) — overridable via
  environment.
- The API user needs the **Time Off Officer/Administrator** role to see the whole team's vacations.

## GOTCHAS

1. **Credential**: ONLY via environment or the WORKDIR's `config.local.sh` — never in the repo.
2. **Host**: the backend is **portal.dynapps.es**. If a query returns 0/empty, suspect the host
   (a 302 redirect) before the key.
3. **TEO**: the Dashboard CONTROL sheet (doc 5800) is the SINGLE source; the manual CSV diverged
   twice (Aitana 65→125, Claudia 125→100). Guard: <3 rows → previous CSV kept.
4. **Discarded UI** (do not reintroduce): ⓘ icons on KPIs and visible lists under the KPIs ("looks
   horrible"); a tandems/support-by-month table under the 8-month chart ("doesn't convince me" ->
   replaced by the per-consultant striped view); a separate go-live strip above the vacation gantt
   ("uglier" -> the ▼ row lives inside the table); the "HOY" chip on the vacation axis; colored
   pill for the Media 3m column (read as another month -> plain bold number). Everything goes in
   tooltips + collapsed disclosures.
5. **account.move team_id is NOT reliable** (Tokyo invoices show up as Paris/INDAWS) → collections
   are ALWAYS resolved through the milestones→sale.order→account.move chain, never by invoice team.
6. **awk**: BEGIN/END-only programs need `/dev/null` as input (they hang otherwise); never reuse
   arrays as scalars; the Bash tool mangles inline backslashes → write awk programs to files.
7. **Stages**: execution = stage_id `[1,2,6,7,11]`; **To Do and Análisis are "waiting"** and are
   EXCLUDED from billing/plan-vs-real (user decision, not an oversight).
8. **Accents**: gawk does NOT tolower/toupper non-ASCII ("Mónaco"→toupper→"MóNACO"): ALWAYS
   transliterate first (gsub ó→o) — that's why team matching uses an ASCII skeleton and the TEO
   block is compared de-accented. And NEVER send an accented name through `ilike` in the JSON
   domain (console encoding breaks it): fetch the full list and match locally.
9. **Snapshots per team** (`snap_<slug>_<date>.csv`): +pp deltas only compare within the SAME team;
   the first report of a new team shows "no deltas" (normal).
10. **HITO_ALIAS is per team**: only Tokyo has the 1103:988 case (Prosersa←Eurolotes inheritance);
    other teams get an empty value unless overridden in config.local.sh.
11. **CRM won/lost = `won_status`, never the stage NAME nor "archived = lost"**: both heuristics
    shipped in v2.2.0 and both leaked (a stage renamed "Adjudicado" counted as open; a lead
    archived mid-flight counted as a lost deal). `crm.lead.won_status` is stored/computed
    (`crm/models/crm_lead.py:613-620`, `CrmLead._compute_won_status`, v19 @d1d161033) and is the column both consumers read. It is **19+ only**
    — fine here (`/json/2/` already is), portable equivalent = `crm.stage.is_won`.
