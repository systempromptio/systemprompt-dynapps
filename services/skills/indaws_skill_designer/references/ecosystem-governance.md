# Ecosystem Governance

Rules for managing skills across 7 suite repositories.

## Suite Responsibilities

| Suite | Scope | Rule |
|-------|-------|------|
| ai-claude-common | Shared by 2+ roles | If more than one role needs it, it goes here |
| ai-claude-developer | Code-writing skills | Only skills that produce/modify source code |
| ai-claude-consultant | Implementation skills | Client-facing project work |
| ai-claude-hr | People operations | Employees, leaves, recruitment |
| ai-claude-management | Executive/reporting | Payroll, billing, workload monitoring |
| ai-claude-marketing | Marketing ops | Campaigns, SEO, content, events |
| ai-claude-sales | Sales pipeline | CRM, demos, proposals, outreach |

## Routing Decision Tree

When creating or moving a skill:

```
1. Does it produce/modify source code?
   YES → developer (unless needed by consultants too → common)

2. Is it client-project specific?
   YES → consultant

3. Is it people/HR specific?
   YES → hr

4. Is it CRM/sales specific?
   YES → sales

5. Is it marketing-channel specific?
   YES → marketing

6. Is it executive reporting?
   YES → management

7. Used by 2+ of the above?
   YES → common
```

## Duplicate Prevention Protocol

Before creating a new skill:

1. Run `detect_duplicates.py` to check name and description similarity
2. Check CATALOG.md of the target suite AND common
3. If a similar skill exists in another suite:
   - Same purpose → extend existing, don't create new
   - Overlapping purpose → discuss with the owner suite first
   - Different purpose, similar name → rename to be distinct

### One-creator rule (base ⇄ domain)

There is **ONE** module scaffolder: `odoo-module-creator`. Any app/domain-specific skill
is a **`-developer` (domain) layer** that delegates the skeleton to that base — see
`references/shared/base-domain-delegation.md`. Do **NOT** create new `-creator` skills
that re-implement scaffolding (manifest, security, multi-company, README, icon, tests): that
reintroduces duplication. A skill named `*-creator` other than `odoo-module-creator` is a smell
— rename to `*-developer` and make it delegate. (Precedent: `odoo-carrier-creator` →
`odoo-carrier-developer`, 2026-07.)

## Cross-Suite Dependencies

Two types of dependencies:

### Vertical (common → child suites)
Every suite depends on common. This is mandatory — common provides infrastructure, knowledge, and connectors.

### Horizontal (child suite ↔ child suite)
Child suites are **peers that see each other**. They can discover skills via CATALOG.md and delegate to them. The mechanism is **delegation by skill name**, not code import.

Examples:
- Consultant delegates code audit to developer's `odoo-code-auditor`
- Sales delegates migration analysis to developer's `odoo-database-upgrader`
- Marketing references consultant's project context

### Rules:
1. **Common dependencies are vertical** — always available, declared as "Vertical" in DEPENDENCIES.md
2. **Cross-suite dependencies are horizontal** — declared as "Horizontal" in DEPENDENCIES.md
3. **3+ suites need it → move to common**. 2 suites → delegate horizontally. 1 suite → keep local
4. **Delegation, not duplication** — invoke the skill by name, don't copy its code or references
5. **CATALOG.md is the discovery mechanism** — check all catalogs before creating a new skill
6. A skill should work standalone if optional dependencies are unavailable (graceful degradation)

## Change Impact Protocol

When modifying a skill in common:

1. Check which suites declare it as a dependency (grep DEPENDENCIES.md files)
2. Verify the change doesn't break consumers
3. If it's a breaking change (renamed function, removed field, changed output format):
   - Bump the major version
   - Update all consumer DEPENDENCIES.md files
   - Notify suite maintainers

## CATALOG.md Lifecycle

Each suite has a `CATALOG.md` at its root:
- Auto-generated by `generate_catalog.py`
- Regenerate after adding, removing, or renaming a skill
- Other skills use CATALOG.md to discover what's available

## DEPENDENCIES.md Structure

Each suite has a `DEPENDENCIES.md` with 3 sections:

```markdown
# {suite-name} — Dependencies

## Vertical (from common)
| Local skill | Depends on | Purpose |
|-------------|-----------|---------|
| skill-a | odoo-pilot | API connection |

## Horizontal (from other suites)
| Local skill | Delegates to | Suite | Purpose |
|-------------|-------------|-------|---------|
| my-tester | odoo-code-auditor | developer | Audit code issues |

## Optional
| Local skill | Uses if available | Purpose |
|-------------|-------------------|---------|
| * | indaws-project-setup | PROJECT_REGISTRY context |
```

## Workflow: Add a New Skill

1. **Discover:** Read CATALOG.md from ALL suites — check nothing similar exists
2. **Route:** Use the decision tree above to pick the target suite
3. **Layer:** If target is common, determine layer (0-3) from ARCHITECTURE.md
4. **Create:** Generate SKILL.md + folder structure with: frontmatter (name, version, description, model, effort), workflow with agent routing, GOTCHAS, NEVER/ALWAYS, REFERENCES
5. **Shared patterns:** Reference `common:references/shared/` for connection, batch, fields — don't reimplement
6. **Dependencies:** Add entries to the target suite's DEPENDENCIES.md (vertical from common + horizontal to peers)
7. **Catalog:** Run `generate_catalog.py` on the target suite
8. **Plugin manifest:** Update target suite's `.claude-plugin/plugin.json` — bump skill count in `description`, add keyword if relevant
9. **Validate:** Run `validate_ecosystem.py` to confirm no errors

## Workflow: Move a Skill Between Suites

1. **Copy** the skill directory to the target suite's `skills/`
2. **Delete** from the source suite's `skills/`
3. **Update CATALOG.md** of both suites (run `generate_catalog.py` on each)
4. **Update DEPENDENCIES.md** of both suites + any suite that referenced the skill
5. **Grep all SKILL.md files** across ALL suites for references to the moved skill — update paths/names
6. **Plugin manifest:** Update `.claude-plugin/plugin.json` of BOTH suites — adjust skill counts and keywords
7. **Validate:** Run `validate_ecosystem.py` and `detect_duplicates.py`

## Workflow: Impact Analysis (before modifying a common skill)

1. **Grep DEPENDENCIES.md** across all suites for the skill name → list vertical consumers
2. **Grep all SKILL.md files** across all suites for horizontal delegations referencing this skill
3. **Classify change:** breaking (major version bump) vs compatible (minor/patch)
4. If breaking: list all consumers, propose migration plan

## Agent Routing (model selection per phase)

Every skill must declare which model runs each phase. See `agent-routing-patterns.md` for the full reference.

**Quick rules:**
- `effort: low` → entire skill runs as `Agent(model: sonnet)`. Example: `/git`, `/docker`
- `effort: medium` → orchestrator (opus) delegates mechanical phases to sonnet subagents. Example: `module-creator`
- `effort: high` → opus runs everything. Example: `database-upgrader`, `flow-tester`

**Phase classification:**

| Phase type | Model | Examples |
|-----------|-------|---------|
| Gather info, read files | sonnet | Read registry, ask user, collect paths |
| Design, architecture | **opus** | Model design, trade-offs, security analysis |
| Generate code | **opus** | Write models, views, security rules |
| Validate, lint, check | sonnet | Naming, imports, structure, coverage |
| Git/Docker/shell ops | sonnet | Commit, push, build, deploy |
| Delegate to other skills | sonnet | Call test-generator, quality-gate |

**CRITICAL:** `model: sonnet` in frontmatter does NOT route to sonnet in slash commands. The SKILL.md must contain explicit `Agent(model: sonnet)` instructions for each delegated phase.

### La delegación se escribe CONDICIONAL, nunca obligatoria (regla de ecosistema, 2026-07-31)

Un paso no puede marcarse `[MANDATORY SUBAGENT]`. Hay entornos donde el subagente **no está
disponible**: una configuración global que prohíbe el fan-out, un pre-flight de contexto en rojo, o
el usuario pidiéndolo expresamente en esa invocación. En esos casos el paso obligatorio no se
ejecuta — y no se ejecuta **en silencio**, que es lo peor: la skill cree que tiene `SCAN_RESULT` y
no lo tiene.

**Medido, no supuesto.** En 15 sesiones de un proyecto real (`dynapps_ai`, 30-31 jul 2026)
`odoo-module-creator` se invocó **5 veces** y hubo **4 subagentes en total** contando todos los
motivos: sus tres pasos `[MANDATORY SUBAGENT]` se saltaron **las cinco veces**. Una instrucción
obligatoria que se incumple siempre enseña a ignorar las obligatorias de esa skill.

**Cómo se escribe entonces.** Tres piezas, siempre las tres:

1. **La regla real**, que casi nunca es «usa un subagente» sino *«no lo hagas de memoria»*:
   `NEVER trabajes de memoria: o lo trae un subagente, o lo lees/scripteas tú — nunca lo inventas.`
2. **La condición explícita** para delegar: pre-flight en verde **y** trabajo no mecánico
   (`grep`/AST/inventario/formato es mecánico → **se scriptea**, no se reparte).
3. **El camino inline**, dicho: `si no se cumplen las dos, haz el paso inline y dilo`.

Marca los pasos `[SUBAGENTE SI PROCEDE — si no, inline]`, y en la tabla *Delegates to* pon
«Subagent **si procede**, si no inline» en vez de «(mandatory)».

**Aplica también a esta meta-skill**: `skill-designer` tiene pasos de subagente y tampoco son
obligatorios. Predicar la regla sin aplicársela es la vía rápida a que no se crea ninguna.

## Plugin Manifest (plugin.json)

Each suite has `.claude-plugin/plugin.json` — the Claude Code plugin descriptor.

### When to update

| Event | What to change |
|-------|---------------|
| Add skill | `description` (skill count +1, add name), `keywords` (add if new term) |
| Remove skill | `description` (skill count -1, remove name), `keywords` (remove if orphaned) |
| Rename skill | `description` (old name → new), `keywords` (old → new) |
| Revamp suite | `version` bump, rewrite `description` with accurate count and grouping, refresh `keywords` |

### When NOT to update

Content changes within existing skills (workflow, references, frontmatter, GOTCHAS) do NOT require plugin.json changes. Only **inventory changes** (add/remove/rename) and **version bumps** trigger an update.

### Format

```json
{
  "name": "{suite-id}-skills",
  "version": "MAJOR.MINOR.PATCH",
  "description": "Skills (N) for {team}: {category} ({skill-list}), ...",
  "author": { "name": "...", "email": "..." },
  "repository": "git@github.com:...",
  "skills": "./skills",
  "license": "PROPRIETARY",
  "keywords": ["odoo", "{domain}", ...]
}
```

### Rules
1. `description` must start with `Skills (N)` where N is the actual count
2. Group skills by category in the description — matches CATALOG.md sections
3. Keep `keywords` under 25 terms — one per skill concept, not per skill name
4. Bump `version` following semver: MAJOR for restructure, MINOR for skill add/remove, PATCH for metadata fixes

## Version Conventions

- `MAJOR.MINOR.PATCH` (semver)
- MAJOR: breaking changes to output format or workflow
- MINOR: new features, new references
- PATCH: fixes, gotcha updates, token optimization
- Every skill MUST have a version in frontmatter

## Enabled-Skill Ceiling & Skill Packs

Context degrades when too many skills are *enabled at once* (Anthropic guidance: re-evaluate past ~20-50 simultaneously enabled). Every enabled skill's name+description sits in the system prompt permanently, and a crowded field makes triggering noisier. For a large ecosystem (100+ skills across suites):
- Users should enable the suites relevant to their role, not all of them — a developer doesn't need the marketing suite enabled.
- Group tightly-related skills into **skill packs** (a suite IS a pack) so enablement is per-pack, not per-skill.
- When auditing, if a single role would need 50+ skills enabled, that's a signal the suite is doing too much — consider splitting or making some skills on-demand rather than always-enabled.

## Ecosystem Health Checks

Run periodically:
1. `validate_ecosystem.py $SKILLS_ROOT` — full linter
2. `detect_duplicates.py $SKILLS_ROOT` — cross-suite duplicates
3. `generate_catalog.py` on each suite — keep catalogs fresh
4. Verify `plugin.json` skill counts match actual `skills/` directory contents
5. Sanity-check enabled-skill count per role against the ceiling above
