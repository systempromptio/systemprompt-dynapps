# Technical Design Standard — Contract and Rubric

This is the canonical definition of a good `technical-design.md` working copy
in the OpenSpec `feature` workflow. The judge uses it to score a candidate.
It is intentionally explicit and self-contained: do not assume the judge has
any ambient project knowledge beyond this standard, the inlined SOURCES, and
  the CONTEXT (the source packet, discovery / design / proposal, the APPROVED
  grooming ledger, this change's delta specs — the `specs.<flow>/…` blocks —
  and, when present, `stories` and the FSD/ISD working copy). FSD/ISD are the
  signed requirements interpretation when present; specs are the structured
  OpenSpec projection for trace/scenarios/tasks.

This judge scores ADHERENCE to the contract (this STANDARD plus the schema
instruction the generator was given), grounded in CONTEXT and using the GOLDEN
only as a non-exhaustive positive example. It does NOT score architecture
quality: elegance, optimality, depth, or whether a stronger design exists are
never findings. The generator runs on a weak model, so the only question is
whether the candidate FOLLOWED the contract — not whether the architecture is
the best possible.

SOURCE AUTHORITY IS PER-DIMENSION, not a single linear ladder: each upstream is
the source of truth for ITS dimension — signed FSD/ISD for the approved
WHAT/intent (primary and highest for what the system must do); specs for the
executable behaviour and RQ/WBS trace (the structured projection of that signed
WHAT, and the trace canon tasks build on); the APPROVED grooming ledger for
decisions and approvals; design for HOW / architecture rationale (never an
independent requirements source); proposal for scope and offer; discovery for
provenance and sources. Priority is NOT a reading restriction — the candidate
may draw on any upstream, and citing a lower-authority source for HOW, scope, or
provenance is correct. A finding requires a lower-authority source OVERRIDING
signed FSD/ISD, specs, or approved grooming on a conflict, never mere use of it.

## What a technical design is (essence)

- The technical design is the FIRST Dev Planning artifact, generated by
  `/opsx:plan` after the BA/SA phase completed and the Grooming Approval
  Gate passed. It owns the developer-level HOW and is the source of
  implementation detail for `tasks.md`. It is an internal engineering
  document — never published to the client.
- It is the pipeline's implementation architecture and phased delivery plan —
  the one artifact allowed to introduce new implementation identifiers: route
  files, component/module names, cartridge names, internal service and cache
  partition names, representative paths/config keys. Those identifiers are its OWN synthesis;
  they are judged for internal consistency, trace, and fitness — never for
  absence from CONTEXT or GOLDEN. The boundary is WHO codes against the
  name: what only the implementation sees is its own to choose, while the
  interface a CONSUMER codes against (the exposed endpoint namespace/path,
  response field names, error/status shape) and every magnitude (TTL,
  quota, limit, timeout) are NOT its to invent — each is sourced,
  inherited from an approved decision, or deferred to an Open Question.
- What it must NOT do: redefine signed behaviour (FSD/ISD when present,
  projected into delta specs for structured trace/scenarios), re-decide
  architecture (design.md decisions are locked and get referenced, not
  reopened), or absorb BA scope changes (a question that changes agreed
  scope goes back to proposal/grooming as a CR, never answered here).
- It opens with two orientation blocks DERIVED from the body — a **Technical
  Design Overview** reader-map and a **Technical Design Source Inventory**. The
  Overview (written last) orients a reader — an LLM first, a human second — to
  what the design settles at implementation level, why it is shaped that way,
  what constrains downstream `tasks.md`, and what is passed forward as OPEN
  questions, by SUBJECT and COUNT; it never re-lists the tables below and never
  claims approval. The Source Inventory lists every upstream this plan consumes
  (discovery, design, proposal, grooming, specs always; stories/FSD/ISD when
  present), each mapped to its authority-role planning use.
- Planning-stage grooming lives inside it: TECHNICAL unknowns discovered
  while planning the HOW go into "Open Questions", tagged CRITICAL
  (tasks built on the wrong answer would need rework) or NICE-TO-HAVE, each
  with an owner. Open Questions is the single home for a question AND its
  resolution: on fresh generation each question is OPEN with an EMPTY
  "Approved by" cell, carrying the agent's RECOMMENDATION in its
  "Recommendation / Decision" cell — no approved answer is recorded yet; the
  same cell records the approved decision in a later human approval session.
  The Planning Gate blocks `tasks.md` while a CRITICAL question is open; it
  never blocks generating this document.
- When `stories` exists in CONTEXT, the document preserves the delivery
  grouping: EVERY story key and title appears in the "Delivery Inventory"
  Story cells mapped to spec trace, classification, and implementation
  areas. Stories are delivery slices only — never a behaviour source.
- It also owns the delivery SEQUENCING: "Delivery Phases" cuts the change
  into increments that each close as something a shopper or a consuming
  feature can observe or call, so `tasks.md` groups work under phases
  instead of inventing its own order. The phase plan is the artifact's own
  synthesis over the delivery units CONTEXT gives it (story keys when
  stories exist, otherwise the in-scope RQ/WBS units); how many phases,
  what they are called, and how they are ordered is planning judgement,
  not a value to be matched against any example.
- The flow shapes the content, not the laws: a functional change may plan
  frontend surfaces with no SFCC backend work, an integration change may
  plan backend/service work with no storefront routes. An inapplicable
  sub-section keeps its template table with a single "None — <grounded
  reason>" row (dashes in the other cells) — that row is correct planning,
  not a gap and not placeholder filler.

## Invariants the candidate MUST satisfy

1. **Trace coverage (closed law).** Every requirement in THIS flow's delta
   specs (each `### Requirement:` with its RQ/WBS trace, including MODIFIED
   and REMOVED sections) appears in a Delivery Inventory Spec trace cell
   with an implementation area or explicit DEFERRED classification, and
   every planned area traces back to spec requirements. Specs are judged as
   the structured projection of the
   signed FSD/ISD scope when FSD/ISD exists, not as permission to invent
   behaviour absent from the signed requirements. Implementation Building
   Blocks carry trace references that cover the in-scope requirements;
   Verification Strategy is DEVELOPER-owned verification only, so it traces
   the requirements that HAVE developer-owned proof — a requirement whose
   only proof is functional/QA (E2E, manual QA, accessibility audit, UAT) is
   covered in Delivery Inventory and Building Blocks and correctly carries NO
   Verification Strategy row. A requirement deferred by the approved lock is excluded
   from planning (a DEFERRED inventory row or note is correct). Every story
   key/title appears exactly once in Delivery Inventory mapped to spec trace
   — a dropped or invented story key is a violation, and omitting the
   Delivery Inventory section is the same violation in bulk.
2. **Behaviour fidelity.** No signed FSD/ISD requirement, spec SHALL, or
   spec scenario is contradicted, weakened, or extended: the data flow's
   branches restate the signed requirement interpretation through the
   structured spec scenarios; approved grooming bounds stay intact (e.g.
   regular hours only, permanent — not temporary — redirect, server-side
   geocoding, lazy map). Implementation choices may STRENGTHEN a bound (a
   tighter privacy posture); they may never relax one or invent new
   shopper-facing behaviour. If FSD/ISD, specs, proposal/stories, grooming,
   or design disagree on signed behaviour, the correct candidate surfaces
   an upstream sync defect instead of silently choosing or synthesizing.
3. **Decision fidelity.** APPROVED grooming decisions and locked design.md
   decisions are honoured and referenced, not re-decided; no rejected or
   undecided alternative is asserted as the approach. design.md is
   architecture working material — solution shape, rationale, PoC notes,
   integration shape, risks, and low-level constraints — not an independent
   requirements source. A choice upstream defers to technical design goes
   through the planning-question cycle: on fresh generation it appears as
   an OPEN question carrying the agent's recommendation in its Recommendation
   / Decision cell; it is never silently asserted as settled, and never
   re-raised when grooming already approved an answer.
4. **Planning ownership.** Content is developer-level HOW: implementation
   architecture surfaces, building blocks, interfaces, runtime flows, and
   verification strategy with trace. Planning questions are TECHNICAL
   unknowns with severity and owner; a BA-scope item framed (or answered)
   as a planning question is a violation. Implementation choices with more
   than one viable option either follow an upstream constraint, or appear
   as a planning question — never as a silently asserted magnitude.
   Deferral law: when the sources explicitly defer a choice to technical
   design ("settled in technical design", an open TTL/cache lifetime, an
   unpublished interface contract consumers build against), the document
   must either decide it (only where no human call is needed) or raise it
   as an OPEN planning question. An EMPTY Open Questions table
   while the sources carry such deferral markers is a violation — as is
   the claim that "everything was settled in grooming". A consumer-facing
   interface contract (endpoint namespace/path, response schema other
   changes and tests build against) that upstream leaves unpublished is
   always a human-call choice: silently asserting it instead of raising
   it is a violation.
5. **Fresh planning state.** Open Questions are OPEN with empty "Approved
   by", each carrying the agent's recommendation in its "Recommendation /
   Decision" cell; no question is recorded as approved (no APPROVED /
   DEFERRED-APPROVED status, no filled "Approved by", no approver / session /
   approval date recorded in the Recommendation / Decision cell); no claim
   that the gate passed; no `- [ ]` checkbox task queue (that is `tasks.md`,
   generated later).
6. **No fabrication.** RQ/WBS codes, story keys, people, tracker ids,
   vendor contract facts (endpoints, fields, mappings), and magnitudes
   (TTLs, quotas, limits, budgets) are closed-world: they trace to CONTEXT.
   An undecided magnitude is raised as a planning question ("TTL per Q2"),
   never asserted as a value. Implementation identifiers are exempt — they
   are the artifact's own synthesis.
7. **Implementation specificity.** Each applicable template section is
   filled with developer-HOW rows (not restated requirements or
   hand-waving) — judged for HOW-presence per the instruction, not for
   architectural quality or optimality; inapplicable sub-sections carry the single grounded
   "None — <reason>" row. Cross-cutting rows conform to design.md where
   it constrains them.
8. **Delivery phase decomposition.** "Delivery Phases" plans how the change
   is delivered in verifiable increments, and it is total over the delivery
   units: every story key (or, when no stories exist, every in-scope RQ/WBS
   unit) is accounted for exactly once — inside a phase row, as a
   cross-cutting obligation the other phases carry, as a seam folded into
   the phase that first consumes it, or as scope the approved lock defers.
   Each phase is a VERTICAL increment: when it closes, a shopper or a
   consuming feature can observe or call something new. Each phase row
   carries acceptance coverage — the behaviour branches it proves, including
   the permission, error, privacy, and negative branches its requirements
   carry — the implementation areas it touches, its dependencies, and a
   verification that could actually prove it done. Shared scaffolding (a
   route shell, a capability seam, a helper module) is folded into the first
   phase that consumes it, never scheduled as a standalone foundation phase
   that delivers nothing consumable; cross-cutting obligations
   (accessibility, localization, privacy, security) are carried by every
   phase for the surface it adds, never postponed to a final clean-up phase.
   Phase count, names, ordering, dependency graph, and granularity are the
   artifact's own synthesis: a small change delivered in two phases is as
   correct as a larger one in seven.
9. **Template & structure conformance.** Template section order and heading
   levels; the source-inventory/inventory/questions/building-block/verification tables with their
   columns; Runtime Flows rendered as mermaid sequence diagram(s) per the
   template (participants are the planned implementation actors; alt
   branches for permission/error/cache paths); Delivery Inventory always
   present, using story cells when stories exist and "—" Story cells when
   planning directly from RQ/WBS. A deterministic code gate already enforces
   exact section presence and order against the golden; score this
   dimension for heading, table-shape, and diagram-shape fidelity only.

## Forbidden (each is a critical finding when present)

- A dropped in-scope spec requirement (no Delivery Inventory Spec trace /
  no planning coverage) or a dropped story key when stories exist; a
  phantom RQ/WBS or story key absent from CONTEXT.
- A contradicted, weakened, or extended behaviour: planning that shows
  holiday hours in v1, a temporary redirect, an eagerly-loaded map, a
  feature-held vendor key, a browser-visible key on a server-side path,
  coordinates persisted or sent to analytics, or any new shopper-facing
  behaviour absent from specs.
- A re-decided or contradicted locked/approved decision, or a rejected
  alternative asserted as the approach.
- A BA-scope change answered or decided in planning (new scope, changed
  agreed behaviour) instead of pushed back as a CR.
- A self-approved or inferred-approval planning decision: any "Approved by"
  value or APPROVED / DEFERRED-APPROVED status on fresh generation, an invented
  approver/date, OR a question whose "Recommendation / Decision" cell records an
  APPROVED answer (a decision, not a recommendation) by INFERRING approval from
  a source document, meeting note, design prose, or the agent's own
  recommendation — approval exists only when a named human approves in the
  session, which does not happen on fresh generation. (A recommendation in that
  cell on an OPEN question is the REQUIRED fresh state, not an approval.)
- An asserted undecided magnitude: a concrete TTL, quota, limit, or budget
  value the sources do not state (raising it as a question is correct).
- A deferral-law breach (ONE critical per document): the sources carry
  explicit deferred-to-technical-design sentences or unpublished
  consumer-facing contracts, and the candidate neither raises them as
  OPEN questions nor cites a source for the values it asserts instead —
  including the literal empty or placeholder-only questions table and
  the "nothing remains open / all settled in grooming" claim.
- A fabricated closed-world fact: vendor endpoint/field beyond the design's
  contract, invented RQ/WBS/story key, person, tracker id, or URL.
- A horizontal phase plan: phases that are layer or task buckets ("data
  layer", "add the service definition", "wire up the components", "write
  the tests") instead of increments that close as something observable or
  callable — including a standalone foundation/scaffolding phase that
  delivers nothing consumable on its own, and a trailing "accessibility",
  "localization", "privacy", or "hardening" phase that postpones an
  obligation every phase must carry.
- A delivery unit dropped from or invented in the phase plan: an in-scope
  story key (or in-scope RQ/WBS unit when no stories exist) that appears in
  no phase row and under no cross-cutting / folded-seam / prerequisite /
  deferred classification, or a phase claiming to deliver a story or RQ
  absent from CONTEXT.
- A phase row that cannot be proven: no acceptance coverage (it never says
  which behaviour branches the phase proves) or no verification (it never
  says how the phase is shown done). A phase whose Verification names only
  developer-owned evidence (unit/integration tests, dev checks) IS proven —
  the functional/QA proof being out of scope is not "no verification".
- Internal leakage: agent/process commentary, project-context wrappers,
  eval-harness references.
- A missing mandatory element: no Delivery Inventory table, no Implementation
  Building Blocks table, no Verification Strategy, no Delivery Phases section, or a missing
  Open Questions section.

## Judging method (apply before scoring)

Judge each claim by what is actually wrong with it, and record it in ONE
place.

- Artifact presence (run FIRST): if the candidate is not a technical-design
  working copy at all — a refusal or STOP message, a status report, an
  onboarding summary, planning notes, or an empty document — record the
  critical finding `no_artifact`, score EVERY dimension 0.0, and stop. A
  missing-upstream complaint is never valid: the upstream artifacts are
  given in CONTEXT.
- GOLDEN is a non-exhaustive positive EXAMPLE, not an answer key. A
  difference from GOLDEN — different file paths, different component or
  cartridge names, different question numbering or wording, different
  diagram splitting, more or fewer table rows — is NEVER by itself a
  finding. Every finding MUST quote the candidate text AND the STANDARD
  rule or CONTEXT fact it violates.
- Deterministic structure ownership: section presence, section order, and
  table column headings are enforced by the structure gate. If Structure
  gate is PASS, do NOT record any finding or warning about a column heading
  being singular/plural, differently punctuated, or not matching the
  template. The gate already compared it exactly; an LLM column nit after a
  passing gate is invalid.
- Technical Design Overview (derived reader-map — judge under
  `structure_conformance`). The Overview sits at the top and is DERIVED from
  the finished body; derive its correct content from the body, never from
  GOLDEN's wording. It orients a reader to what the design settles at
  implementation level, why it is shaped that way, what constrains downstream
  `tasks.md`, and what is passed forward, by SUBJECT and COUNT (e.g. "seven
  vertical phases", "two open questions, one CRITICAL"). Stating a subject and
  a count is the intended reader-map shape. Two defects only: a count or claim
  the body CONTRADICTS (e.g. "five phases" when the body carries seven) is a
  `structure_conformance` deduction — and a fresh-document Overview that CLAIMS
  approval or names an approver is a `fresh_planning_state` critical, not a
  reader-map nit; RE-LISTING the Delivery Inventory rows, phase names, or
  building blocks, restating a section, or dumping implementation detail into
  the Overview is a reader-map warning. Prose that agrees with the body is
  correct however worded; a plainer or richer phrasing than GOLDEN's is never
  a defect.
- Golden-anchor filter (apply to EVERY candidate finding before recording
  it): name the authority the finding rests on. If that authority is a
  GOLDEN row, module, question, test, or diagram the candidate lacks —
  and no CONTEXT sentence or STANDARD law independently REQUIRES that
  element — the finding is invalid: drop it or record it as
  `missing_evidence`, never as a critical. "The golden plans X and the
  candidate does not" is a description of the golden, not a violation.
  Only three omission families may ever be critical, and all cite CONTEXT
  or the STANDARD, not GOLDEN: a trace-law breach (a spec requirement
  heading or story key in CONTEXT with no row), a phase-coverage breach (a
  CONTEXT delivery unit with no phase row and no explicit classification),
  and a missing mandatory element (no Delivery Inventory, no Implementation
  Building Blocks, no Verification Strategy, no Delivery Phases, no Open
  Questions section).
- Closed-world vs open-world. Signed FSD/ISD requirement meaning (when
  present), spec RQ/WBS codes, story keys, behaviour bounds, approved
  decisions, people, tracker ids, vendor contract facts, and magnitudes are
  CLOSED-world: they must trace to CONTEXT. Implementation identifiers
  (route files, components, modules, cartridges, internal service and cache
  names, config keys), area naming and grouping, table granularity, diagram
  layout and splitting, question numbering, and prose wording are OPEN-world
  synthesis: judge them for grounded, consistent, traceable planning —
  never for verbatim presence anywhere. The consumer-facing interface
  contract and magnitudes are NOT open-world synthesis — they fall under
  the decision-layer boundary above.
- Trace sweep (closed rule — run BEFORE scoring `trace_coverage`): list
  every `### Requirement:` heading across THIS flow's delta spec files
  (ADDED / MODIFIED / REMOVED sections; cross-cutting requirements such as
  privacy or accessibility count) with their RQ/WBS, and the story keys
  when stories exist. Treat specs as the structured projection of FSD/ISD
  when FSD/ISD exists; if the candidate notes a real FSD/ISD-vs-spec sync
  conflict, judge the stop/question as correct instead of forcing it to
  choose. Diff the candidate's Delivery Inventory against those inventories.
  Fire a critical only on: a missing in-scope requirement, a phantom
  requirement or story, a dropped story, or planning content for a
  requirement the approved lock defers. Row COUNT, grouping, and repeated
  RQ ids across rows (one per spec requirement) are never findings when the
  mapping is total.
- Behaviour sweep (closed rule — run BEFORE scoring `behaviour_fidelity`):
  test every behavioural assertion (tables, diagram messages, notes)
  against signed FSD/ISD requirement meaning when present, the delta specs
  as structured projection, and approved grooming bounds. Fire on
  contradiction, weakening, or extension — not on compression, and not on
  an implementation choice that satisfies or strengthens the bound.
- Decision sweep (closed rule — run BEFORE scoring `decision_fidelity`):
  test placement/caching/security/performance statements against APPROVED
  grooming decisions and locked design.md decisions. Design is architecture
  working material: it may constrain HOW, integration shape, and lower-level
  technical choices, but it cannot add or reinterpret requirements absent
  from signed FSD/ISD + specs. Deciding something design explicitly deferred
  to technical design is CORRECT ownership, not a violation; deciding
  something grooming/design already decided differently is the violation.
- Deferral proof gate (closed rule — run BEFORE scoring
  `planning_ownership`, and record its output in your reasoning):
  1. Enumerate from CONTEXT every sentence containing "technical design" /
     "technical-design" that defers a choice to this artifact, and every
     undecided magnitude or unpublished consumer-facing contract the
     sources leave open. Quote each verbatim. SCOPE the set by what each
     deferral's RESOLUTION names: a deferral — even a design/grooming
     Planning Deferral PD# — whose resolution is pure internal wiring (no
     consumer-facing contract, no magnitude, no human-call choice: how a
     vendor bundle loads or is version-pinned, which module owns a seam, how a
     flow is wired) is CORRECTLY decided inline in the architecture and is NOT
     an open deferral — the GOLDEN itself decides such a PD# inline and raises
     no question for it, so its absence from Open Questions is never a breach.
     Only deferrals carrying a Bucket-B value or contract (a caching strategy /
     TTL / cache lifetime / quota, an endpoint namespace/path, a
     request / response / error schema) or a choice that needs a human call are
     the closed set this gate tests.
  2. Enumerate the candidate's Open Questions rows and every
     concrete magnitude/contract value the candidate asserts (TTLs,
     quotas, endpoint paths, response fields).
  2b. Exclusion filter (apply to EACH candidate value BEFORE step 3 — a
     value that matches ANY of these is NOT an asserted-magnitude breach,
     because the candidate handled it exactly as the contract requires):
     - It is the text of an Open Question the candidate RAISES
       ("What TTL should cached responses use?", "What quota…?"). Raising
       a magnitude as an OPEN question is the REQUIRED behaviour — never
       fire "asserted magnitude" on a question row. A mis-severity here
       (CRITICAL vs NICE-TO-HAVE) is at most a warning, never a critical.
     - It carries a grounded deferral note ("TTL per Q3", "contract per
       Q1", "per Q#") AND a matching question row exists — the value is
       deferred, not asserted. (A dangling "per Q#" with NO matching
       question IS a defect, but a fresh-state/planning-ownership warning
       about the missing row, not an asserted-magnitude critical.)
      A deferred cell may still name the category being deferred (endpoint
      namespace/path, request fields, response schema, error shape, cache
      lifetime, TTL) so the reader knows what Q# governs. Those category
      words are NOT asserted values. Only a concrete path, field name,
      schema, TTL, quota, or cache dimension that remains after this
      matching-Q# filter survives to step 3.
     - It is a decision GROOMING or design APPROVED (e.g. the server-proxy
       geocoding approach, the domain-restricted key posture) — asserting
       an approved decision is CORRECT inheritance (see the Decision
       sweep and allowed patterns d/j). A missing `grooming Q#` citation
       on an approved decision is a warning, never a deferral-law critical.
       Only a magnitude/contract value that NO source states AND that
       grooming/design did NOT approve survives to step 3.
  3. Judge the diff both ways over the values that SURVIVE 2b: a CONTEXT
     deferral with no question row AND no cited source for an asserted
     value is ONE critical (the deferral law); an asserted value no source
     states is a critical (asserted undecided magnitude) recorded ONCE
     even when the value appears in several cells. Count the deferral-law
     breach ONCE per document, not once per missed question.
  The law tests the candidate against CONTEXT deferrals — never against
  the GOLDEN's question list, ids, wording, or count. "Empty questions
  table" findings are valid ONLY when the table is literally empty or
  placeholder-only; a non-empty table with wrong/missing questions is
  judged by the same diff, phrased for what it actually is.
- Phase decomposition gate (closed rule — run BEFORE scoring
  `phase_decomposition`, and record its output in your reasoning):
  1. Enumerate the delivery units from CONTEXT: every story key when
     `stories` exists, otherwise every in-scope RQ/WBS unit in this flow's
     delta specs. Mark the units the approved lock defers.
  2. Enumerate the candidate's phase rows — what each claims to deliver,
     its acceptance coverage, its areas, its dependencies, its verification
     — plus every row or sentence classifying scope as cross-cutting, as a
     seam folded into a phase, as a prerequisite, or as deferred.
  3. Justify coverage both ways: each enumerated unit sits in exactly one
     phase row or carries an explicit classification, and each phase row's
     claimed unit exists in CONTEXT. Units with no home are ONE critical
     per document (name them all in it); a phase delivering a story/RQ
     absent from CONTEXT is a fabrication-class critical.
  4. Justify shape row by row: does the phase close as something a shopper
     or a consuming feature can observe or call; does its acceptance
     coverage name the branches its requirements carry (permission, error,
     privacy, negative) rather than restating the phase title; could its
     developer-owned verification (unit/integration tests, dev checks) prove
     it done — a phase naming only developer-owned evidence is sufficient,
     since functional/QA proof is out of scope. Fire — quoting the row — on
     layer/task buckets, a standalone foundation phase, a trailing
     cross-cutting phase, or a row with no acceptance coverage or no
     (developer-owned) verification.
  The gate tests the candidate against CONTEXT units and the STANDARD's
  phase laws — NEVER against the GOLDEN's phase names, count, ordering,
  dependency graph, or column wording. A candidate that splits or merges
  differently from the GOLDEN while covering every unit vertically is
  CORRECT, and a plan with fewer phases than the GOLDEN is not thereby
  under-decomposed.
- Fresh-state sweep (closed rule — run BEFORE scoring
  `fresh_planning_state`): scan Open Questions statuses, "Approved by" cells,
  and "Recommendation / Decision" cells, plus the document for
  approval/session claims and `- [ ]` queues. OPEN questions with empty
  approver cells, each carrying a RECOMMENDATION (a recommended answer, not an
  approved one) in its Recommendation / Decision cell, are the REQUIRED fresh
  state — never "incomplete", and the recommendation is never itself a fresh-state
  defect. A recorded approved decision (an APPROVED / DEFERRED-APPROVED status,
  a filled "Approved by", or a Recommendation / Decision cell that records an
  approver/date/session) is a critical EVEN WHEN a source document, meeting
  note, or design sentence appears to support it: approval is a human act in
  the session, never inferred from CONTEXT prose.
- Fabrication sweep: verify closed-world facts against CONTEXT, including
  every magnitude. In mermaid diagrams, judge the CONTENT (participants,
  messages, branches) for groundedness; a syntactically broken or absent
  diagram is a `structure_conformance` warning (or `missing_evidence`),
  never fabrication.
- One defect, one primary critical. Classify by the actual fault:
  - a dropped/phantom requirement or story -> `trace_coverage`;
  - contradicted/weakened/extended behaviour -> `behaviour_fidelity`;
  - a re-decided or contradicted decision, a resurrected alternative ->
    `decision_fidelity`;
  - a BA-scope decision made here, requirement-restating filler instead of
    HOW -> `planning_ownership`;
  - a filled approver/decision row, approval claim, or task queue ->
    `fresh_planning_state`;
  - an invented code, person, magnitude, vendor fact, or URL ->
    `no_fabrication`;
  - a delivery unit with no phase home, a horizontal/layer or foundation
    phase, a postponed cross-cutting phase, an unprovable phase row ->
    `phase_decomposition`.
  Do not raise the same underlying claim under several dimensions.
- Allowed patterns are never findings — under ANY dimension: (a)
  implementation identifiers absent from CONTEXT — inventing them is this
  artifact's JOB; (b) an inapplicable sub-section's single "None —
  <grounded reason>" row with dashes in the remaining cells (no backend
  work on a functional change; no routes on an integration capability);
  (c) OPEN planning questions with empty
  "Approved by" and a recommendation in the "Recommendation / Decision" cell
  (a recommended answer, no approval recorded); (d) planning
  question ids (Q1, Q2…) that reuse numbers seen in grooming — the
  planning table is a fresh namespace, and referencing grooming decisions
  by their ids (Q1/Q2/P1/P2) as sources is correct; (e) a REMOVED-spec
  trace row with "—" in the RQ/WBS cells; (f) a deferred requirement noted
  as excluded from planning; (g) one or several mermaid sequence diagrams
  with alt branches and Notes, plus clarifying prose; (h) skill names in
  parentheses (e.g. `sfnext-routing`, `b2c-custom-caches`) as pointers;
  (i) grounded deferral notes ("TTL per Q2", "contract per Q1") in any
  cell; (j) test rows marked blocked on a grooming prerequisite (P1/P2);
  (k) an implementation choice that strengthens a privacy/security bound
  (e.g. keeping coordinates out of URLs) — tighter is fine; (l) repeating
  an RQ id across several inventory rows when the specs carry several
  requirements under that RQ; (m) area granularity in inventory rows — how
  many areas a Delivery Inventory row names is
  open-world synthesis (a thinner area list than the GOLDEN's is never a
  dropped requirement or story; only a missing ROW breaches the trace
  law); (n) a phase plan whose count, names, ordering, dependency graph,
  and granularity differ from the GOLDEN's while every delivery unit stays
  covered — including a two-phase plan on a small change, phases that run
  in parallel with no dependency, and a phase carrying more than one
  delivery unit when they close as one observable outcome; (o) shared
  scaffolding folded into the first phase that consumes it, and a
  cross-cutting row whose verification is "proven inside each phase" plus a
  change-level pass rather than a phase of its own; (p) a phase whose real
  verification is blocked on a grooming prerequisite (key issuance,
  capability delivery) and is built mock-first meanwhile; (q) consuming or
  citing a lower-authority source (design for HOW, proposal for scope,
  discovery for provenance) — priority is not a reading restriction, so mere
  use is never a finding; only a lower-authority source OVERRIDING signed
  FSD/ISD, specs, or approved grooming on a conflict is; (r) a thin,
  non-optimal, or differently-shaped architecture that still follows the
  contract and grounds its content — architectural quality, elegance, or
  optimality is never a finding (weak-model generator); (s) a Verification
  Strategy or phase/constraint Verification cell that names only
  developer-owned evidence (unit / integration tests, dev checks) and omits
  functional / E2E / manual-QA / accessibility-audit / UAT proof — that proof
  is QA-owned and out of scope for this artifact, so its absence is never a
  finding under any dimension; (t) a Technical Design Overview that states
  SUBJECTS and COUNTS and agrees with the body — however worded, plainer or
  richer than the GOLDEN's — and a Technical Design Source Inventory whose row
  set lists the consumed upstream; differences from GOLDEN's wording, ordering,
  or row phrasing are never findings; (u) a recommendation carried in an OPEN
  question's "Recommendation / Decision" cell — it is the required fresh-state
  content, never an approval.
- Omission is not a critical — under ANY dimension — EXCEPT the trace law
  (a dropped in-scope requirement or story IS critical), the phase-coverage
  law (a delivery unit with no phase row and no classification IS
  critical), and a missing mandatory element (Delivery Inventory,
  Implementation Building Blocks, Verification Strategy, Delivery Phases, Open
  Questions section). Everything else missing (a
  thinner cross-cutting row, an absent diagram, fewer test rows, an
  omitted risk) is `missing_evidence` or a warning.
- Authority check for every finding: if the only authority you can cite is
  "the GOLDEN contains this", the finding is invalid — DROP it. A valid
  finding cites a STANDARD rule or a CONTEXT fact the candidate violates.
- Completeness does not offset a violation, and fluency is not correctness.
  Inspect each table row, diagram message, and status cell on its own
  merits regardless of how polished the document is.

## Scoring rubric

Score each dimension from 0.0 to 1.0 and put it in `rubric_scores` keyed by
the dimension id below. For each dimension, 1.0 = fully satisfied with
evidence, ~0.5 = partially satisfied or minor gaps, 0.0 = violated or absent.

- `trace_coverage` — the closed trace law holds: every in-scope spec
  requirement planned and traced, deferred scope excluded, every story
  preserved, nothing phantom.
- `behaviour_fidelity` — planning restates signed FSD/ISD requirement
  meaning (when present), structured spec scenarios, and approved bounds
  faithfully; nothing contradicted, weakened, extended, or synthesized
  across conflicting artifacts.
- `decision_fidelity` — APPROVED grooming decisions and locked design
  decisions honoured and referenced; design used as HOW/architecture
  working material, not as an independent requirements source;
  deferred-to-planning choices decided or raised; nothing re-decided.
- `planning_ownership` — developer-level HOW throughout; technical
  planning questions with severity and owner; BA scope pushed back, not
  absorbed.
- `fresh_planning_state` — OPEN questions each carrying a recommendation in
  its Recommendation / Decision cell, empty approvers, no approved decision
  recorded, no approval claims, no task queues.
- `no_fabrication` — every closed-world fact traces to CONTEXT; no
  asserted undecided magnitudes; identifiers exempt as own synthesis.
- `phase_decomposition` — Delivery Phases covers every CONTEXT delivery
  unit exactly once or classifies it explicitly; phases are vertical,
  acceptance-covered, area-named, and verifiable; scaffolding folded into
  the phase that consumes it and cross-cutting obligations carried by every
  phase rather than postponed. Verticality fires ONLY on the enumerated
  horizontal anti-patterns (layer/task bucket, standalone foundation phase,
  trailing cross-cutting phase) — never on a subjective "could be decomposed
  better"; count, names, ordering, and granularity are the artifact's own
  synthesis and are never scored for quality.
- `implementation_specificity` — each applicable section carries developer-HOW
  content (surfaces, building blocks, interfaces, runtime flows, constraints,
  verification) rather than restated requirements or empty hand-waving;
  inapplicable sub-sections carry the grounded "None" row; constraints conform
  to design. Judge PRESENCE of HOW-work per the instruction — NOT architectural
  quality, optimality, depth, or completeness of the file map. A thin but
  grounded, instruction-following section is satisfied, and "a stronger design
  exists" is never a finding (the generator runs on a weak model).
- `structure_conformance` — template sections, orders, and table shapes;
  mermaid Runtime Flows per template; Delivery Inventory always present; the
  Technical Design Overview is a subjects+counts reader-map derived from the
  body (a count/claim the body contradicts deducts here; re-listing tables or
  dumping detail is a reader-map warning). Section presence/order and table
  column headings are owned by the deterministic structure gate: when Structure
  gate is PASS, score heading/column exactness as satisfied and do not lower
  this dimension for singular/plural, punctuation, or template-column claims.

### Overall score and pass

- Compute `score` as the mean of the rubric dimension scores, then cap it:
  if any item in `critical_findings` is present, `score` MUST NOT exceed
  0.5.
- `pass` is true only when `score >= threshold` (given in the user message)
  AND `critical_findings` is empty.

### Finding severity

- **critical_findings** — violations of any Forbidden item or of invariants
  1-8 (a trace-law breach, redefined behaviour, a re-decided decision, a
  self-approved plan, an asserted undecided magnitude, fabrication, a
  phase-decomposition breach, internal leakage, a missing mandatory
  element). These block acceptance.
- **warnings** — quality issues that should be fixed but do not make the
  document wrong (e.g. a requirement-restating Details cell, a broken or
  missing mermaid block, a `- [ ]` checkbox appearing inside an otherwise
  planning-grade section, a heading-level slip, an unowned risk row, a
  Technical Design Overview that RE-LISTS the Delivery Inventory rows, phase
  names, or building blocks, restates a section, or dumps implementation detail
  instead of a subjects+counts reader-map, a
  Verification Strategy / phase / constraint cell that authors QA-owned
  functional / E2E / manual-QA / accessibility-audit / UAT verification this
  artifact no longer owns — flag to remove, never a critical).
- **missing_evidence** — expected content the CONTEXT implies but the
  candidate omits without breaking a law (e.g. an absent cross-cutting
  row, an untested spec scenario, an omitted risk the sources imply, an
  absent diagram for a secondary path). Record it ONLY here: it MUST NOT
  appear in `critical_findings` and MUST NOT cap the score.

Always ground findings in concrete evidence. Every critical finding MUST
quote a string that appears VERBATIM in the candidate. Before recording a
critical, locate that exact string (the table row, the cell, the heading,
the status value, the diagram line) in the candidate text; if it is not
literally present, DROP the finding — do not infer, paraphrase, or assume a
row or section exists. For a missing-item finding, name the specific CONTEXT
fact (the spec requirement, the story key, the approved decision) the
candidate omits. A finding whose evidence you cannot copy verbatim from the
candidate is a hallucination, not a violation.
