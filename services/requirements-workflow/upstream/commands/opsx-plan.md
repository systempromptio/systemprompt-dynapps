Plan the implementation - the Dev Planning phase. Take an approved change (BA/SA artifacts already
generated by `/opsx:propose` — at least `specs`, plus optional `design`, `fsd`, `isd`; and `stories.md`
when the change warranted it, scripted from the artifacts by `/opsx:propose-approved`) and generate
`technical-design.md` followed by implementation `tasks.md`.

The BA/SA phase hands off after the specs (and stories when produced). This command picks up from there:
Dev owns `technical-design.md` and `tasks.md`. Keep developer-level HOW in `technical-design.md`; keep `tasks.md`
as the parseable checkbox queue. Like `/opsx:propose`, this STOPS after each artifact for the Per-Artifact
Review Gate (human review + approval) before generating the next one.

When the tasks are ready, run /opsx:apply

## Preflight (MANDATORY FIRST STEP): `/project-sync` + ground every phase in project-context

**This runs before anything else in this command. It is not optional and it is not skippable.** Do not
select the change, read artifacts, or generate `technical-design`/`tasks` before it completes.

1. **Run `/project-sync` first, always.** It fast-forwards the current project branch, force-refreshes
   the OpenSpec schema/config from the library, and syncs + reindexes project-context so retrieval
   reflects the latest project state. `/project-sync` is a preflight, not an OpenSpec artifact step: it
   works only on the current project branch, never merges the shared tooling base branch, does not
   compare OpenSpec templates to existing artifacts, and does not run `openspec status` or
   `openspec instructions`. Do not ask the user what to do unless a step is blocked. Stop on the first
   real failure — never plan on a stale or partially-synced index.

2. **Ground every planning artifact in project-context — not just once.** Planning reads the approved
   specs (the behaviour source of truth), optional architecture design, optional publication docs, and
   stories; when stories exist, Planning uses them as the delivery grouping. Before you produce OR
   advance each artifact — `technical-design`, then `tasks` — **actively re-query project-context (the
   `project-context` skill) for the sources that artifact needs**: prior specs/design, and Jira/Confluence
   for published state and freshness when stories exist. For UI/visual planning inputs, rely on committed
   design assets and the FSD/ISD source docs. Do NOT coast on artifacts already in the change folder or on
   your memory of the BA/SA phase — re-query as you move between artifacts.

---

**Input**: The argument after `/opsx:plan` is the change name (kebab-case). If omitted, infer from
conversation context; if ambiguous, run `openspec list --json` and use the **AskUserQuestion tool** to
let the user select.

**Steps**

1. **Select the change**

   Always announce: "Using change: <name>" and how to override (e.g., `/opsx:plan <other>`).

2. **Check the BA/SA phase is complete**
   ```bash
   openspec status --change "<name>" --json
   ```
   Parse the JSON to get:
   - `applyRequires`: array of artifact IDs needed before implementation (e.g., `["tasks"]`)
   - `artifacts`: list of all artifacts with their status and dependencies

   **Precondition gate:** the BA/SA phase must have produced the specs — `specs` (and its dependencies)
   MUST have `status: "done"`. `design`, `fsd`, `isd`, and `stories` are OPTIONAL / CONDITIONAL; do NOT
   hard-require them. If `specs` is not done, STOP and show:

   ```
   BA/SA artifacts are not complete yet — `specs` is required before planning.

   Run `/opsx:propose <name>` to generate the BA/SA artifacts, then run `/opsx:plan` again.
   ```

   If `stories` exists, read it as the Jira-oriented delivery grouping. Always treat specs as the
   behaviour source of truth. Read `design.md`, FSD, and ISD working copies only when they exist.

   **Stories handoff contract:**
   - If `stories.md` exists, MUST read it from the change directory before the Planning Onboarding
     summary and before generating `technical-design.md`.
   - MUST extract every story heading as a delivery slice: story key/placeholder, title, and Jira key
     state (`<PROJECT>-<number>` or local placeholder).
   - If story headings contain real Jira keys, MUST re-check the corresponding Jira issues through
     project-context/Jira after `/project-sync` for freshness. This check validates board/publication
     state only.
   - DO NOT treat Jira/project-context as the source of behaviour. If Jira text differs from specs,
     STOP and surface the conflict; do not silently change scope.
   - DO NOT report "no stories" or collapse planning to WBS-only requirements when local `stories.md`
     exists, even if project-context retrieval misses the Jira issues.

3. **Mini-onboarding — read the artifacts and brief the reader**

   Before generating anything, load the change context so both the LLM and the developer understand what
   they are about to work on. Read every BA/SA artifact that exists:
   - `discovery.md`, `proposal.md`, `grooming.md`, `specs/**/*.md` (required)
   - `design.md`, `fsd/**/*.md`, `isd/**/*.md`, `stories.md` (only when present)

   For fresh business context, re-check the tracker/Confluence via the `project-context` skill, and
   rely on committed design assets and the FSD/ISD source docs for any UI/visual inputs.

   Then present a short **Planning Onboarding** summary (do not skip — this is the entry point of the
   step) covering:
   - **Ticket / business task** — the tracker ID and the business problem being solved (from
     proposal.md "Why" + discovery intent).
   - **Delivery stories / Jira slices** — every story key and title from `stories.md` when it exists,
     plus Jira visibility/freshness state when real Jira keys are present. If `stories.md` does not
     exist, state "No stories.md for this change — Planning will decompose directly from specs."
   - **High-level task** — what this change delivers at a glance, plus In / Out of scope (from
     proposal.md scope).
   - **Key requirements** — the RQ/WBS groups from specs Trace metadata (one line per group).
   - **Decisions to honour** — human-approved grooming decisions (A#) and any `design.md` constraints that
     Planning must respect.
   - **Open items entering Planning** — any NICE-TO-HAVE grooming questions carried forward, plus
     prerequisites/access still pending from grooming.

   Keep it tight (a short briefing, not a rewrite of the artifacts). Confirm the specs' acceptance
   criteria still match the tracker and, when `stories.md` exists, that each story is covered by specs
   before proceeding. Then continue to the next step.

4. **Generate the Planning artifacts until apply-ready**

   Use the **TodoWrite tool** to track progress.

   Loop through the remaining Planning artifacts in dependency order (typically `technical-design`, then
   `tasks`). Skip any remaining optional BA/SA artifact (`design`, `fsd`, `isd`) that was not generated by
   `/opsx:propose`, and treat `stories.md` (scripted by `/opsx:propose-approved`) as optional too;
   Planning reads all of these only when they already exist.

   a. **For each artifact that is `ready` (dependencies satisfied)**:
      - Get instructions:
        ```bash
        openspec instructions <artifact-id> --change "<name>" --json
        ```
      - The instructions JSON includes:
        - `context`: Project background (constraints for you - do NOT include in output)
        - `rules`: Artifact-specific rules (constraints for you - do NOT include in output)
        - `template`: The structure to use for your output file
        - `instruction`: Schema-specific guidance for this artifact type
        - `outputPath`: Where to write the artifact
        - `dependencies`: Completed artifacts to read for context
      - Read the dependency files for context — `specs/**` (system behaviour), `technical-design.md` for
        `tasks`, and optional `design.md`, `stories.md`, FSD/ISD working copies when they exist
      - When `stories.md` exists, preserve story trace through `technical-design.md` and `tasks.md`.
        `tasks.md` MUST show how each story maps to implementation phases/tasks; cross-cutting tasks may
        be marked as cross-cutting instead of tied to a single story.
      - Create the artifact file using `template` as the structure
      - Apply `context` and `rules` as constraints - but do NOT copy them into the file
      - Show brief progress: "Created <artifact-id>"
      - **For `technical-design` only — BEFORE the summary, run the decomposition walkthrough (MANDATORY,
        chat-only).** Do NOT jump straight from "Created technical-design" to the AskUserQuestion gate.
        First give a short chat-only architecture & decomposition walkthrough: explain the solution shape
        plainly, THEN by the building-a-car-on-an-assembly-line analogy — each delivery phase rolls off the
        line as a drivable car (a vertical, acceptance-closing slice, not a horizontal layer), cross-cutting
        concerns built into every stage rather than bolted on as their own phase, and any deferred part
        fitted "per spec / pending decision". Convey the PRINCIPLE, not a part-by-part map; keep it short;
        NEVER write it into the artifact (it is outside the eval contour) and it never gates approval. Full
        wording: the Per-Artifact Review Gate reference (`artifact-review-gate.md`).
      - Then run the **Per-Artifact Review Gate** (see `openspec-workflow.mdc`) before creating the next
        artifact: STOP, post a short summary + open questions, and offer the choice via the
        **AskUserQuestion tool** — Approve / Request changes, plus **Walk the questions (recommended)
        ONLY when this artifact actually has open questions** (with none, drop Walk; never re-walk
        already-settled decisions). Record
        approval with a named human (never the agent): `technical-design` uses its `## Review & Approval`
        box; `tasks` uses `## Review & Approval` → set `Approved for implementation: yes`. For
        `technical-design`, the CRITICAL Planning gate (step 4b) runs FIRST and must pass before this
        artifact can be approved — that Planning session IS the "Walk the questions" path for it.

   b. **Planning gate — resolve CRITICAL planning questions before `tasks`**
      - `technical-design.md` may raise planning-stage grooming: technical unknowns in its "Planning
        Open Questions" table, tagged CRITICAL or NICE-TO-HAVE, and approved answers in "Planning
        Decisions".
      - After `technical-design.md` is created, if any CRITICAL planning question is still `OPEN`/`BLOCKED`
        or lacks a named human approver, STOP before generating `tasks.md`. Surface the open CRITICAL
        questions and start a chat-based Planning approval session. Do not use the **AskUserQuestion**
        tool for Planning questions.
      - Handle exactly one planning question at a time. For each question, write a concise but complete
        prompt:
        - what the technical unknown is and which implementation area it affects;
        - why it matters before `tasks.md`;
        - what approval/decision is needed now;
        - the available options, with one short explanation of what each option means for implementation,
          test design, risk, or sequencing;
        - the agent recommendation, clearly labelled as a recommendation, not approval;
        - a direct request for the human/dev lead/SA approval.
      - After the user answers, update `technical-design.md`: set the question to APPROVED or
        DEFERRED-APPROVED, add the named `Approved by`, and record the approved answer in that same
        question's "Recommendation / Decision" cell (no separate decisions table).
        Then ask the next planning question in chat.
      - NICE-TO-HAVE questions may be carried into implementation only as DEFERRED-APPROVED with a named
        owner/approver. A question that changes agreed BA scope is not answered here — push it back to
        proposal/grooming as a CR.

   c. **Continue until all `applyRequires` artifacts are complete**
      - After creating each artifact, re-run `openspec status --change "<name>" --json`
      - Check if every artifact ID in `applyRequires` has `status: "done"` in the artifacts array
      - Stop when all `applyRequires` artifacts are done

   d. **If an artifact requires user input** (unclear context):
      - Use **AskUserQuestion tool** to clarify
      - Then continue with creation

5. **Show final status**
   ```bash
   openspec status --change "<name>"
   ```

**Output**

After completing the Dev-phase artifacts, summarize:
- Change name and location
- List of artifacts created with brief descriptions
- Per-artifact review status: `technical-design` and `tasks` approval (by whom); `tasks` shows
  `Approved for implementation`
- What's ready: "Developer technical design and implementation tasks ready."
- Prompt: "Run `/opsx:apply` to start implementing (it confirms `tasks` is Approved for implementation first)."

**Artifact Creation Guidelines**

- Follow the `instruction` field from `openspec instructions` for each artifact type
- The schema defines what each artifact should contain - follow it
- Read dependency artifacts for context before creating new ones (specs, technical-design for tasks, and
  optional design/stories/FSD/ISD when present)
- Use `template` as the structure for your output file - fill in its sections
- **IMPORTANT**: `context` and `rules` are constraints for YOU, not content for the file
  - Do NOT copy `<context>`, `<rules>`, `<project_context>` blocks into the artifact
  - These guide what you write, but should never appear in the output

**Guardrails**
- Stop after EVERY artifact for the **Per-Artifact Review Gate** (`openspec-workflow.mdc`): summarize,
  offer Approve / Request changes (plus Walk the questions ONLY when open questions exist), and get a
  named human's approval before generating the next one. For `technical-design`, the CRITICAL Planning gate must pass first.
  Never self-approve.
- Start with the mini-onboarding briefing before generating artifacts — read the BA/SA artifacts and summarize ticket, business task, and high-level goal so LLM and dev share context
- Honour the planning gate: do NOT generate `tasks.md` while any CRITICAL "Open Question" in `technical-design.md` is still OPEN/BLOCKED or lacks a named human approver — approve it and record the decision in that question's "Recommendation / Decision" cell first
- Do NOT run this before `specs` is done — that is the minimum BA/SA output; `stories` is optional (small changes skip it)
- If `stories.md` exists, do not skip it: preserve every story key/title in Planning Onboarding and
  carry story trace into `technical-design.md` and `tasks.md`
- Create ALL artifacts needed for implementation (as defined by schema's `apply.requires`)
- Always read dependency artifacts before creating a new one
- Dev owns `technical-design.md` and `tasks.md` — `technical-design.md` carries technical design; `tasks.md` carries
  parseable phases and role-tagged work items
- If context is critically unclear, ask the user. Do not self-approve planning questions or decisions to keep momentum
- Verify each artifact file exists after writing before proceeding to next

**Failure Recovery**
Enter this section only after a command in the normal workflow fails.
- Missing OpenSpec CLI: run `openspec --version 2>&1`, then tell the user to install it with
  `npm install -g @fission-ai/openspec@latest`.
- Project not initialized: tell the user to run `openspec init` once, then rerun `/opsx:plan`.
