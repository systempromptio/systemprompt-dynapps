Hi Kateryna — ahead of tomorrow's Google meeting, here's where I've landed on Drive search for Claude Code, so we can plug into whatever Astound decides.

*What I'm trying to achieve*
One connector for the whole organisation. A person signs in once with their Astound Google account in Systemprompt; when they search from Claude Code, Google returns only the Drive documents that person can already open. Every call is governed and audited on our side. No copies of documents, no per-team indexes, no service accounts, nothing for us to curate or re-sync.

*What I found (and proved this morning)*
There are two Google products in play, and they are not interchangeable:

• *RAG Engine* (Vertex AI / Agent Platform) — you import folders into a corpus, it stores a copy, access is by GCP project IAM. Anyone who can query the corpus sees everything in it; Drive sharing is not consulted. I tested this end to end with my own Drive folder — retrieval, citations and the MCP tools all work — but it forces one corpus per readership and someone has to own re-imports. This is what Vladimir's team built for Victor's project.

• *Gemini Enterprise — Google Drive data store* — federated (nothing copied), covers the whole Workspace Drive, and searches *as the signed-in user*, filtered by that person's own Drive permissions. GA MCP server. This is the "organisation-level product" your Google account manager described, and it's the one that gives us the target above.

*The catch, which Vladimir rightly flagged*
Gemini Enterprise is licensed: a subscription on the billing account, licenses distributed to one GCP project + location, and a seat assigned to every person who searches. Neither of the existing projects has licenses today. So the ask is one dedicated project (e.g. `astound-drive-search`), licenses distributed there, and seats for the pilot group — the per-seat price is the number Terry needs.

*UK vs USA — one solution or two?*
For permissions, one. Google filters per user, so a single app serves everyone. The only reasons we'd end up with two:
1. *Data residency* — a data store lives in one multi-region (`eu` or `us`). If US content must stay in the US, that's one per region.
2. *Separate Workspace domains* — federated Drive search only returns documents owned by the searcher's own domain. If UK and US staff are on different Google Workspace domains, a UK user never sees US-owned files regardless of sharing.
Could you confirm which of those applies? That decides whether it's one app or two.

*What I need from whichever solution is chosen*
Same four things either way — the connector on our side is already built and handles both products:
1. The MCP endpoint and region
2. The engine (or corpus) resource name
3. The OAuth scope the endpoint requires
4. An internal-audience OAuth client with our callback: `https://astound.systemprompt.io/api/public/connectors/google_drive/callback`
Plus `roles/mcp.toolUser` and search access for my account so I can run the acceptance test: two users, one file only one of them can open, the other must not see it.
