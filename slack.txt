Good question. The connector calls Google *as the signed-in user*: each person's own OAuth token, not a service account. So when someone searches, Google checks whether *that person* is allowed to use the search engine in `astound-knowledge-uk-sales`. Without the roles, sign-in succeeds but every search is refused (`tools.call denied`), which is exactly the error we hit before.

The two roles are the minimum for that call:
• `roles/mcp.toolUser`: allowed to call Google's hosted MCP endpoint
• `roles/discoveryengine.viewer`: allowed to query the search engine (read-only; can't change the engine or data stores)

Neither gives access to anyone's data. Google filters every result to what the person can already open in Drive, Gmail and Calendar, so a user only ever sees their own mail/calendar and the files already shared with them.

Domain-wide (`domain:astounddigital.com`) is just the simplest way to say "anyone at Astound who connects", so new starters work without anyone touching IAM. If you'd rather keep it narrower, granting the same two roles to a Google group (e.g. the UK pilot group) works just as well. Access is then managed by group membership.

@s.kubrakov this needs Owner or Project IAM Admin on `astound-knowledge-uk-sales` (Volod doesn't have it):
```
gcloud projects add-iam-policy-binding astound-knowledge-uk-sales --member="domain:astounddigital.com" --role="roles/mcp.toolUser"
gcloud projects add-iam-policy-binding astound-knowledge-uk-sales --member="domain:astounddigital.com" --role="roles/discoveryengine.viewer"
```
Or in the console: IAM & Admin → IAM → Grant access → principal `astounddigital.com` → add both roles → Save.
